# 9장 AWS 컨테이너 아키텍처

## 마이크로서비스, ECR, ECS, EKS

---

# 9.1 컨테이너 아키텍처 개요

애플리케이션을 실행하는 방식은 계속 발전해 왔음.

초기에는 물리 서버에 직접 애플리케이션을 설치했고, 이후 가상머신 기반으로 여러 서버를 나누어 사용하게 되었음.

ㅓ그리고 최근에는 컨테이너 기반 배포가 매우 일반적인 방식이 되었음.

컨테이너가 주목받는 이유는 다음과 같음.

* 애플리케이션 실행 환경을 일관되게 만들 수 있음

* 배포 단위를 가볍게 가져갈 수 있음

* 개발 환경과 운영 환경 차이를 줄일 수 있음

* 마이크로서비스 구조와 잘 맞음

* 자동화와 확장에 유리함

즉, 컨테이너는 단순히 “가볍게 실행되는 기술”이 아니라

**현대적인 애플리케이션 배포와 운영 방식의 핵심 구성요소**임.

---

# 9.2 전통적인 배포 방식의 한계

컨테이너의 필요성을 이해하려면 먼저 기존 배포 방식의 한계를 봐야 함.

예를 들어 하나의 서버에 다음을 직접 설치한다고 가정하면

* 운영체제

* 웹 서버

* 런타임

* 라이브러리

* 애플리케이션

이 방식은 다음 문제를 일으키기 쉬움.

### 1. 환경 차이

개발 서버와 운영 서버의 패키지 버전이 다르면 예상하지 못한 오류가 발생할 수 있음.

### 2. 의존성 충돌

서로 다른 애플리케이션이 같은 서버에서 다른 버전의 라이브러리를 요구할 수 있음.

### 3. 배포 재현성 부족

새 서버에 동일한 환경을 다시 만드는 과정이 복잡할 수 있음.

### 4. 확장 속도 한계

새 인스턴스를 띄운 뒤 패키지를 설치하고 애플리케이션을 구성하는 시간이 오래 걸릴 수 있음.

즉, 서버 중심 배포 방식은 규모가 커질수록 관리 부담이 커짐.

---

# 9.3 컨테이너란 무엇인가

컨테이너는 애플리케이션과 그 실행에 필요한 라이브러리, 설정, 종속성을 하나의 패키지로 묶어 실행하는 기술임.

핵심은 다음과 같음.

```
애플리케이션이 어디서 실행되든 동일한 방식으로 동작하도록 실행 환경을 함께 묶는다.
```

즉, 컨테이너는 “코드만 배포”하는 것이 아니라

**코드 + 실행 환경을 함께 배포하는 방식**이라고 볼 수 있음.

---

# 9.4 가상머신과 컨테이너 차이

학생들이 가장 많이 헷갈리는 부분 중 하나가

가상머신과 컨테이너를 비슷한 것으로 보는 점임.

둘 다 격리된 실행 환경을 제공하지만 구조가 다름.

| 항목 | 가상머신 | 컨테이너 |
| --- | --- | --- |
| 격리 단위 | OS 전체 | 프로세스/애플리케이션 |
| 포함 내용 | Guest OS 포함 | 애플리케이션과 종속성 |
| 무게 | 상대적으로 무거움 | 상대적으로 가벼움 |
| 시작 속도 | 느린 편 | 빠른 편 |
| 자원 효율성 | 낮을 수 있음 | 높음 |

가상머신은 하이퍼바이저 위에 게스트 OS 전체를 올리는 구조임.

반면 컨테이너는 호스트 OS 커널을 공유하면서 프로세스를 격리하는 방식임.

즉, 컨테이너는 더 가볍고 빠르게 확장하기 좋음.

---

# 9.5 컨테이너의 장점

### 1. 일관된 실행 환경

개발 환경, 테스트 환경, 운영 환경 차이를 줄일 수 있음.

### 2. 빠른 배포

이미지 단위로 배포하므로 실행 준비가 빠름.

### 3. 높은 자원 효율성

게스트 OS 전체를 매번 띄우지 않아도 됨.

### 4. 마이크로서비스 친화성

서비스를 작은 단위로 쪼개 배포하기 좋음.

### 5. 확장 자동화에 유리함

동일 이미지 기반으로 인스턴스를 여러 개 복제하기 쉬움.

즉, 컨테이너는 배포 속도와 운영 유연성 측면에서 강점이 큼.

---

# 9.6 컨테이너의 한계와 고려사항

컨테이너가 만능은 아님.

다음과 같은 운영 복잡성이 생길 수 있음.

### 1. 오케스트레이션 필요

컨테이너 수가 많아지면 배포, 장애 복구, 확장, 네트워크 연결을 수동 관리하기 어려움.

### 2. 상태 저장 문제

컨테이너는 본질적으로 일시적인 실행 단위이므로 상태 저장을 별도 설계해야 함.

### 3. 네트워크와 보안 복잡성

서비스 간 통신, 인증, 접근 제어, 비밀값 관리가 중요해짐.

### 4. 운영 추적성 필요

로그, 모니터링, 버전 관리가 더 중요해짐.

즉, 컨테이너 자체보다

**컨테이너를 대규모로 어떻게 관리할 것인가**가 실제 핵심 과제임.

---

# 9.7 Docker 개요

컨테이너 기술을 설명할 때 가장 대표적으로 언급되는 것이 Docker임.

Docker는 컨테이너 이미지를 만들고 실행하고 배포하는 데 널리 사용되는 도구임.

Docker를 이해할 때 중요한 요소

* Docker Image

* Docker Container

* Dockerfile

* Registry

이 개념을 먼저 이해하면 AWS의 ECR, ECS, EKS도 훨씬 쉽게 이해할 수 있음.

---

# 9.8 Docker Image

이미지는 컨테이너 실행에 필요한 파일과 설정을 담고 있는 불변 패키지임.

쉽게 말하면 “컨테이너의 실행 원본”임.

예를 들어 하나의 이미지 안에는 다음이 포함될 수 있음.

* 애플리케이션 코드

* 런타임

* 라이브러리

* 환경 설정 일부

* 실행 명령

즉, 이미지는 실행 가능한 템플릿이고, 컨테이너는 그 이미지를 기반으로 실행된 인스턴스라고 보면 됨.

---

# 9.9 Container

컨테이너는 이미지를 실제로 실행한 결과물임.

이미지가 설계도라면 컨테이너는 그 설계도로 띄운 실행 중 프로세스임.

이미지와 컨테이너의 관계

```
Image → 실행 → Container
```

같은 이미지를 여러 번 실행하면 여러 개의 컨테이너를 만들 수 있음.

이 특성 때문에 동일한 애플리케이션을 여러 개 손쉽게 복제해 확장하기 좋음.

---

# 9.10 Dockerfile

Dockerfile은 이미지를 만들기 위한 정의 파일임.

즉, 컨테이너 이미지를 어떻게 구성할지를 코드처럼 적어 놓은 파일임.

예를 들어 Dockerfile에는 다음 정보가 들어갈 수 있음.

* 어떤 베이스 이미지를 사용할지

* 어떤 파일을 복사할지

* 어떤 패키지를 설치할지

* 어떤 명령으로 애플리케이션을 실행할지

즉, Dockerfile은

**애플리케이션 실행 환경을 코드로 정의하는 파일**임.

이 점에서 CloudFormation이 인프라 정의 파일이라면, Dockerfile은 애플리케이션 실행 환경 정의 파일이라고 볼 수 있음.

---

# 9.11 Registry

Registry는 컨테이너 이미지를 저장하고 배포하는 저장소임.

Docker 이미지를 만들었다면 어딘가에 보관하고, 필요할 때 가져와야 함.

그 역할을 하는 것이 Registry임.

대표적인 예

* Docker Hub

* Amazon ECR

즉, 이미지가 애플리케이션 패키지라면 Registry는 그 패키지 보관소임.

---

# 9.12 마이크로서비스 개요

컨테이너 아키텍처를 설명할 때 마이크로서비스를 빼놓기 어려움.

둘은 자주 함께 사용되기 때문임.

마이크로서비스는 애플리케이션을 하나의 거대한 단일 프로그램으로 만드는 대신,

작고 독립적인 여러 서비스로 나누어 구성하는 아키텍처 방식임.

예를 들어 전자상거래 시스템을 생각하면 다음처럼 나눌 수 있음.

* 사용자 서비스

* 주문 서비스

* 상품 서비스

* 결제 서비스

* 알림 서비스

즉, 기능별로 독립된 서비스 단위로 나누는 방식임.

---

# 9.13 모놀리식과 마이크로서비스 차이

### 모놀리식 아키텍처

애플리케이션 전체가 하나의 큰 배포 단위로 구성됨.

장점

* 초기 구조가 단순함

* 개발과 배포가 직관적일 수 있음

한계

* 일부 기능 변경도 전체 재배포가 필요할 수 있음

* 규모가 커질수록 복잡도가 증가함

* 특정 기능만 독립 확장하기 어려움

### 마이크로서비스 아키텍처

기능별로 작은 서비스로 분리함.

장점

* 독립 배포 가능

* 서비스별 확장 가능

* 기술 스택 선택 유연성 증가

* 장애 영향 범위를 줄일 수 있음

한계

* 서비스 간 통신 복잡도 증가

* 운영 복잡도 증가

* 모니터링, 배포, 인증, 데이터 관리가 어려워질 수 있음

즉, 마이크로서비스는 강력하지만 운영 난이도도 같이 올라감.

---

# 9.14 컨테이너와 마이크로서비스의 관계

마이크로서비스는 논리적 아키텍처 방식이고, 컨테이너는 그 서비스를 배포하기 좋은 실행 단위임.

둘은 같은 개념이 아니지만 매우 잘 맞음.

왜 잘 맞는가

* 각 서비스를 독립 이미지로 만들기 쉬움

* 서비스별로 다른 배포 주기를 가질 수 있음

* 서비스별 개별 확장이 가능함

* 동일한 실행 환경을 유지하기 쉬움

즉, 마이크로서비스를 운영할 때 컨테이너가 매우 유용한 배포 단위가 됨.

---

# 9.15 오케스트레이션의 필요성

컨테이너를 하나만 실행하는 것은 비교적 단순함.

하지만 운영 환경에서는 다음 상황이 발생함.

* 컨테이너가 여러 대의 서버에 분산 실행됨

* 장애가 나면 자동 재시작이 필요함

* 트래픽 증가 시 컨테이너 수를 늘려야 함

* 이미지 버전을 교체해 무중단 배포가 필요함

* 네트워크 연결과 서비스 디스커버리가 필요함

즉, 컨테이너가 많아질수록 “실행”보다 “관리”가 더 어려워짐.

이 문제를 해결하는 것이 컨테이너 오케스트레이션임.

AWS에서는 이 영역을 대표적으로 다음 서비스가 담당함.

* ECS

* EKS

---

# 9.16 Amazon ECR 개요

Amazon ECR은 **Elastic Container Registry**의 약자임.

AWS에서 제공하는 관리형 컨테이너 이미지 저장소임.

역할은 매우 명확함.

```
컨테이너 이미지를 안전하게 저장하고, 배포 대상이 그 이미지를 가져가도록 한다.
```

즉, ECR은 실행 환경이 아니라 **이미지 저장소**임.

---

# 9.17 ECR의 역할

ECR은 다음 용도로 사용됨.

* Docker 이미지 저장

* 버전 태깅

* ECS/EKS 배포용 이미지 제공

* 접근 제어

* AWS IAM과 통합된 인증

예를 들어 개발자가 애플리케이션 이미지를 빌드한 뒤 ECR에 업로드하면,

ECS나 EKS가 그 이미지를 pull해서 컨테이너를 실행함.

즉, ECR은 컨테이너 배포 파이프라인의 시작점이라고 볼 수 있음.

---

# 9.18 ECR의 장점

### 1. AWS 통합

IAM, ECS, EKS와 자연스럽게 연동됨.

### 2. 이미지 버전 관리

태그를 통해 버전을 구분할 수 있음.

### 3. 보안 통제

누가 어떤 이미지를 업로드하고 가져갈지 제어 가능함.

### 4. 운영 단순화

별도 사설 레지스트리를 직접 구축하지 않아도 됨.

즉, ECR은 AWS 환경에서 컨테이너 이미지를 관리하기 위한 표준 저장소 역할을 함.

---

# 9.19 Amazon ECS 개요

Amazon ECS는 **Elastic Container Service**의 약자임.

AWS의 관리형 컨테이너 오케스트레이션 서비스임.

쉽게 말하면 다음 역할을 함.

* 컨테이너를 어디서 실행할지 결정

* 몇 개를 실행할지 관리

* 장애가 나면 다시 실행

* 업데이트 시 교체

* 로드 밸런서와 연결

* 오토스케일링 연동

즉, ECS는 컨테이너를 “저장”하는 서비스가 아니라

**컨테이너를 실행하고 운영하는 서비스**임.

---

# 9.20 ECS의 핵심 개념

ECS를 이해할 때 중요한 개념

* Cluster

* Task Definition

* Task

* Service

* Launch Type

---

## 9.20.1 Cluster

클러스터는 ECS가 컨테이너를 실행하는 논리적 영역임.

즉, 실행 대상과 관리 범위를 묶는 단위라고 보면 됨.

---

## 9.20.2 Task Definition

Task Definition은 컨테이너를 어떻게 실행할지 정의한 설계서임.

포함 예시

* 어떤 이미지 사용할지

* 몇 개 컨테이너를 묶을지

* CPU/메모리 얼마나 쓸지

* 환경변수

* 포트

* 로그 설정

즉, Task Definition은 ECS 버전의 실행 청사진임.

---

## 9.20.3 Task

Task는 Task Definition을 실제로 실행한 단위임.

즉, 이미지를 바탕으로 띄운 컨테이너 실행 단위라고 보면 됨.

---

## 9.20.4 Service

Service는 원하는 수의 Task를 계속 유지하도록 관리하는 기능임.

예를 들어 3개의 Task를 항상 유지하고 싶다면, Service가 이를 보장함.

Task 하나가 죽으면 새로 다시 띄우는 식으로 동작함.

즉, Service는 운영 환경에서 지속적으로 애플리케이션을 유지하는 핵심 개념임.

---

# 9.21 ECS Launch Type

ECS는 컨테이너를 어디서 실행할지에 따라 대표적으로 두 가지 방식을 가짐.

* EC2 Launch Type

* Fargate Launch Type

---

## 9.21.1 EC2 Launch Type

ECS용 EC2 인스턴스를 직접 준비하고, 그 위에서 컨테이너를 실행하는 방식임.

특징

* EC2 서버 관리가 필요함

* 더 세밀한 제어 가능

* 특정 커스텀 환경이 필요할 때 유리할 수 있음

즉, ECS를 쓰더라도 하부 서버 운영 책임이 일부 남아 있음.

---

## 9.21.2 Fargate Launch Type

서버를 직접 관리하지 않고 컨테이너를 실행하는 방식임.

즉, 서버리스에 가까운 컨테이너 실행 모델임.

특징

* EC2 인스턴스 관리 불필요

* 컨테이너 단위로 실행

* 운영 단순화

* 빠른 시작과 학습에 유리함

교육 환경이나 표준적인 웹 애플리케이션에서는 Fargate가 설명하기 쉬움.

---

# 9.22 ECS와 로드 밸런서

운영 환경에서는 ECS Service를 ALB와 연결해서 트래픽을 분산하는 경우가 많음.

구조 예

```
사용자
  │
ALB
  │
ECS Service
  │
여러 Task
```

이 구조에서는 ALB가 요청을 여러 Task로 분산하고, ECS는 Task 개수를 유지함.

즉, ECS는 컨테이너 운영 계층, ALB는 트래픽 진입 계층 역할을 함.

---

# 9.23 ECS와 Auto Scaling

ECS도 부하에 따라 확장할 수 있음.

단, EC2 Auto Scaling과 개념이 조금 다름.

여기서는 인스턴스 수가 아니라 주로 **Task 수**를 조정함.

예

* 요청 증가 → Task 수 증가

* 부하 감소 → Task 수 감소

즉, ECS에서의 스케일링은

“서버 수 조정”보다 “컨테이너 실행 단위 조정” 관점으로 보는 것이 더 적절함.

---

# 9.24 Amazon EKS 개요

Amazon EKS는 **Elastic Kubernetes Service**의 약자임.

AWS에서 제공하는 관리형 Kubernetes 서비스임.

즉, Kubernetes를 AWS 환경에서 비교적 쉽게 운영할 수 있도록 제어 영역을 관리해 주는 서비스임.

중요한 점은 다음임.

```
ECS는 AWS 자체 컨테이너 오케스트레이션 서비스이고,
EKS는 Kubernetes 기반 오케스트레이션 서비스다.
```

즉, 둘 다 컨테이너를 운영하지만 기반 철학과 생태계가 다름.

---

# 9.25 Kubernetes 개요

Kubernetes는 컨테이너 오케스트레이션을 위한 오픈소스 플랫폼임.

대규모 컨테이너 배포, 확장, 복구, 네트워킹을 자동화하기 위해 널리 사용됨.

핵심 목적

* 원하는 수의 컨테이너 유지

* 장애 시 자동 복구

* 무중단 배포 지원

* 서비스 디스커버리

* 확장 자동화

즉, Kubernetes는 컨테이너를 “띄우는 도구”가 아니라

**대규모 컨테이너 운영 플랫폼**임.

---

# 9.26 EKS가 필요한 이유

Kubernetes를 직접 구축하려면 제어 플레인, 인증, 네트워크, 업그레이드, 고가용성 등을 많이 관리해야 함.

이 부담이 크기 때문에 AWS에서는 EKS를 제공함.

EKS의 의미

* Kubernetes 제어 영역 운영 부담 완화

* AWS 서비스와 연계 쉬움

* 표준 Kubernetes 생태계 활용 가능

* 멀티클라우드/하이브리드 경험과 연결 가능

즉, EKS는 “Kubernetes를 AWS에 맞게 쉽게 운영하는 방식”이라고 보면 됨.

---

# 9.27 ECS와 EKS 차이

이 둘은 매우 자주 비교됨.

| 항목 | ECS | EKS |
| --- | --- | --- |
| 기반 | AWS 고유 서비스 | Kubernetes |
| 학습 난이도 | 비교적 낮음 | 상대적으로 높음 |
| 유연성/생태계 | AWS 중심 | Kubernetes 생태계 활용 |
| 운영 복잡도 | 상대적으로 낮음 | 상대적으로 높음 |
| 이식성 | 낮은 편 | 높은 편 |

즉,

* **AWS에 최적화된 단순한 운영**을 원하면 ECS가 적합할 수 있음

* **Kubernetes 표준과 확장성**이 중요하면 EKS가 적합할 수 있음

---

# 9.28 Fargate와 EKS/ECS 관계

Fargate는 별도의 오케스트레이터가 아니라 **컨테이너 실행 방식**에 가까움.

ECS와도 함께 사용할 수 있고, EKS에서도 일부 방식으로 활용할 수 있음.

즉, 관계를 정리하면 다음과 같음.

* ECR : 이미지 저장

* ECS / EKS : 컨테이너 오케스트레이션

* Fargate : 서버 관리 없이 컨테이너 실행

이 구분을 명확히 해야 학생들이 서비스 역할을 헷갈리지 않음.

---

# 9.29 컨테이너 네트워크와 서비스 연결

컨테이너 환경에서는 단순히 애플리케이션을 띄우는 것만이 아니라, 서비스 간 연결 방식도 중요함.

주요 고려 요소

* 서비스 디스커버리

* 내부 통신 방식

* 로드 밸런서 연결

* 보안 그룹 또는 네트워크 정책

* 외부 공개 여부

즉, 컨테이너 환경도 결국 네트워크 아키텍처 위에서 동작함.

VPC, Subnet, Security Group과의 연결을 이해해야 전체 구조가 보임.

---

# 9.30 상태 비저장과 상태 저장

컨테이너 아키텍처를 설명할 때 중요한 원칙 중 하나는 **상태 비저장(Stateless)** 설계임.

왜냐하면 컨테이너는 쉽게 생성되고 쉽게 종료될 수 있기 때문임.

따라서 운영 환경에서는 다음과 같이 분리하는 것이 일반적임.

* 애플리케이션 컨테이너 : 상태 비저장

* 데이터 저장소 : 외부 서비스 사용

예

* 데이터베이스 → RDS, DynamoDB

* 세션 → Redis

* 파일 → S3, EFS

즉, 컨테이너 자체에 중요한 데이터를 저장하는 방식은 피하는 것이 일반적임.

---

# 9.31 컨테이너 보안 고려사항

컨테이너 환경에서도 보안은 매우 중요함.

주요 관점

### 1. 이미지 보안

신뢰할 수 없는 이미지를 사용하면 위험함.

### 2. 비밀정보 관리

DB 비밀번호, API 키를 이미지에 직접 넣으면 안 됨.

### 3. 권한 최소화

컨테이너가 AWS 서비스에 접근할 때 최소 권한 원칙이 필요함.

### 4. 네트워크 제한

서비스 간 불필요한 통신을 줄여야 함.

즉, 컨테이너가 가볍다고 해서 보안이 단순해지는 것은 아니며,

오히려 이미지·레지스트리·런타임까지 포함해 더 넓게 봐야 함.

---

# 9.32 운영 관점의 컨테이너 아키텍처

컨테이너 환경에서는 다음 요소를 함께 봐야 함.

* 이미지 저장소

* 배포 자동화

* 서비스 확장

* 로깅

* 모니터링

* 장애 복구

* 버전 롤백

* 네트워크 연결

* 비밀값 관리

즉, 컨테이너는 실행 기술 하나가 아니라

**배포, 운영, 확장, 복구를 포함하는 운영 체계 전체와 연결된 아키텍처 주제**임.

---

# 9.33 멀티 티어 아키텍처와 컨테이너의 연결

기존 EC2 기반 멀티 티어 구조를 컨테이너 기반으로 바꾸면 다음처럼 볼 수 있음.

```
사용자
  │
ALB
  │
ECS Service 또는 EKS Workload
  │
RDS / Redis / DynamoDB / S3
```

즉, 웹·앱 계층이 EC2 인스턴스 대신 컨테이너 오케스트레이션 환경으로 대체되는 구조임.

이 구조의 의미는 다음과 같음.

* 애플리케이션 계층 배포가 더 유연해짐

* 서비스별 독립 배포가 쉬워짐

* 확장 단위가 인스턴스보다 더 작아짐

* 마이크로서비스 구조와 잘 맞음

# 9.34 서비스 역할 한 번에 정리

이 장에서 학생들이 가장 헷갈리지 않게 이해해야 하는 핵심 구분은 다음임.

## ECR

컨테이너 이미지를 저장하는 곳임.

## ECS

AWS 방식으로 컨테이너를 실행하고 운영하는 서비스임.

## EKS

Kubernetes 기반으로 컨테이너를 운영하는 서비스임.

## Fargate

서버를 직접 관리하지 않고 컨테이너를 실행하는 방식임.

즉,

```
이미지는 ECR에 저장한다.
컨테이너는 ECS 또는 EKS에서 운영한다.
서버 관리 없이 실행하려면 Fargate를 사용할 수 있다.
```

이렇게 정리하면 됨.
