# 6장 AWS 스토리지 서비스

## 6.1 스토리지 서비스란 무엇인가

스토리지 서비스는 데이터를 저장하기 위한 서비스이다.

애플리케이션은 단순히 실행만 되는 것이 아니라, 실행 과정에서 지속적으로 데이터를 생성하고 읽고 수정하고 보관한다.

따라서 컴퓨팅 자원만으로는 서비스를 운영할 수 없고, 반드시 데이터를 담아둘 저장소가 필요하다.

예를 들어 웹 서비스를 운영한다고 가정하면 다음과 같은 데이터가 존재한다.

```
웹 애플리케이션 실행 파일
운영체제 파일
사용자가 업로드한 이미지와 문서
데이터베이스가 저장하는 레코드
시스템 로그와 애플리케이션 로그
백업 파일과 아카이브 데이터
```

이러한 데이터는 모두 성격이 다르다.

* 운영체제와 애플리케이션 실행 파일은 서버에 직접 연결된 디스크 형태가 적합함

* 여러 서버가 동시에 접근해야 하는 파일은 공유 파일 시스템이 적합함

* 이미지, 로그, 백업처럼 대량으로 저장해야 하는 데이터는 객체 스토리지가 적합함

즉, 모든 데이터를 하나의 저장 방식으로 처리하지 않음.

데이터의 성격과 접근 방식에 따라 적절한 스토리지 유형을 선택해야 함.

온프레미스 환경에서는 이러한 저장소를 직접 설계하고 구축해야 했음.

예를 들어 다음과 같은 작업이 필요했음.

```
디스크 용량 산정
스토리지 서버 구매
RAID 구성
SAN / NAS 장비 연결
백업 장비 운영
장애 복구 구성
확장 시 장비 증설
```

이 방식은 초기 비용이 크고, 확장에 시간이 많이 들며, 운영 복잡도가 높았음.

AWS에서는 이러한 스토리지 기능을 관리형 서비스 형태로 제공한다.

즉 사용자는 장비 구매나 물리적 설치보다, 어떤 유형의 저장소를 사용할지에 집중하면 된다.

대표적인 AWS 스토리지 서비스는 다음과 같다.

```
Amazon EBS
Amazon EFS
Amazon S3
```

각 서비스는 저장 구조와 접근 방식, 성능 특성, 비용 모델이 다르다.

따라서 스토리지 서비스는 단순히 “데이터를 저장하는 곳”이 아니라, **시스템 구조와 성능, 운영 방식에 직접 영향을 주는 핵심 구성 요소**라고 볼 수 있다.

---

## 6.2 스토리지 유형

클라우드 스토리지는 크게 세 가지 유형으로 구분된다.

```
Block Storage
File Storage
Object Storage
```

이 세 가지는 단순한 이름 차이가 아니라, 데이터를 바라보는 방식 자체가 다르다.

---

## 6.2.1 Block Storage

Block Storage는 데이터를 작은 블록 단위로 나누어 저장하는 방식이다.

운영체제는 이 블록들을 디스크처럼 인식하고 파일 시스템을 생성해서 사용한다.

즉 애플리케이션 입장에서는 “저장 서비스”라기보다 “하드디스크”처럼 보인다.

대표 서비스는 Amazon EBS이다.

구조는 다음과 같이 이해하면 된다.

```
EC2
 └ EBS Volume
```

특징은 다음과 같다.

```
운영체제 설치 가능
낮은 지연시간
고성능 입출력 처리 가능
데이터베이스 워크로드에 적합
EC2에 직접 연결해서 사용
```

Block Storage는 디스크 수준의 제어가 가능하기 때문에 다음과 같은 용도에 적합하다.

```
운영체제 루트 볼륨
데이터베이스 저장소
애플리케이션 전용 디스크
고성능 파일 시스템 구성
```

즉 Block Storage는 “서버에 붙는 디스크”라고 이해하면 된다.

---

## 6.2.2 File Storage

File Storage는 파일 시스템 형태로 데이터를 저장하는 방식이다.

사용자는 디렉터리와 파일 구조를 기준으로 데이터를 접근한다.

여러 서버가 같은 파일 시스템을 공유할 수 있다는 점이 큰 특징이다.

대표 서비스는 Amazon EFS이다.

구조는 다음과 같다.

```
EC2
 ├ EFS
EC2
 └ EFS
```

특징은 다음과 같다.

```
표준 파일 시스템 제공
여러 서버가 동시에 접근 가능
공유 디렉터리 구성 가능
파일 단위 접근 가능
```

예를 들면 다음과 같은 상황에서 사용한다.

```
여러 웹 서버가 같은 업로드 디렉터리를 사용해야 하는 경우
애플리케이션 서버가 공통 설정 파일을 공유해야 하는 경우
분산 환경에서 동일한 파일 시스템이 필요한 경우
```

즉 File Storage는 “공유 네트워크 드라이브”처럼 이해하면 된다.

---

## 6.2.3 Object Storage

Object Storage는 데이터를 객체 단위로 저장하는 방식이다.

이 방식에서는 파일을 블록으로 직접 관리하거나 운영체제의 파일 시스템처럼 마운트해서 다루는 것이 아니라, 각 데이터를 하나의 독립된 객체로 저장한다.

대표 서비스는 Amazon S3이다.

객체는 보통 다음 요소로 구성된다.

```
실제 데이터
메타데이터
고유한 식별자(Key)
```

특징은 다음과 같다.

```
대규모 확장에 유리
매우 높은 내구성
HTTP API 기반 접근
정적 데이터 저장에 적합
```

Object Storage는 다음과 같은 용도에 적합하다.

```
이미지 파일 저장
동영상 저장
백업 파일 저장
로그 파일 저장
데이터 레이크 저장소
정적 웹 자원 저장
```

즉 Object Storage는 “대규모 파일 보관소”이자 “API 기반 데이터 저장소”로 이해하면 된다.

---

## 6.2.4 세 가지 스토리지 유형의 차이

세 가지 유형은 모두 데이터를 저장하지만, 사용하는 방식이 다르다.

| 구분 | 저장 방식 | 접근 방식 | 대표 서비스 | 적합한 용도 |
| --- | --- | --- | --- | --- |
| Block Storage | 블록 단위 | 디스크처럼 연결 | EBS | 운영체제, DB, 고성능 저장소 |
| File Storage | 파일 시스템 | 파일/디렉터리 접근 | EFS | 공유 파일 시스템 |
| Object Storage | 객체 단위 | API/HTTP 접근 | S3 | 이미지, 백업, 로그, 정적 콘텐츠 |

이 차이를 정확히 이해해야 AWS 스토리지 서비스를 올바르게 선택할 수 있다.

---

# 6.3 Amazon EBS

EBS는 Elastic Block Store의 약자이다.

Amazon EC2에 연결해서 사용하는 블록 스토리지 서비스이다.

EBS는 EC2 인스턴스의 외장 디스크이자, 경우에 따라서는 루트 디스크 역할도 한다.

구조는 다음과 같다.

```
EC2 Instance
 └ EBS Volume
```

EBS의 핵심 특징은 다음과 같다.

```
블록 스토리지
지속성 보장
스냅샷 지원
고성능 입출력 처리 가능
EC2와 함께 사용
```

여기서 중요한 점은 **지속성(Persistence)** 이다.

EC2 인스턴스를 중지했다가 다시 시작하더라도, 연결된 EBS 볼륨의 데이터는 유지된다.

즉 컴퓨팅 자원과 저장 자원을 어느 정도 분리해서 운영할 수 있다.

---

## 6.3.1 EBS의 역할

EBS는 다음과 같은 역할로 자주 사용된다.

```
EC2의 루트 볼륨
데이터베이스 디스크
애플리케이션 로그 저장소
트랜잭션 처리용 고성능 스토리지
```

예를 들어 MySQL, PostgreSQL, Oracle 같은 데이터베이스는 지연시간과 입출력 성능이 중요하기 때문에 주로 EBS 위에서 운영한다.

---

## 6.3.2 EBS의 특징

### 1) EC2에 연결해서 사용

EBS는 독립적으로 사용하는 저장소가 아니라, 기본적으로 EC2와 연결해서 사용하는 디스크이다.

즉 EBS만 단독으로 웹에서 접근하는 형태가 아니라, EC2가 EBS를 파일 시스템으로 마운트해서 사용한다.

---

### 2) 데이터 지속성 보장

인스턴스를 재부팅하거나 중지해도 EBS 자체가 삭제되지 않는 한 데이터는 유지된다.

이는 임시 스토리지와 구분되는 중요한 특징이다.

---

### 3) Snapshot 지원

EBS는 특정 시점의 데이터를 스냅샷으로 백업할 수 있다.

스냅샷은 Amazon S3 기반으로 저장되며, 다음과 같은 용도로 활용된다.

```
백업
복구
새 볼륨 생성
운영환경 복제
재해 복구 구성
```

---

### 4) 성능 특화 스토리지

EBS는 범용 SSD, 프로비저닝 IOPS SSD, 처리량 최적화 HDD 등 다양한 볼륨 유형을 제공한다.

따라서 워크로드 특성에 따라 비용과 성능을 조정할 수 있다.

즉 EBS는 단순 디스크가 아니라, **성능 요구사항에 맞춰 선택하는 클라우드 블록 스토리지**이다.

---

# 6.4 Amazon EFS

EFS는 Elastic File System의 약자이다.

AWS에서 제공하는 관리형 파일 스토리지 서비스이다.

EFS는 여러 EC2 인스턴스가 동시에 같은 파일 시스템에 접근할 수 있도록 설계되었다.

구조는 다음과 같다.

```
EC2 A ─┐
EC2 B ─┼─ EFS
EC2 C ─┘
```

---

## 6.4.1 EFS의 특징

```
파일 시스템 기반 저장소
여러 인스턴스에서 동시 접근 가능
자동 확장
관리형 서비스
리눅스 기반 공유 스토리지로 적합
```

EFS는 다음과 같은 환경에 잘 어울린다.

```
웹 서버 팜의 공용 업로드 디렉터리
공유 콘텐츠 저장소
컨테이너 기반 애플리케이션의 공용 파일 영역
분산 애플리케이션의 공통 파일 시스템
```

즉 EFS는 “여러 서버가 함께 쓰는 파일 저장소”라는 점이 핵심이다.

---

## 6.4.2 EBS와 EFS의 차이

EBS와 EFS는 이름이 비슷하지만 목적이 다르다.

| 항목 | EBS | EFS |
| --- | --- | --- |
| 저장 방식 | 블록 스토리지 | 파일 스토리지 |
| 연결 대상 | 보통 단일 EC2 중심 | 여러 EC2 동시 접근 |
| 사용 목적 | OS, DB, 고성능 디스크 | 공유 파일 시스템 |
| 접근 방식 | 디스크처럼 연결 | 파일 시스템 마운트 |

정리하면 다음과 같다.

```
EBS는 서버 전용 디스크
EFS는 서버 공동 사용 파일 시스템
```

---

# 6.5 Amazon S3

S3는 Simple Storage Service의 약자이다.

AWS에서 제공하는 대표적인 객체 스토리지 서비스이다.

S3는 AWS 환경에서 매우 자주 사용되며, 단순 파일 저장소를 넘어 백업, 로그 저장, 정적 웹 호스팅, 데이터 분석 기반 저장소 등 다양한 역할을 수행한다.

S3의 기본 구조는 다음과 같다.

```
Bucket
 └ Object
```

---

## 6.5.1 Bucket

Bucket은 객체를 저장하는 논리적 컨테이너이다.

쉽게 말하면 파일을 담는 최상위 저장 공간이다.

예시는 다음과 같다.

```
my-company-images
my-backup-data
my-log-storage
```

Bucket의 특징은 다음과 같다.

```
전 세계에서 유일한 이름 사용
특정 Region에 생성
객체 저장의 최상위 단위
권한 관리와 정책 적용의 기준 단위
```

여기서 “전 세계에서 유일한 이름”이라는 점이 중요하다.

S3는 글로벌 네임스페이스를 사용하므로 동일한 버킷 이름을 다른 사용자가 이미 사용 중이면 생성할 수 없다.

---

## 6.5.2 Object

Object는 S3에 저장되는 실제 데이터이다.

Object는 단순히 파일만 의미하지 않는다.

S3 내부에서는 각 데이터를 객체로 저장하며, 이 객체는 파일 내용뿐 아니라 추가 정보도 함께 가진다.

구성 요소는 다음과 같다.

```
Object Data
Metadata
Key
```

설명하면 다음과 같다.

* **Object Data**: 실제 파일 내용

* **Metadata**: 콘텐츠 타입, 생성 정보 등 부가 정보

* **Key**: 객체를 식별하는 이름

예를 들어 다음과 같은 형태가 가능하다.

```
images/logo.png
videos/intro.mp4
backup/2026-03-23/db-backup.zip
```

여기서 `images/logo.png` 같은 문자열이 Key이다.

중요한 점은 S3는 전통적인 파일 시스템의 폴더를 실제로 가지는 것이 아니라, **Key 이름을 통해 폴더처럼 보이게 표현**한다는 점이다.

즉 다음 구조는 실제 디렉터리 구조라기보다 논리적 표현이다.

```
images/
 └ logo.png
```

실제로는 하나의 Key 값일 뿐이다.

---

# 6.6 S3의 핵심 특징

## 6.6.1 높은 내구성

S3는 매우 높은 내구성을 제공한다.

AWS는 S3 객체를 여러 가용 영역 기반 인프라에 분산 저장하여 데이터 손실 가능성을 매우 낮춘다.

일반적으로 다음과 같이 표현한다.

```
99.999999999% durability
```

이를 흔히 **11 9's durability**라고 부른다.

여기서 중요한 것은 **내구성(Durability)** 과 **가용성(Availability)** 을 구분하는 것이다.

* 내구성은 데이터가 손실되지 않을 가능성

* 가용성은 필요할 때 접근할 수 있는 가능성

즉 내구성이 높다는 말은 “데이터가 잘 보존된다”는 의미이지, 항상 100% 즉시 접근 가능하다는 의미와는 다르다.

---

## 6.6.2 높은 확장성

S3는 저장 용량을 미리 할당하지 않는다.

즉 사용자는 디스크를 증설하거나 파티션을 조정할 필요 없이 필요한 만큼 데이터를 저장하면 된다.

이 특성 때문에 다음과 같은 대규모 데이터 저장에 적합하다.

```
대량 이미지 저장
로그 축적
백업 아카이브
분석용 원천 데이터 저장
```

운영자가 저장소 증설 작업에 직접 관여하지 않아도 된다는 점이 큰 장점이다.

---

## 6.6.3 HTTP 및 API 기반 접근

S3는 HTTP, HTTPS, SDK, CLI, API를 통해 접근할 수 있다.

즉 서버에 디스크를 연결하듯 사용하는 방식이 아니라, 네트워크를 통해 객체를 요청하는 방식이다.

예를 들면 다음과 같은 URL 형식으로 접근할 수 있다.

```
https://bucket-name.s3.amazonaws.com/image.jpg
```

또는 애플리케이션에서는 AWS SDK를 사용해서 객체 업로드와 다운로드를 수행한다.

이 특성 때문에 S3는 웹 애플리케이션과 매우 잘 어울린다.

---

## 6.6.4 관리형 서비스

S3는 사용자가 디스크 장애, RAID 구성, 스토리지 증설, 하드웨어 교체를 직접 처리하지 않아도 된다.

즉 인프라 운영 부담을 줄이고, 데이터 저장 그 자체에 집중할 수 있게 해준다.

---

## 6.6.5 높은 범용성

S3는 단순한 파일 저장소를 넘어 매우 다양한 AWS 서비스와 연계된다.

예를 들면 다음과 같다.

```
CloudFront와 연계한 정적 콘텐츠 배포
Athena와 연계한 데이터 분석
Glue와 연계한 ETL
Backup 및 Archive 저장소
CloudTrail / VPC Flow Logs 저장소
```

즉 S3는 AWS 데이터 저장의 중심 축에 가까운 서비스이다.

---

# 6.7 S3 주요 사용 사례

S3는 매우 넓은 범위에서 사용된다.

---

## 6.7.1 정적 웹사이트 호스팅

HTML, CSS, JavaScript, 이미지처럼 서버 측 연산이 필요 없는 정적 리소스를 S3에 저장하고 웹으로 제공할 수 있다.

대표 예시는 다음과 같다.

```
회사 소개 페이지
문서 배포 사이트
정적 프론트엔드 페이지
```

S3 자체 웹사이트 호스팅 기능을 사용할 수도 있고, CloudFront와 함께 구성할 수도 있다.

---

## 6.7.2 이미지 및 미디어 저장

사용자가 업로드하는 프로필 이미지, 상품 이미지, 동영상 파일 등을 저장하는 용도로 매우 많이 사용된다.

장점은 다음과 같다.

```
대용량 저장 가능
확장 용이
애플리케이션 서버와 저장소 분리 가능
```

즉 웹 서버 내부 디스크에 파일을 보관하지 않고, 외부 저장소로 분리해서 확장성과 관리성을 높일 수 있다.

---

## 6.7.3 로그 저장

서버 로그, 애플리케이션 로그, 접근 로그, 감사 로그 등을 장기 저장하는 데 적합하다.

예를 들어 다음 서비스들이 S3를 로그 저장소로 자주 사용한다.

```
CloudTrail
ALB Access Log
VPC Flow Log
애플리케이션 백업 로그
```

---

## 6.7.4 백업 및 아카이브

데이터베이스 덤프, 시스템 백업 파일, 장기 보관 문서를 저장하는 용도로 적합하다.

필요에 따라 S3 스토리지 클래스를 조정하면 비용 최적화도 가능하다.

예를 들어 자주 접근하지 않는 데이터는 저비용 스토리지 클래스로 이동할 수 있다.

---

## 6.7.5 데이터 분석 저장소

S3는 데이터 레이크의 중심 저장소로 자주 사용된다.

대량의 CSV, JSON, Parquet 같은 파일을 저장해 두고 Athena, EMR, Glue, Redshift Spectrum 같은 서비스가 이를 분석 대상으로 사용한다.

즉 S3는 단순 저장소이면서 동시에 분석 플랫폼의 기반 저장소가 되기도 한다.

---

# 6.8 EBS, EFS, S3를 언제 선택하는가

스토리지 서비스를 비교할 때 가장 중요한 질문은 다음이다.

```
이 데이터는 어떤 방식으로 접근되는가
한 대의 서버만 쓰는가, 여러 대가 공유하는가
운영체제 디스크처럼 필요한가
파일 공유가 필요한가
대량 객체 저장이 필요한가
```

선택 기준은 다음과 같이 정리할 수 있다.

---

## EBS를 선택하는 경우

```
EC2에 디스크를 직접 붙여야 하는 경우
운영체제 설치가 필요한 경우
데이터베이스처럼 높은 성능이 필요한 경우
저지연 블록 스토리지가 필요한 경우
```

---

## EFS를 선택하는 경우

```
여러 EC2가 동시에 같은 파일을 사용해야 하는 경우
공유 업로드 디렉터리가 필요한 경우
파일 시스템 형태의 저장소가 필요한 경우
```

---

## S3를 선택하는 경우

```
대량 파일을 저장해야 하는 경우
정적 콘텐츠를 저장하는 경우
로그와 백업을 보관하는 경우
HTTP/API 기반 접근이 필요한 경우
확장성과 내구성이 중요한 경우
```

---

# 6.9 스토리지 서비스 비교

| 서비스 | 유형 | 접근 방식 | 대표 용도 | 핵심 특징 |
| --- | --- | --- | --- | --- |
| EBS | Block Storage | EC2에 디스크처럼 연결 | OS, DB, 애플리케이션 디스크 | 고성능, 저지연 |
| EFS | File Storage | 여러 인스턴스가 파일 시스템으로 접근 | 공유 파일 영역 | 동시 공유 가능 |
| S3 | Object Storage | HTTP/API 기반 접근 | 이미지, 로그, 백업, 정적 웹 | 대규모 확장, 높은 내구성 |

---

# 6.10 핵심 정리

AWS의 대표적인 스토리지 서비스는 저장 방식에 따라 다음과 같이 구분된다.

```
Block Storage  → Amazon EBS
File Storage   → Amazon EFS
Object Storage → Amazon S3
```

각 서비스는 서로 대체 관계라기보다, 목적이 다른 서비스이다.

* EBS는 EC2에 연결하는 디스크

* EFS는 여러 서버가 공유하는 파일 시스템

* S3는 대규모 객체 저장소

특히 Amazon S3는 다음과 같은 이유로 매우 중요하다.

```
높은 내구성
무제한에 가까운 확장성
HTTP/API 기반 접근
정적 콘텐츠, 로그, 백업, 분석 저장소로 폭넓게 활용 가능
```

스토리지 서비스를 올바르게 선택하는 것은 단순 저장 공간 확보 문제가 아니라,

애플리케이션 성능, 확장성, 운영 편의성, 비용 구조까지 결정하는 중요한 설계 요소이다.
