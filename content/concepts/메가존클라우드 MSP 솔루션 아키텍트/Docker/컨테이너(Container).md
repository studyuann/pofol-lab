# 컨테이너(Container)

## 0. 가상화 기술의 진화

### 0.1 물리 서버 시대의 문제

예전에는 애플리케이션(웹/DB/배치 등)을 **물리 서버 1대에 1개**씩 깔아 운영하는 경우가 많았다.

**문제점**

* 서버 자원이 남음: CPU 5%, 메모리 20% 쓰는데도 서버는 한 대를 통째로 사용

* 환경 구축이 느림: OS 설치 → 패치 → 미들웨어 설치 → 설정 → 배포 (시간이 오래 걸림)

* 장애 영향 범위 큼: 한 서버에 여러 앱이 있으면 서로 영향(라이브러리 충돌/포트 충돌)

---

### 0.2 하이퍼바이저 기반 가상화(VM)의 등장

이 문제를 해결하려고 **VM(가상머신)** 이 등장.

### VM이란?

* 물리 서버 위에 **하이퍼바이저**(KVM/VMware/Hyper-V 등)를 올리고

* 그 위에 **가상 하드웨어**(가상 CPU, 가상 디스크, 가상 NIC)를 만들고

* 각 VM마다 **게스트 OS**를 따로 설치해 애플리케이션을 실행

### VM의 장점

* OS 수준으로 완전 분리(다른 커널, 다른 OS 가능)

* 강한 격리(보안/장애 영향 최소화)

* 서버 자원 활용률 증가(한 대에서 여러 VM)

### VM의 한계(컨테이너가 등장한 이유)

* 무겁다: VM마다 OS가 있어 디스크/메모리 사용량이 큼

* 느리다: 부팅이 OS 부팅이라 분 단위로 걸릴 수 있음

* 이미지가 크다: VM 이미지(수 GB~수십 GB)는 이동/배포가 느림

> 정리
>
> VM은 “서버를 쪼개는 데” 매우 강력하지만, **배포/이식/빠른 확장**에는 부담이 있었다.

---

## 1. 컨테이너란 무엇인가?

### 1-1. 컨테이너의 정의

컨테이너(Container)는 **애플리케이션과 그 실행에 필요한 모든 의존성(라이브러리, 설정 파일 등)을 하나의 실행 단위로 패키징**한 기술이다.

> 핵심 키워드

* **프로세스 격리**

* **운영체제 커널 공유**

* **가볍고 빠른 실행**

컨테이너는 가상머신(VM)처럼 보이지만 **OS 전체를 가상화하지 않는다**는 점이 가장 큰 차이점이다.

---

### 1-2. 컨테이너가 등장한 배경

### 기존 서버 운영 방식의 문제

1. **환경 불일치 문제**
   * 개발 서버에서는 정상
   * 운영 서버에서는 오류

     → “내 PC에서는 되는데요?”

2. **리소스 낭비**
   * VM 1대 = OS 1개
   * 애플리케이션 하나 돌리는데 OS 전체 필요

3. **배포 속도 저하**
   * 서버 생성 → OS 설치 → 패키지 설치 → 설정

👉 이런 문제를 해결하기 위해 **컨테이너 기술**이 등장

## 2. 컨테이너 vs 가상머신(VM)

[![](https://s7280.pcdn.co/wp-content/uploads/2018/07/containers-vs-virtual-machines.jpg)](https://s7280.pcdn.co/wp-content/uploads/2018/07/containers-vs-virtual-machines.jpg)

### 2-1. 구조 비교

| 구분 | 가상머신(VM) | 컨테이너 |
| --- | --- | --- |
| 가상화 대상 | 하드웨어 | OS 커널 |
| OS 포함 여부 | 포함 | 미포함 |
| 실행 단위 | OS + App | App + 라이브러리 |
| 부팅 속도 | 수십 초 ~ 분 | 수 초 |
| 리소스 사용 | 무거움 | 매우 가벼움 |

### 2-2. 요약

* **VM**: “서버를 가상으로 만든다”

* **컨테이너**: “프로세스를 격리해서 실행한다”

## 3. 컨테이너 내부 동작 원리

### 3-1. 컨테이너는 ‘프로세스’다

컨테이너는 리눅스에서 보면 **일반 프로세스**다.

```
ps aux | grep nginx
```

👉 컨테이너로 실행한 nginx도 **호스트 프로세스 목록에 보임**

---

### 3-2. Namespace

Namespace는 **하나의 리눅스 시스템을 여러 개의 독립된 공간으로 나누는 기능**이다.

컨테이너마다 namespace가 다르기 때문에,

* 프로세스가 다르게 보이고

* hostname이 다르게 보이고

* 네트워크가 분리된 것처럼 보인다

실제로는 같은 서버지만, 각 컨테이너는 **자기만의 환경을 가진 것처럼 보이게 된다.**

| Namespace | 역할 |
| --- | --- |
| PID | 프로세스 ID 격리 |
| NET | 네트워크 인터페이스 격리 |
| MNT | 파일시스템 마운트 격리 |
| UTS | hostname 격리 |
| IPC | 프로세스 간 통신 격리 |
| USER | 사용자 ID 격리 |

👉 컨테이너 안에서는

* PID 1부터 시작

* 자기만의 네트워크가 있는 것처럼 보임

---

### 3-3 Namespace 실습

> 실습은 가상 머신에서 root 권한으로 진행한다.

---

### 1) hostname만 분리해 보기 (UTS namespace)

### ① 새로운 namespace에서 쉘 실행

```
unshare --uts /bin/bash
```

* `unshare` : 기존 환경과 분리해서 실행

* `-uts` : hostname을 따로 쓰도록 분리

* `/bin/bash` : 분리된 환경에서 bash 실행

→ **hostname만 다른 공간으로 들어간다**

---

### ② hostname 변경

```
hostname test-container
```

* 현재 공간의 hostname을 `test-container`로 변경

* 이 변경은 **지금 공간에만 적용**

---

### ③ hostname 확인

```
hostname
```

* 현재 공간의 hostname 출력

---

### ④ 호스트에서 확인

```
hostname
```

* 호스트의 hostname은 바뀌지 않는다

→ **같은 서버지만 이름이 다른 공간**

---

### 3-4 프로세스가 분리된 환경 (PID namespace)

이번에는 **프로세스 자체를 분리**한다.

---

### 1) PID namespace 생성

```
unshare --pid --fork --mount-proc /bin/bash
```

* `-pid` : 프로세스 번호를 따로 사용

* `-fork` : 새로 분리된 환경에서 프로세스 시작

* `-mount-proc` : 프로세스 정보를 새 기준으로 표시

* `/bin/bash` : 분리된 환경에서 bash 실행

→ **프로세스 세계 자체가 분리된 공간**

---

### 2) 실행 중인 프로세스 확인

```
ps -ef
```

* 현재 실행 중인 모든 프로세스 출력

결과:

* 실행 중인 프로세스 수가 매우 적다

* `bash`가 PID 1로 보인다

→ **이 공간에서는 내가 시스템의 첫 프로세스처럼 보인다**

---

### 3) 현재 namespace 확인

```
ls -l /proc/self/ns
```

* 현재 쉘이 속한 namespace 정보를 보여준다

* 숫자가 다르면 다른 namespace

---

### 3-5. cgroups – “자원을 제한하는 기술”

cgroups(Control Groups)는 **CPU, 메모리, 디스크 I/O 사용량 제한**을 담당한다.

**즉, 프로세스가 사용할 수 있는 자원의 양을 제한하는 기능**이다.

* CPU를 얼마나 쓸 수 있는지

* 메모리를 얼마나 쓸 수 있는지

를 커널이 **강제로 제한**한다.

Namespace가 “보이지 않게 나누는 것”이라면,

cgroup은 “마음대로 못 쓰게 막는 것”이다.

예시:

* CPU 1코어만 사용

* 메모리 512MB 제한

👉 없으면?

* 컨테이너 하나가 서버 자원 독점 가능

---

### 3-6. CPU 제한의 두 가지 방식

CPU 제한에는 **두 가지 서로 다른 개념**이 있다.

1. **CPU를 얼마나 사용할 수 있는가** (사용량 제한)

2. **어떤 CPU 코어를 사용할 수 있는가** (CPU 지정)

---

### 1) CPU 제한용 cgroup 생성

```
mkdir /sys/fs/cgroup/test
```

* CPU 제한을 적용할 그룹을 만든다

---

### 2) CPU 사용량 제한 설정

```
echo "50000 100000" > /sys/fs/cgroup/test/cpu.max
```

**이 설정의 의미**

* 0.1초 동안

* CPU를 0.05초만 사용 가능

* 결과적으로 **CPU 50% 제한**

---

### 3) 현재 쉘을 제한 대상에 포함

```
echo $$ > /sys/fs/cgroup/test/cgroup.procs
```

* `$$` : 현재 쉘의 프로세스 번호

* 이 쉘과 그 안에서 실행되는 프로그램을

  CPU 제한 그룹에 포함

⚠️ 이 시점에서는

**모든 CPU 코어를 사용할 수 있다.**

---

### 4) CPU 부하 발생

```
yes > /dev/null
```

* CPU를 계속 사용하도록 만드는 명령

다른 터미널에서:

```
top
```

* CPU 사용률이 50% 근처에서 더 올라가지 않는다

---

### 3-6. CPU 코어 지정

**특정 CPU 코어만 사용하도록 제한**한다.

---

### 1) 사용할 CPU 코어 지정

```
echo "0,1" > /sys/fs/cgroup/test/cpuset.cpus
```

* 이 그룹에 속한 프로세스는

  CPU 0번과 1번 코어만 사용 가능

예:

* `0` → CPU 0번만 사용

* `2-3` → CPU 2번부터 3번까지 사용

---

### 2) 결과 확인

```
yes > /dev/null
```

다른 터미널에서:

```
top
```

* CPU 0, 1번만 사용률이 올라간다

* 다른 CPU는 거의 사용되지 않는다

---

### 3-7. CPU 제한 정리

| 구분 | 의미 |
| --- | --- |
| cpu.max | CPU를 얼마나 쓸 수 있는지 |
| cpuset.cpus | 어떤 CPU를 쓸 수 있는지 |
| cgroup.procs | 어떤 프로세스에 적용할지 |

## 자원 제한 정리

| 자원 | 제한 가능 여부 | 목적 |
| --- | --- | --- |
| CPU | ⭕ | 과도한 연산 방지 |
| 메모리 | ⭕ | 메모리 폭주 방지 |
| 디스크 I/O | ⭕ | 디스크 독점 방지 |
| 프로세스 수 | ⭕ | 시스템 보호 |
| 네트워크 | △ | 간접적 제어 |

> 컨테이너 = Namespace(격리) + cgroups(제어)

[![](https://miro.medium.com/1%2AAkZf5G5bfV7vq9XT9b83vQ.png)](https://miro.medium.com/1%2AAkZf5G5bfV7vq9XT9b83vQ.png)

### 4-1. 이미지란?

컨테이너 이미지는 **컨테이너 실행을 위한 템플릿**이다.

* OS 일부

* 라이브러리

* 애플리케이션

* 설정 파일

---

### 4-2. 이미지의 Layer 구조

이미지는 **읽기 전용 Layer들의 집합**이다.

```
[ App Layer ]
[ Runtime Layer ]
[ OS Base Layer ]
```

👉 공통 Layer는 **재사용**됨

👉 디스크 절약 + 빌드 속도 향상

---

### 4-3. 컨테이너 실행 시

* 이미지 → 읽기 전용

* 컨테이너 → 쓰기 가능한 Layer 추가

```
Container RW Layer
------------------
Image Layers (RO)
```

## 6. 컨테이너 네트워크 개념

### 6-1. 기본 구조

* 컨테이너는 **가상 네트워크 인터페이스**를 가짐

* 브리지 네트워크를 통해 통신

```
Container → veth → bridge → host NIC
```

---

### 6-2. 포트 포워딩

```
-p 8080:80
```

* 호스트 8080 → 컨테이너 80

👉 외부 접근을 위해 필수

## 8. 컨테이너의 장점과 한계

### 8-1. 장점

* 리소스 효율성

* CI/CD 친화적
