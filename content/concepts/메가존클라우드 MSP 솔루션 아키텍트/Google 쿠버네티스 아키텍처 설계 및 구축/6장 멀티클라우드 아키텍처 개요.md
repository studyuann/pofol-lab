# 6장. 멀티클라우드 아키텍처 개요

## 장 개요

## 학습 목표

* 네트워크, 인증, 관찰성 관점에서 멀티클라우드 설계 포인트를 설명할 수 있음

* 단순 연결과 아키텍처 목적 중심 연결의 차이를 설명할 수 있음

* GKE와 AWS 자산을 연결하는 상위 설계 흐름을 설명할 수 있음

* 다음 장에서 다룰 HA VPN 실습의 목적을 이해할 수 있음

# 1. 멀티클라우드란 무엇인가

멀티클라우드는 **둘 이상의 퍼블릭 클라우드 환경을 함께 사용하는 아키텍처**를 말한다.

예를 들어 AWS와 GCP를 동시에 사용하는 구조가 대표적이다.

하지만 멀티클라우드를 단순히 아래처럼 이해하면 부족하다.

* AWS도 씀

* GCP도 씀

* 둘 다 있으면 멀티클라우드

실제 아키텍처 관점에서는 아래가 더 중요하다.

* 어떤 워크로드를 어느 클라우드에 둘 것인가

* 두 클라우드 사이에 어떤 데이터가 오갈 것인가

* 네트워크를 어떤 방식으로 연결할 것인가

* 인증과 접근 제어를 어디까지 통합할 것인가

* 장애와 운영 책임을 어떻게 나눌 것인가

멀티클라우드는 여러 CSP 환경을 함께 사용하는 아키텍처 패턴이고, 각 클라우드에 맞는 최적의 환경을 선택할 수 있다는 장점이 있다. 동시에 운영 복잡성 증가도 고려해야 한다.

---

# 2. 왜 AWS와 GCP를 함께 쓰는가

## 대표 이유

* 기존 AWS 자산이 이미 많음

* GKE 또는 Google Cloud 특정 서비스 도입이 필요함

* 조직 또는 사업부마다 사용하는 클라우드가 다름

* 특정 워크로드는 AWS, 특정 워크로드는 GCP가 더 적합함

* 벤더 종속을 줄이고 싶음

* 지역, 비용, 조직 구조, 인수합병 등의 이유로 다중 클라우드가 자연스럽게 형성됨

---

# 3. 멀티클라우드가 잘 맞는 대표 시나리오

## 3.1 기존 AWS 기반 서비스 + 신규 GKE 도입

* 기존 서비스는 AWS에 있음

* 신규 Kubernetes 플랫폼은 GKE로 운영하고 싶음

* 두 환경 간 API 호출, 내부 서비스 연동, 데이터 접근이 필요함

즉, 기존 EKS/EC2 기반 자산 위에 GKE를 추가하는 구조로 이해하면 된다.

---

## 3.2 리전 또는 서비스별 최적화

* 특정 데이터 처리나 AI/분석 워크로드는 GCP

* 기존 애플리케이션 계층은 AWS

* 필요한 구간만 사설 연결

---

## 3.3 단계적 이전 또는 공존 구조

* 모든 것을 한 번에 옮기지 않음

* 일정 기간 AWS와 GCP가 공존

* 필요한 서비스만 순차 이전

* 연결은 VPN 또는 더 강한 전용 연결로 유지

---

# 4. 멀티클라우드는 무엇을 먼저 결정해야 하는가

멀티클라우드를 설계할 때 가장 먼저 해야 하는 일은 **연결 기술 선택**이 아니다.

먼저 아래를 결정해야 한다.

## 4.1 무엇을 공유할 것인가

* 네트워크만 연결할 것인가

* 서비스 호출까지 할 것인가

* 데이터베이스를 공유할 것인가

* 인증을 통합할 것인가

## 4.2 무엇을 분리할 것인가

* 운영 도메인

* 보안 경계

* 장애 도메인

* 변경 관리 범위

## 4.3 누가 어느 영역을 책임지는가

* AWS 네트워크팀

* GCP 플랫폼팀

* 보안팀

* 애플리케이션팀

---

# 5. 멀티클라우드 설계의 4가지 핵심

## 5.1 네트워크

* AWS VPC와 GCP VPC를 어떻게 연결할 것인가

* 라우팅을 정적으로 할 것인가, 동적으로 할 것인가

* 어떤 CIDR 대역을 쓸 것인가

* 어떤 경로만 열 것인가

---

## 5.2 인증과 권한

* 양쪽 클라우드의 IAM을 완전히 통합할 것인가

* 워크로드 간 호출은 어떤 자격 모델을 사용할 것인가

* 장기 자격 증명을 어디까지 허용할 것인가

---

## 5.3 관찰성과 운영

* 로그와 메트릭을 어디서 볼 것인가

* 장애 분석 기준은 어느 플랫폼인가

* 운영자가 양쪽 환경을 모두 이해해야 하는가

* 중앙 운영 모델을 둘 것인가

---

## 5.4 보안 경계

* 어떤 서브넷끼리만 통신하게 할 것인가

* API 서버를 외부에 노출할 것인가

* 데이터는 어느 구간을 암호화할 것인가

* 어떤 쪽이 trust anchor 역할을 하는가

멀티클라우드에서는 “연결”보다 “경계 정의”가 더 중요하다.

---

# 6. 연결 방식은 왜 VPN부터 시작하는가

AWS와 GCP를 연결하는 방식은 여러 가지가 있을 수 있지만, 실습에서는 **VPN** 부터 시작하는 것이 가장 적절하다.

## 이유

* 개념이 비교적 명확함

* 사설 네트워크 연결 구조를 이해하기 좋음

* BGP와 동적 라우팅까지 연결 가능

* 하이브리드/멀티클라우드의 기본 감각을 익히기 좋음

---

# 7. 왜 HA VPN이 중요한가

* 단순 Site-to-Site VPN이 아니라

* 운영형 멀티클라우드 연결을 위해 고가용성 구조를 고려해야 함

* 이중 터널, 이중 인터페이스, 동적 라우팅 감각이 중요함

---

# 8. GKE와 AWS를 연결할 때 자주 나오는 구조

## 예시 구조

* GKE 클러스터는 GCP VPC 안에 있음

* AWS에는 EKS 또는 EC2 기반 서비스가 있음

* 두 VPC를 HA VPN으로 연결

* 내부 CIDR끼리 통신 가능하게 함

* 필요 시 GKE 워크로드가 AWS 내부 서비스에 접근

* 또는 AWS 워크로드가 GKE 내부 서비스에 접근

---

# 10. 멀티클라우드 설계 시 질문 체크리스트

* 왜 두 클라우드를 연결하는가

* 어느 서비스가 어느 방향으로 통신하는가

* 어떤 CIDR을 사용할 것인가

* 동적 라우팅이 필요한가

* 어떤 서브넷/포트만 열 것인가

* 장애가 나면 어떤 쪽이 우선인가

* 로그와 메트릭은 어디서 볼 것인가

* 운영자는 어느 경로로 접근하는가

---

# 11. 장 요약

* 멀티클라우드는 두 개 이상의 퍼블릭 클라우드를 함께 사용하는 아키텍처다.

* 설계의 핵심은 연결 기술보다 목적, 경계, 운영 책임 분배다.

* AWS와 GCP를 함께 쓰는 대표 시나리오는 기존 자산 공존, 최적 워크로드 배치, 단계적 이전이다.

* 멀티클라우드는 네트워크, IAM, 관찰성, 보안 경계를 함께 봐야 한다.

* VPN은 멀티클라우드 사설 연결의 기본 패턴을 이해하기 좋은 출발점이다.

### 핵심 결론

**멀티클라우드는 “연결 기술”보다 “왜 연결하는가”를 먼저 정의해야 하며, VPN 실습은 그 목적을 구현하는 수단이다.**
