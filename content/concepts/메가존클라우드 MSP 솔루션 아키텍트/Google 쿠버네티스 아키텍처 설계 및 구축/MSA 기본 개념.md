# MSA 기본 개념

## 1. 학습 목표

* MSA가 무엇인지 설명할 수 있음

* 모놀리식 아키텍처와 MSA의 차이를 설명할 수 있음

* 왜 MSA를 사용하는지 이해할 수 있음

* MSA를 구성하는 대표 요소를 말할 수 있음

* MSA의 장점과 단점을 균형 있게 설명할 수 있음

* 이후 간단한 실습에서 어떤 부분을 확인해야 하는지 감을 잡을 수 있음

---

# 2. MSA란 무엇인가

MSA는 **Microservices Architecture**의 약자다.

이 구조는 하나의 큰 애플리케이션을 여러 개의 **작고 독립적인 서비스**로 나누어 구성하는 방식이다.

예를 들어 쇼핑몰 시스템이 있다고 가정해보자.

하나의 큰 프로그램 안에 다음 기능이 모두 들어갈 수 있다.

* 회원 관리

* 상품 관리

* 주문 처리

* 결제 처리

* 배송 관리

* 알림 발송

모놀리식 구조에서는 이런 기능들이 **하나의 애플리케이션** 안에 함께 들어간다.

반면 MSA에서는 기능별로 나누어 다음처럼 구성할 수 있다.

* 회원 서비스

* 상품 서비스

* 주문 서비스

* 결제 서비스

* 배송 서비스

* 알림 서비스

즉, **기능을 서비스 단위로 잘게 나누고**, 이 서비스들이 서로 통신하면서 하나의 전체 시스템을 이루는 구조라고 보면 된다.

---

# 3. 왜 MSA가 등장했는가

과거에는 하나의 애플리케이션으로 묶어서 개발하는 방식이 훨씬 일반적이었음.

이 방식은 구조가 단순하고 시작이 쉬웠다.

그런데 서비스 규모가 커지면서 문제가 생겼다.

예를 들어 다음과 같은 상황이 발생한다.

* 코드가 너무 커져서 수정이 어려움

* 작은 기능 하나 수정해도 전체를 다시 배포해야 함

* 특정 기능만 트래픽이 몰려도 전체 애플리케이션을 확장해야 함

* 여러 팀이 동시에 개발하면 충돌이 많아짐

* 장애가 발생했을 때 영향 범위가 커짐

이런 문제를 줄이기 위해 **기능별로 나누고 독립적으로 운영하자**는 생각이 발전했고, 그 결과가 MSA다.

즉, **서비스 규모 확대와 운영 복잡성 증가에 대응하기 위해 나온 방식**이다.

---

# 4. 모놀리식과 MSA 비교

## 4.1 모놀리식 아키텍처

모놀리식은 말 그대로 **하나로 뭉쳐 있는 구조**다.

프론트엔드, 비즈니스 로직, 데이터 접근 코드가 하나의 애플리케이션 안에 들어가는 경우가 많다.

### 특징

* 개발 초기에 만들기 쉬움

* 배포 방식이 단순함

* 테스트 구조가 비교적 단순함

* 작은 규모에서는 빠르게 개발 가능함

### 한계

* 코드가 커질수록 유지보수가 어려워짐

* 일부 기능만 수정해도 전체 배포가 필요함

* 장애 전파 범위가 큼

* 기술 스택 변경이 어려움

* 팀이 커질수록 협업 충돌이 많아짐

---

## 4.2 MSA

MSA는 기능을 서비스 단위로 분리한다.

각 서비스는 독립적으로 개발, 배포, 확장이 가능하다.

### 특징

* 기능별로 서비스 분리

* 서비스별 독립 배포 가능

* 서비스별 독립 확장 가능

* 서비스 간 네트워크 통신 사용

* 각 서비스가 자체 데이터 저장소를 가질 수 있음

### 한계

* 구조가 복잡해짐

* 네트워크 통신 문제가 생김

* 운영 자동화가 매우 중요해짐

* 장애 추적이 어려워질 수 있음

* 데이터 일관성 관리가 어려워질 수 있음

---

## 4.3 한눈에 비교

| 항목 | 모놀리식 | MSA |
| --- | --- | --- |
| 구조 | 하나의 큰 애플리케이션 | 여러 개의 작은 서비스 |
| 배포 | 전체 배포 | 서비스별 배포 |
| 확장 | 전체 확장 | 필요한 서비스만 확장 |
| 개발 | 초기에 쉬움 | 설계와 운영이 더 복잡함 |
| 장애 영향 | 전체 영향 가능성 큼 | 일부 서비스로 제한 가능 |
| 운영 난이도 | 상대적으로 단순함 | 더 복잡함 |
| 적합한 경우 | 소규모, 빠른 시작 | 규모 확장, 팀 분리, 빈번한 배포 |

---

# 5. MSA의 핵심 개념

MSA를 이해할 때 반드시 잡아야 하는 핵심 개념이 몇 가지 있다.

---

## 5.1 서비스는 작고 명확한 역할을 가져야 한다

MSA에서 서비스는 무조건 작다고 좋은 것이 아니다.

중요한 것은 **역할이 명확하게 분리되어 있는가**다.

예를 들어 주문 서비스는 주문 생성, 주문 조회, 주문 상태 변경 같은 주문 관련 기능을 담당한다.

결제 서비스는 결제 승인, 결제 취소, 결제 상태 조회를 담당한다.

즉, 서비스는 **하나의 비즈니스 책임**을 중심으로 나누는 것이 중요하다.

이걸 너무 잘게 나누면 오히려 더 복잡해진다.

반대로 너무 크게 만들면 모놀리식과 차이가 없어진다.

---

## 5.2 서비스는 독립적으로 배포 가능해야 한다

MSA의 중요한 목적 중 하나는 **독립 배포**다.

예를 들어 알림 서비스 코드만 수정했다면,

주문 서비스나 상품 서비스는 건드리지 않고 **알림 서비스만 다시 배포**할 수 있어야 한다.

이렇게 되면 변경 속도가 빨라지고, 배포 영향 범위도 줄어든다.

---

## 5.3 서비스는 서로 통신한다

서비스를 나누면 서로 데이터를 주고받아야 한다.

이때 서비스 간 통신이 필요하다.

대표 방식은 다음과 같다.

* HTTP/REST API

* gRPC

* 메시지 큐 기반 비동기 통신

예를 들어 주문 서비스가 주문을 생성한 뒤 결제 서비스에 결제를 요청할 수 있다.

또는 주문 생성 이벤트를 메시지 브로커에 보내고, 알림 서비스가 이를 받아 문자나 이메일을 발송할 수도 있다.

즉, MSA에서는 **프로세스 내부 함수 호출 대신 네트워크 통신**이 일어난다.

---

## 5.4 각 서비스는 자신의 데이터를 관리하는 것이 이상적이다

MSA에서는 가능하면 서비스마다 **자신의 데이터 저장소**를 갖도록 설계한다.

예를 들어

* 회원 서비스 → 회원 DB

* 주문 서비스 → 주문 DB

* 결제 서비스 → 결제 DB

왜냐하면 하나의 공용 DB를 모든 서비스가 직접 함께 사용하면,

결국 서비스는 나뉘었어도 데이터 관점에서는 다시 강하게 엮이기 때문이다.

즉, **서비스 분리의 핵심은 코드 분리만이 아니라 데이터 책임 분리까지 포함**한다.

---

## 5.5 장애는 항상 발생할 수 있다고 가정해야 한다

MSA에서는 서비스 간 호출이 네트워크를 타기 때문에 다음 문제가 발생할 수 있다.

* 응답 지연

* 타임아웃

* 일시적 장애

* 일부 서비스 다운

* 네트워크 단절

그래서 MSA에서는 항상

“상대 서비스가 응답하지 않을 수도 있음”을 전제로 설계해야 한다.

이 때문에 자주 나오는 개념이 있다.

* Timeout

* Retry

* Circuit Breaker

* Fallback

핵심은 **MSA는 네트워크 장애를 고려해야 하는 구조**라는 점이다.

---

# 6. MSA 요소

---

## 6.1 API Gateway

클라이언트가 여러 서비스에 직접 접근하지 않고,

중간에 **API Gateway**를 통해 요청하도록 하는 구조다.

예를 들어 사용자가 모바일 앱에서 요청을 보내면,

API Gateway가 요청을 받아 적절한 내부 서비스로 전달한다.

### 역할

* 단일 진입점 제공

* 인증/인가 처리

* 라우팅

* 로깅

* 공통 정책 적용

즉, 외부 요청의 **입구 역할**을 한다.

---

## 6.2 Service Discovery

서비스가 많아지면 서비스의 위치를 어떻게 찾을지가 문제다.

컨테이너 환경에서는 서비스 IP가 고정되지 않는 경우가 많다.

그래서 서비스 이름으로 다른 서비스를 찾을 수 있게 해주는 개념이 필요하다.

이것이 Service Discovery다.

예를 들어 주문 서비스가 결제 서비스를 호출할 때

고정 IP 대신 서비스 이름으로 찾아가는 구조를 생각하면 된다.

쿠버네티스에서는 Service 객체와 DNS가 이 역할을 많이 담당한다.

---

## 6.3 중앙 로그 수집

서비스가 여러 개면 로그도 여러 군데 흩어진다.

장애가 나면 어디를 봐야 할지 어렵다.

그래서 MSA에서는 로그를 한 곳으로 모으는 것이 중요하다.

예시:

* Elasticsearch / Kibana

* Cloud Logging

* Loki / Grafana

핵심은 **분산된 로그를 중앙에서 모아 봐야 한다**는 점이다.

---

## 6.4 모니터링

서비스가 많아질수록 상태를 지속적으로 관찰해야 한다.

예를 들어 다음을 봐야 한다.

* 응답 시간

* 오류율

* CPU / 메모리 사용량

* 요청 수

* 재시도 횟수

* 큐 적체 여부

대표 도구로는 Prometheus, Grafana 같은 것이 있다.

---

## 6.5 분산 추적

사용자 요청 하나가 여러 서비스를 거치면,

문제가 어디서 발생했는지 찾기 어렵다.

예를 들어

* API Gateway

* 회원 서비스

* 주문 서비스

* 결제 서비스

* 알림 서비스

이 순서로 요청이 흘러갔다면,

중간 어디에서 지연이 발생했는지 추적할 수 있어야 한다.

이때 사용하는 개념이 **분산 추적(Distributed Tracing)** 이다.

대표적으로 다음 도구가 있다.

* Jaeger

* Zipkin

* OpenTelemetry

**즉, 하나의 요청이 여러 서비스를 지날 때 흐름을 추적해야 한다**.

---

# 7. MSA의 장점

## 7.1 서비스별 독립 배포가 가능함

하나의 서비스만 수정해서 빠르게 배포할 수 있다.

전체 시스템 배포 부담이 줄어든다.

---

## 7.2 필요한 부분만 확장 가능함

주문 요청만 많아졌다면 주문 서비스만 여러 개로 늘릴 수 있다.

전체 시스템을 같이 키우지 않아도 된다.

---

## 7.3 팀 단위 분업에 유리함

회원팀, 주문팀, 결제팀처럼 역할을 나누기 좋다.

각 팀이 담당 서비스 중심으로 빠르게 개발할 수 있다.

---

## 7.4 장애 영향 범위를 줄일 수 있음

한 서비스에 문제가 생겨도 전체가 모두 멈추지 않도록 설계할 수 있다.

물론 설계를 잘못하면 연쇄 장애가 날 수도 있음.

하지만 구조적으로는 장애 격리에 유리하다.

---

## 7.5 기술 선택의 유연성이 생길 수 있음

서비스마다 서로 다른 언어나 DB를 선택할 수도 있다.

예를 들어 검색 서비스는 Elasticsearch, 결제 서비스는 관계형 DB를 사용할 수 있다.

다만 실제 운영에서는 기술 스택을 너무 다양하게 가져가면 오히려 관리가 어려워질 수 있다.

---

# 8. MSA의 단점

## 8.1 구조가 복잡해진다

서비스를 나누는 순간 고려할 것이 많아진다.

* 통신 방식

* 인증

* 장애 처리

* 데이터 관리

* 배포 방식

* 관측성 확보

즉, 애플리케이션 구조보다 운영 구조가 크게 복잡해진다.

---

## 8.2 네트워크 비용이 생긴다

모놀리식에서는 함수 호출로 끝날 일이 MSA에서는 HTTP 호출이나 메시지 전송이 된다.

* 지연 시간 증가

* 네트워크 실패 가능성

* 재시도 필요

* 타임아웃 처리 필요

---

## 8.3 데이터 일관성 관리가 어려워진다

모놀리식에서는 하나의 DB 트랜잭션으로 끝낼 수 있는 작업이 많다.

하지만 MSA에서는 서비스별 DB가 분리되면 하나의 작업이 여러 시스템에 걸칠 수 있다.

예를 들어

* 주문 생성

* 결제 승인

* 재고 차감

이 3개가 서로 다른 서비스라면, 하나가 성공하고 하나가 실패할 수도 있다.

즉, 분산 환경에서는 **데이터 정합성**을 맞추는 일이 더 어렵다.

---

## 8.4 운영 자동화 수준이 낮으면 오히려 더 힘들다

MSA는 보통 다음이 같이 필요하다.

* CI/CD

* 컨테이너

* 오케스트레이션

* 모니터링

* 로깅

* 장애 대응 체계

즉, 운영 자동화가 준비되지 않은 상태에서 무리하게 MSA를 도입하면

개발보다 운영이 더 힘들어질 수 있다.

---

# 9. MSA가 적합한 경우와 아닌 경우

## 9.1 적합한 경우

* 서비스 규모가 커지고 있음

* 팀이 여러 개로 나뉘어 협업하고 있음

* 기능별 배포 주기가 다름

* 특정 기능만 트래픽이 급증함

* 서비스 확장성과 독립성이 중요함

---

## 9.2 아직 적합하지 않을 수 있는 경우

* 서비스 규모가 작음

* 개발 인원이 많지 않음

* 배포 빈도가 높지 않음

* 운영 자동화가 거의 없음

* 빠르게 MVP(Model-View-Presenter)를 만드는 것이 더 중요함

즉, 작은 시스템에서 무조건 MSA로 시작하는 것이 항상 좋은 것은 아니다.

처음에는 모놀리식으로 시작하고, 필요 시 점진적으로 분리하는 전략도 많이 사용한다.

# 10. 정리

MSA는 하나의 큰 애플리케이션을 여러 개의 독립적인 서비스로 나누어 구성하는 아키텍처다.

핵심 목적은 다음과 같다.

* 기능별 분리

* 독립 배포

* 독립 확장

* 팀 단위 개발 효율 향상

하지만 그만큼 다음 부담도 생긴다.

* 운영 복잡성 증가

* 네트워크 장애 고려 필요

* 데이터 일관성 관리 어려움

* 모니터링과 로깅 체계 필요

따라서 MSA는 **규모와 조직, 운영 수준에 따라 적절히 선택해야 하는 구조**이다.
