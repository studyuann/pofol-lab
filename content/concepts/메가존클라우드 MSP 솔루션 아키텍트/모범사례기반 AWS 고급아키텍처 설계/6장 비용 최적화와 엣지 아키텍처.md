# 6장 비용 최적화와 엣지 아키텍처

---

# 6.1 비용 최적화와 엣지 설계를 함께 보는 이유

아키텍처 설계에서는 성능, 가용성, 보안만 강조되기 쉬움.

하지만 실제 운영에서는 아무리 구조가 좋아도 비용이 통제되지 않으면 지속 가능한 아키텍처라고 보기 어려움.

반대로 비용만 줄이려고 하다가 성능과 안정성이 무너지면 그것도 좋은 설계가 아님.

엣지 아키텍처도 비슷함.

CloudFront 같은 엣지 서비스를 쓰면 사용자 경험이 좋아질 수 있지만, 무조건 붙인다고 끝나는 것은 아님.

어떤 콘텐츠를 어디까지 캐시할지, 원본 부하를 어떻게 줄일지, 어떤 요청은 원본으로 보내야 할지, 어떤 보안 기능을 앞단에서 처리할지를 함께 봐야 함.

즉, 이 장의 핵심은 다음과 같음.

```
좋은 아키텍처는 성능만 좋은 것이 아니라
비용까지 통제 가능해야 하며,
사용자 접점 품질도 함께 고려해야 한다.
```

---

# 6.2 비용 최적화의 의미

비용 최적화는 단순히 예산을 줄이는 활동이 아님.

필요한 성능과 가용성을 유지하면서, 불필요한 낭비를 줄이고, 구조적으로 효율적인 선택을 하는 것이 핵심임.

즉, 비용 최적화는 다음 질문에 답하는 과정임.

* 이 리소스는 정말 항상 켜져 있어야 하는가

* 더 작은 단위로 확장 가능한가

* 관리형 서비스를 쓰는 편이 운영비까지 포함해 더 유리한가

* 저장소 계층을 분리할 수 있는가

* 캐시를 두면 원본 비용을 줄일 수 있는가

* 트래픽을 더 가까운 곳에서 처리하면 원본 부하를 줄일 수 있는가

즉, 비용 최적화는 “싸게 만들기”가 아니라

**구조적으로 낭비를 줄이는 설계 활동**임.

---

# 6.3 비용이 증가하는 대표 원인

AWS 비용은 단순히 리소스를 많이 써서만 증가하는 것이 아님.

설계가 비효율적일 때도 비용이 빠르게 증가할 수 있음.

대표적인 원인은 다음과 같음.

### 1. 과도한 리소스 프로비저닝

실제 필요보다 큰 인스턴스를 계속 유지하는 경우임.

### 2. 사용하지 않는 리소스 방치

중지하지 않은 개발 서버, 연결 해제된 볼륨, 미사용 스냅샷, 사용하지 않는 Elastic IP 등이 여기에 해당함.

### 3. 무분별한 데이터 저장

모든 데이터를 고성능, 고비용 스토리지에 장기간 보관하는 경우임.

### 4. 네트워크 경로 비효율

굳이 NAT를 거치지 않아도 되는 트래픽이 NAT를 통과하거나, 캐시 없이 원본까지 반복 호출되는 경우임.

### 5. 수동 고정 확장 구조

항상 최대 트래픽을 기준으로 서버 수를 고정 운영하는 경우임.

즉, 비용은 단순 사용량 문제가 아니라

**아키텍처 선택의 결과**이기도 함.

---

# 6.4 비용 최적화의 핵심 원칙

고급 설계 관점에서 비용 최적화는 몇 가지 원칙으로 정리할 수 있음.

### 1. 필요에 따라 확장하고 줄일 수 있어야 함

Auto Scaling, 서버리스, 컨테이너 기반 확장 구조가 여기에 해당함.

### 2. 계층별로 다른 비용 전략을 가져가야 함

컴퓨팅, 저장소, 데이터베이스, 네트워크는 비용 특성이 다름.

### 3. 사용 패턴을 반영해야 함

24시간 항상 켜져 있는 워크로드와 간헐적으로 사용하는 워크로드는 다른 방식으로 설계해야 함.

### 4. 운영 비용까지 함께 봐야 함

직접 관리하는 구조가 단순히 인스턴스 비용만 싸다고 해서 전체적으로 저렴한 것은 아닐 수 있음.

### 5. 사용자 경험과 비용의 균형을 맞춰야 함

비용만 줄이다가 성능 저하가 심하면 전체적으로 손해가 될 수 있음.

즉, 비용 최적화는 단순히 리소스를 줄이는 것이 아니라

**구조와 운영 방식 전체를 조정하는 일**임.

---

# 6.5 AWS 비용은 어떻게 구성되는가

비용을 최적화하려면 먼저 어떤 항목에서 비용이 발생하는지 이해해야 함.

대표적으로 다음 영역이 중요함.

* 컴퓨팅 비용

* 스토리지 비용

* 데이터 전송 비용

* 데이터베이스 비용

* 관리형 서비스 비용

* 로그 및 모니터링 비용

이때 중요한 점은 단순히 서비스 이름만 보는 것이 아니라

**워크로드 성격에 따라 어떤 축의 비용이 커지는지**를 보는 것임.

예를 들어

* 웹 애플리케이션은 컴퓨팅과 데이터 전송 비용이 중요할 수 있음

* 데이터 중심 구조는 스토리지와 데이터베이스 비용이 중요할 수 있음

* 글로벌 서비스는 CloudFront와 데이터 전송 최적화가 중요할 수 있음

즉, 비용 최적화는 서비스별이 아니라 **워크로드별**로 접근해야 함.

---

# 6.6 컴퓨팅 비용 최적화

컴퓨팅 계층은 대부분의 아키텍처에서 비용 비중이 큼.

따라서 컴퓨팅 비용을 구조적으로 최적화하는 것이 중요함.

대표 방법

### 1. 인스턴스 크기 적정화

실제 CPU, 메모리 사용량을 보고 과도한 크기를 줄임.

### 2. Auto Scaling 활용

필요할 때만 확장하고, 한가할 때는 줄임.

### 3. 관리형 실행 모델 고려

Lambda, Fargate 같은 구조가 특정 워크로드에서는 더 유리할 수 있음.

### 4. 사용 패턴에 맞는 요금 모델 선택

항상 실행되는 리소스와 간헐적 리소스를 구분해서 봐야 함.

즉, 컴퓨팅 비용은 서버 수만이 아니라

**확장 방식과 실행 모델 선택**에 크게 좌우됨.

---

# 6.7 스토리지 비용 최적화

스토리지는 쉽게 쌓이고 오래 남기 쉬워서, 시간이 갈수록 비용 누적 효과가 큼.

특히 로그, 백업, 정적 파일, 데이터 적재가 많은 구조에서는 스토리지 전략이 매우 중요함.

대표 방법

### 1. 저장소 유형 구분

EBS, S3, EFS, 아카이브 스토리지는 서로 비용 구조가 다름.

### 2. 수명주기 기반 계층화

자주 쓰는 데이터와 오래된 데이터를 같은 클래스에 둘 필요가 없음.

### 3. 불필요한 복제와 중복 저장 점검

필요하지 않은 스냅샷, 버전, 장기 보관 데이터를 정리해야 함.

### 4. 객체 저장소 적극 활용

정적 파일이나 공유 파일 성격이 강한 데이터는 로컬 디스크보다 객체 저장소가 적합할 수 있음.

즉, 스토리지 비용 최적화는

**무엇을 어디에 얼마나 오래 저장하는가**를 설계하는 문제임.

---

# 6.8 데이터 전송 비용 최적화

AWS 비용에서 자주 간과되지만, 실제로는 큰 비중을 차지할 수 있는 것이 데이터 전송 비용임.

특히 다음 상황에서 중요함.

* 인터넷으로 나가는 트래픽이 많을 때

* 여러 계층 간 데이터 이동이 많을 때

* 캐시 없이 원본까지 반복 호출될 때

* NAT Gateway를 통해 대량 트래픽이 나갈 때

데이터 전송 비용을 줄이기 위한 대표적인 방법

### 1. CloudFront 사용

정적 콘텐츠와 반복 요청을 엣지에서 처리해 원본과 인터넷 송신 부담을 줄일 수 있음.

### 2. VPC Endpoint 활용

S3 같은 AWS 서비스 접근 시 불필요한 NAT 경로를 줄일 수 있음.

### 3. 캐시 구조 도입

원본 호출 횟수를 줄이면 데이터 전송과 원본 부하를 함께 줄일 수 있음.

즉, 데이터 전송 비용은 성능 구조와 밀접하게 연결되어 있음.

---

# 6.9 비용 관리 도구가 필요한 이유

좋은 구조를 만들었더라도 비용을 보지 않으면 문제를 늦게 발견하게 됨.

비용은 실시간 리소스 상태처럼 눈에 바로 보이지 않기 때문에, 별도의 가시화 도구가 중요함.

비용 관리 도구가 필요한 이유

* 어떤 서비스가 비용을 많이 쓰는지 파악

* 급격한 비용 증가 탐지

* 환경별, 계정별 비용 구분

* 장기적인 비용 추세 분석

* 예산 초과 위험 관리

즉, 비용 관리 도구는 단순 회계 기능이 아니라

**아키텍처 피드백 도구**라고 볼 수 있음.

---

# 6.10 Cost Explorer의 의미

Cost Explorer는 비용을 시각적으로 분석하고 추세를 파악하는 대표적인 도구임.

다음 같은 질문에 답하는 데 유용함.

* 이번 달 비용이 왜 늘었는가

* 어떤 서비스가 가장 많은 비용을 차지하는가

* 특정 계정 또는 태그의 비용은 얼마인가

* 과거와 비교했을 때 증가 원인이 무엇인가

즉, Cost Explorer는 단순히 총액만 보는 것이 아니라

**비용의 구조를 분석하는 도구**임.

---

# 6.11 AWS Budgets의 의미

Budgets는 비용과 사용량에 대한 기준선을 두고, 일정 수준에 도달하면 알림을 받도록 하는 기능임.

이 기능이 중요한 이유는 다음과 같음.

* 비용 문제를 월말이 아니라 중간에 감지 가능

* 개발/실험 환경의 과도한 사용을 빨리 발견 가능

* 팀별 예산 통제 가능

* 운영 리소스 이상 징후를 조기에 파악 가능

즉, Budgets는 비용을 줄이는 도구라기보다

**비용 이상 징후를 빨리 발견하는 통제 장치**임.

---

# 6.12 태그와 비용 가시성의 관계

비용 최적화는 리소스를 보는 일인 동시에, 리소스를 분류하는 일이기도 함.

이때 중요한 것이 태그 전략임.

예를 들어 다음 기준으로 비용을 나눠 볼 수 있음.

* Environment = Prod / Dev / Test

* Project = 서비스명

* Owner = 담당 조직

* CostCenter = 비용 회계 구분

이런 태그가 없다면 비용을 서비스별, 팀별, 목적별로 분석하기 어려움.

즉, 비용 최적화는 아키텍처 설계뿐 아니라 **분류 체계 설계**와도 연결됨.

---

# 6.13 비용 최적화에서 관리형 서비스가 가지는 의미

직접 EC2를 운영하는 방식이 겉으로는 단순하고 저렴해 보일 수 있음.

하지만 다음을 함께 고려해야 함.

* 패치 운영

* 장애 대응

* 백업 구성

* 확장 자동화

* 보안 관리

* 인력 운영 비용

즉, 단순 리소스 비용만 보면 직접 운영이 싸 보일 수 있어도

전체 운영 비용까지 보면 관리형 서비스가 더 유리할 수 있음.

예를 들어

* Fargate

* Lambda

* RDS

* S3

* CloudFront

같은 서비스는 운영 부담을 줄이는 대신 사용량 기반 비용 구조를 가짐.

따라서 비용 최적화는 단순 인프라 비용이 아니라 **총 소유 비용(TCO)** 관점으로 봐야 함.

---

# 6.14 엣지 아키텍처의 의미

엣지 아키텍처는 사용자와 가까운 위치에서 성능, 가용성, 보안을 개선하는 구조를 의미함.

클라우드 서비스는 보통 리전 중심으로 배치되지만, 사용자는 다양한 지역에서 접속하므로 사용자 경험은 네트워크 거리와 응답 방식에 따라 크게 달라질 수 있음.

엣지 아키텍처가 필요한 이유는 다음과 같음.

* 전 세계 사용자에게 더 빠른 응답 제공

* 원본 서버 부하 감소

* 정적 콘텐츠 전송 최적화

* 엣지에서 보안 통제 가능

* 사용자 접점 품질 향상

즉, 엣지 아키텍처는 단순 성능 보강 기능이 아니라

**사용자 접점 최적화 계층**임.

---

# 6.15 CloudFront 개요

CloudFront는 AWS의 CDN(Content Delivery Network) 서비스임.

사용자와 가까운 엣지 로케이션에서 콘텐츠를 캐시하고 전달해 원본 서버까지의 거리를 줄이는 역할을 함.

즉, CloudFront의 핵심은 다음과 같음.

```
반복 요청되는 콘텐츠를 사용자 가까운 위치에서 전달해
지연시간을 줄이고 원본 부하를 낮춘다.
```

CloudFront는 특히 다음 구조에서 자주 사용됨.

* S3 기반 정적 콘텐츠 배포

* ALB 앞단 웹 콘텐츠 가속

* API 전송 최적화 일부

* 다운로드 파일 배포

* 이미지, CSS, JavaScript 전달

---

# 6.16 CDN이 왜 중요한가

CDN이 중요한 이유는 단순히 빠르기 때문만은 아님.

다음과 같은 구조적 이점이 있음.

### 1. 사용자 지연시간 감소

원본까지 직접 가지 않고 가까운 엣지에서 응답 가능함.

### 2. 원본 부하 감소

같은 파일을 반복 요청할 때 원본 서버까지 도달하지 않아도 됨.

### 3. 트래픽 분산

대규모 요청을 원본이 직접 모두 처리하지 않게 됨.

### 4. 보안 구조 강화

CloudFront 앞단에 WAF, Shield를 붙여 엣지에서 요청 통제가 가능함.

즉, CloudFront는 성능 가속기이면서 동시에

**비용 절감과 보안 강화에도 기여하는 구조 요소**임.

---

# 6.17 CloudFront의 기본 구조

CloudFront를 이해할 때 중요한 개념은 다음과 같음.

* Distribution

* Origin

* Edge Location

* Cache

* Behavior

---

## 6.17.1 Distribution

CloudFront 배포 단위 전체를 의미함.

어떤 원본을 사용할지, 어떤 경로를 어떻게 캐시할지, 어떤 정책을 적용할지 포함한 전체 구성임.

---

## 6.17.2 Origin

CloudFront가 콘텐츠를 가져오는 원본 위치임.

대표 예

* S3

* ALB

* EC2 웹 서버

* API Gateway

즉, CloudFront는 원본을 대체하는 것이 아니라

**원본 앞단에서 캐시와 전달 최적화를 수행하는 계층**임.

---

## 6.17.3 Edge Location

사용자와 가까운 위치에서 콘텐츠를 전달하는 글로벌 접점임.

반복되는 요청은 이 위치들에서 캐시를 활용해 더 빠르게 처리할 수 있음.

---

## 6.17.4 Behavior

경로별로 캐시 정책, 원본, 보안 정책, 요청 처리 정책을 다르게 적용하는 설정임.

예를 들어

* `/images/*` 는 강하게 캐시

* `/api/*` 는 캐시 없이 원본 전달

같이 설계할 수 있음.

즉, CloudFront는 모든 콘텐츠를 똑같이 처리하는 서비스가 아니라

**경로와 요청 유형에 따라 동작을 다르게 설계하는 서비스**임.

---

# 6.18 CloudFront와 비용 최적화의 관계

CloudFront는 비용이 추가되는 서비스처럼 보일 수 있음.

하지만 전체 구조로 보면 비용을 줄이는 방향으로 작동할 수도 있음.

대표 이유는 다음과 같음.

### 1. 원본 서버 요청 감소

같은 정적 파일을 원본이 반복 처리하지 않게 됨.

### 2. ALB/EC2 부하 감소

웹 서버 수를 무작정 늘리지 않아도 될 수 있음.

### 3. 데이터 전송 효율 개선

전송 구조를 더 최적화할 수 있음.

### 4. 보안 처리 앞단화

원본까지 도달하는 악성 요청 일부를 줄일 수 있음.

즉, CloudFront는 단순 추가 비용이 아니라

**원본 인프라 비용과 사용자 경험을 함께 조정하는 도구**임.

---

# 6.19 S3와 CloudFront 조합이 중요한 이유

정적 파일을 EC2 로컬 디스크에 두는 구조는 확장성과 운영성 측면에서 불리할 수 있음.

반면 S3와 CloudFront를 조합하면 다음 장점이 있음.

* 정적 파일을 EC2와 분리 가능

* 파일 저장과 웹 전달을 역할별로 분리 가능

* 전 세계 사용자에게 더 빠른 응답 가능

* 원본 서버 부하 감소

* 운영 단순화

즉, 이 조합은 단순 정적 호스팅을 넘어서

**멀티 티어 아키텍처에서 파일 계층을 분리하는 대표 패턴**임.

---

# 6.20 엣지 아키텍처와 보안의 관계

엣지 아키텍처는 성능만의 주제가 아님.

사용자 접점에서 요청을 처리한다는 의미는, 곧 보안 통제를 앞단에서 적용할 수 있다는 뜻이기도 함.

대표 조합

* CloudFront

* WAF

* Shield

이 구조를 사용하면

* 비정상 요청을 앞단에서 필터링 가능

* 원본 애플리케이션 노출 축소 가능

* 대량 공격 완충 가능

* HTTPS 종료 및 전달 구조 관리 가능

즉, 엣지 설계는 성능 최적화와 보안 최적화가 함께 가는 영역임.

---

# 6.21 비용과 성능 사이의 균형

비용 최적화와 엣지 아키텍처를 함께 설명할 때 중요한 점은

**무조건 싸거나 무조건 빠른 것이 정답이 아니라는 것**임.

예를 들어

* 모든 것을 캐시하면 동적 콘텐츠 품질 문제가 생길 수 있음

* 모든 요청을 원본으로 보내면 성능과 비용이 나빠질 수 있음

* 너무 작은 인스턴스만 쓰면 오히려 장애와 성능 저하가 생길 수 있음

* 관리형 서비스를 무조건 피하면 운영 부담이 커질 수 있음

즉, 좋은 설계는 항상 **균형점**을 찾는 과정임.

이 장에서는 그 균형점을 다음처럼 봐야 함.

* 성능 요구사항

* 사용자 위치

* 요청 패턴

* 운영 부담

* 비용 한계

---

# 6.22 비용 최적화 관점에서 자주 하는 실수

### 1. 작은 인스턴스가 항상 유리하다고 생각함

너무 작은 리소스는 성능 문제를 일으켜 오히려 더 많은 확장 비용을 만들 수 있음.

### 2. 캐시 없이 원본만 확장함

원본 서버를 늘리는 것만으로는 비효율적일 수 있음.

### 3. 저장소 계층화를 하지 않음

오래된 데이터를 계속 비싼 저장소에 두는 경우가 많음.

### 4. 개발/실험 환경을 상시 켜 둠

운영 외 환경의 낭비가 누적될 수 있음.

### 5. 태그 없이 비용을 보려 함

원인을 찾기 어려워짐.

즉, 비용 최적화는 도구 문제가 아니라

**설계와 운영 습관의 문제**이기도 함.

---

# 6.23 엣지 설계에서 자주 하는 실수

### 1. 캐시 정책 없이 CloudFront만 붙임

효과가 제한적일 수 있음.

### 2. 동적 요청과 정적 요청을 구분하지 않음

모든 요청에 같은 정책을 적용하면 비효율적임.

### 3. 원본 서버를 계속 직접 노출함

엣지 보호 구조의 이점을 살리지 못할 수 있음.

### 4. WAF와 CloudFront를 별개로 생각함

보안과 성능을 함께 설계해야 함.

즉, 엣지 아키텍처도 서비스 추가가 아니라

**경로별 정책 설계**가 핵심임.

---

# 6.24 비용 최적화와 멀티 계정 구조의 관계

멀티 계정 구조는 비용 가시성과도 매우 밀접하게 연결됨.

계정을 적절히 나누면 다음이 쉬워짐.

* 운영과 비운영 비용 구분

* 프로젝트별 비용 분리

* 조직별 책임 부여

* 공통 서비스 비용 식별

즉, 비용 최적화는 단일 계정 안에서만 보는 것이 아니라

**계정 구조와 태그 구조를 함께 설계해야 효과적**임.

---

# 6.25 비용 최적화와 컨테이너 / 서버리스의 관계

이전 장에서 다룬 컨테이너 플랫폼과도 연결됨.

예를 들어

* Fargate는 서버 운영 부담을 줄일 수 있음

* ECS 기반 App Tier는 수평 확장 구조와 잘 맞음

* Lambda는 간헐적 요청 워크로드에 유리할 수 있음

즉, 비용 최적화는 단순히 EC2 크기를 줄이는 것이 아니라

**실행 모델 자체를 바꾸는 선택**과도 연결됨.

---

# 6.26 설계 시 핵심 질문

이 장에서는 다음 질문이 중요함.

### 1. 어떤 비용이 가장 많이 발생할 것인가

컴퓨팅, 저장소, 전송, DB 중 무엇이 핵심 축인지 먼저 봐야 함.

### 2. 반복 요청을 원본까지 보낼 필요가 있는가

캐시 가능성을 검토해야 함.

### 3. 항상 켜 둘 필요가 있는 리소스와 아닌 리소스를 구분했는가

고정 비용과 탄력 비용을 나눠 봐야 함.

### 4. 사용자 위치에 따른 지연시간 차이를 고려했는가

글로벌 서비스에서는 엣지 구조가 중요함.

### 5. 비용 절감이 운영 복잡도를 과도하게 키우지는 않는가

단순 인프라 비용만으로 판단하면 안 됨.

즉, 좋은 설계는 비용을 줄이는 동시에

**운영 가능성과 사용자 경험을 유지하는 방향**이어야 함.

---

# 6.27 전체 아키텍처 관점에서의 의미

비용 최적화와 엣지 설계는 전체 멀티 티어 구조의 마지막 조정 단계가 아님.

오히려 처음부터 함께 고려해야 하는 요소임.

예를 들어

* Web Tier는 CloudFront로 원본 부하를 줄일 수 있음

* App Tier는 Fargate나 Auto Scaling으로 탄력 운영 가능함

* Data Tier는 캐시와 저장소 계층화로 비용을 낮출 수 있음

* 네트워크는 엔드포인트와 캐시로 전송 비용을 조정할 수 있음

즉, 비용과 엣지는 부가 기능이 아니라

**전체 아키텍처 품질을 완성하는 핵심 축**임.
