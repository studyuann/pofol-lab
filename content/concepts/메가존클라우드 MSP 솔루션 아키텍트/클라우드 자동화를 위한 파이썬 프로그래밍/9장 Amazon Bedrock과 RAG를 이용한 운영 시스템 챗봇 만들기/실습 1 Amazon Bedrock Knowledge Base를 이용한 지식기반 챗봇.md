# 실습 1. Amazon Bedrock Knowledge Base를 이용한 지식기반 챗봇

---

## 1. 실습 개요

이 실습에서는 Amazon Bedrock Knowledge Base를 사용하여 정적인 운영 문서를 기반으로 답변하는 지식기반 챗봇을 구현한다.

일반적인 생성형 AI 모델은 이미 학습된 범용 지식을 기반으로 답변한다. 하지만 회사 내부 운영 매뉴얼, 장애 대응 가이드, 패치 일정, 서버 점검 문서처럼 외부에 공개되지 않은 문서는 모델이 기본적으로 알 수 없다.

이런 문제를 해결하기 위해 RAG 방식을 사용한다.

RAG는 사용자의 질문이 들어왔을 때 먼저 관련 문서를 검색하고, 검색된 문서 내용을 기반으로 생성형 AI가 답변을 생성하는 구조이다. Amazon Bedrock Knowledge Bases는 사용자의 데이터 소스에서 관련 정보를 검색하고, 검색된 내용을 바탕으로 답변을 생성하며, 응답에 출처를 포함할 수 있다.

이번 실습에서는 다음 흐름을 구성한다.

```
운영 문서 준비
        ↓
S3 버킷에 문서 업로드
        ↓
Amazon Bedrock Knowledge Base 생성
        ↓
Embedding 모델 선택
        ↓
Vector Store 생성
        ↓
S3 문서 동기화
        ↓
Bedrock 콘솔에서 질문 테스트
        ↓
출처 기반 답변 확인
```

---

## 2. 실습 목표

* RAG의 기본 동작 흐름을 설명할 수 있다.

* Amazon Bedrock Knowledge Base의 역할을 설명할 수 있다.

* S3를 Knowledge Base의 데이터 소스로 연결할 수 있다.

* 문서 데이터를 벡터화하여 검색 가능한 형태로 저장할 수 있다.

* Embedding 모델의 역할을 설명할 수 있다.

* OpenSearch Serverless 기반 Vector Store를 생성할 수 있다.

* Bedrock 콘솔에서 Knowledge Base를 테스트할 수 있다.

* 답변에 사용된 원본 문서 출처를 확인할 수 있다.

---

## 3. 실습 아키텍처

이번 실습의 전체 구조는 다음과 같다.

```
[사용자 질문]
     ↓
Amazon Bedrock Knowledge Base
     ↓
관련 문서 검색
     ↓
OpenSearch Serverless Vector Store
     ↑
문서 벡터 저장
     ↑
Embedding Model
     ↑
S3 운영 문서
```

각 구성요소의 역할은 다음과 같다.

| 구성요소 | 역할 |
| --- | --- |
| S3 | 운영 매뉴얼, 장애 대응 문서, 패치 일정 파일 저장 |
| Amazon Bedrock Knowledge Base | 문서 검색과 답변 생성을 연결하는 RAG 관리 서비스 |
| Embedding Model | 문서와 질문을 벡터로 변환 |
| Vector Store | 벡터화된 문서 조각을 저장하고 유사도 검색 수행 |
| OpenSearch Serverless | 실습에서 사용할 벡터 저장소 |
| Foundation Model | 검색된 문서 내용을 바탕으로 자연어 답변 생성 |

---

## 4. RAG 동작 원리 이해

## 4.1 일반 생성형 AI 답변 방식

일반적인 생성형 AI 사용 흐름은 다음과 같다.

```
사용자 질문
    ↓
Foundation Model
    ↓
답변 생성
```

예를 들어 사용자가 다음과 같이 질문한다고 하자.

```
서버 패치 작업은 매월 언제 수행하나요?
```

일반 모델은 회사 내부 패치 일정을 알지 못한다.

따라서 추측하거나 일반적인 답변을 생성할 수 있다.

---

## 4.2 RAG 기반 답변 방식

RAG 기반 흐름은 다르다.

```
사용자 질문
    ↓
질문과 관련된 문서 검색
    ↓
검색된 문서 내용을 프롬프트에 포함
    ↓
Foundation Model 답변 생성
    ↓
출처 포함 답변 반환
```

예를 들어 S3에 다음 문서가 있다고 하자.

```
정기 서버 패치 작업은 매월 둘째 주 화요일 22:00에 수행한다.
패치 작업 전에는 대상 서버의 스냅샷을 생성해야 한다.
```

사용자가 질문한다.

```
서버 패치 작업 전에 무엇을 해야 하나요?
```

Knowledge Base는 관련 문서 조각을 검색하고, 모델은 검색된 내용을 기반으로 다음처럼 답변할 수 있다.

```
서버 패치 작업 전에는 대상 서버의 스냅샷을 생성해야 한다.
```

이처럼 RAG는 모델이 모르는 내부 문서를 검색해서 답변에 활용하는 방식이다.

# 5. 사전 준비

이번 실습에는 다음 항목이 필요하다.

실습 계정에는 다음 서비스에 대한 사용 권한이 필요하다.

* Amazon S3

* Amazon Bedrock

* IAM

* OpenSearch Serverless

---

## 5.2 리전 선택

Amazon Bedrock은 리전별로 지원 모델과 기능이 다를 수 있다.

실습 전에는 사용하는 리전에서 Knowledge Base, Embedding 모델, 답변 생성 모델이 사용 가능한지 확인해야 한다.

실습에서는 예시로 다음 리전을 사용한다.

```
ap-northeast-2
```

다만 실습 계정에서 해당 리전에 필요한 모델이 보이지 않으면 다음 리전을 사용할 수 있다.

```
us-east-1
us-west-2
ap-northeast-1
```

Amazon Bedrock Knowledge Bases는 문서를 벡터 임베딩으로 변환하기 위해 Embedding 모델을 사용한다. AWS 공식 문서에서도 Knowledge Base가 Embedding 모델을 사용해 데이터를 벡터 임베딩으로 변환하고 벡터 데이터베이스에 저장한다고 설명한다.

---

## 5.3 모델 접근 권한 확인

Amazon Bedrock에서 모델을 사용하려면 모델 접근 권한이 필요하다.

AWS 콘솔에서 다음 메뉴로 이동한다.

```
Amazon Bedrock
→ Model access
```

실습에 사용할 모델 접근 권한을 활성화한다.

예시 모델은 다음과 같다.

| 용도 | 모델 예시 |
| --- | --- |
| Embedding 모델 | Amazon Titan Text Embeddings V2 |
| 답변 생성 모델 | Anthropic Claude, Amazon Nova, Meta Llama 등 계정에서 사용 가능한 모델 |

Titan Text Embeddings V2는 검색 작업에 적합한 Amazon의 2세대 텍스트 임베딩 모델이며, 출력 차원을 설정할 수 있다.

# 서버 운영 매뉴얼

## EC2 인스턴스 점검 기준

운영 중인 EC2 인스턴스는 매일 오전 9시에 상태를 점검한다.

점검 항목은 다음과 같다.

- 인스턴스 상태가 running인지 확인한다.
- CPU 사용률이 80% 이상인지 확인한다.
- 메모리 사용률이 85% 이상인지 확인한다.
- 디스크 사용률이 90% 이상인지 확인한다.
- 최근 24시간 동안 재부팅 이력이 있는지 확인한다.

## CPU 사용률 대응 기준

CPU 사용률이 80% 이상이고 10분 이상 지속되면 담당자에게 알림을 전송한다.

CPU 사용률이 90% 이상이고 5분 이상 지속되면 즉시 원인 분석을 수행한다.

원인 분석 시 다음 항목을 확인한다.

- 비정상 프로세스 존재 여부
- 최근 배포 여부
- 트래픽 급증 여부
- Auto Scaling 정책 동작 여부

## 디스크 사용률 대응 기준

디스크 사용률이 90% 이상이면 불필요한 로그 파일을 정리한다.

디스크 사용률이 95% 이상이면 긴급 조치 대상으로 분류한다.

긴급 조치 시 다음 순서로 작업한다.

1. 로그 디렉터리 사용량을 확인한다.
2. 오래된 로그 파일을 압축하거나 삭제한다.
3. 필요 시 EBS 볼륨 확장을 검토한다.
4. 조치 내용을 운영 기록에 남긴다.
```

# 서버 패치 일정

## 정기 패치 일정

정기 서버 패치 작업은 매월 둘째 주 화요일 22:00에 수행한다.

패치 작업 시간은 기본적으로 22:00부터 23:30까지이다.

서비스 영향이 예상되는 경우 최소 3일 전에 공지한다.

패치 작업 전에는 다음 항목을 확인한다.

1. 대상 서버 목록을 확인한다.
2. 각 서버의 현재 상태가 running인지 확인한다.
3. 패치 전 EBS 스냅샷을 생성한다.
4. 최근 배포 작업이 있었는지 확인한다.
5. 서비스 담당자에게 작업 시작을 알린다.

## 패치 후 확인 사항

패치 작업 후에는 다음 항목을 확인한다.

1. 서버가 정상적으로 부팅되었는지 확인한다.
2. 주요 서비스 프로세스가 실행 중인지 확인한다.
3. 헬스체크 URL이 정상 응답하는지 확인한다.
4. 최근 10분간 5xx 오류가 증가했는지 확인한다.
5. 패치 결과를 운영 기록에 남긴다.

## 긴급 패치 기준

보안 취약점이 공개되었고 위험도가 높음 이상이면 긴급 패치를 검토한다.

긴급 패치는 보안 담당자, 서비스 담당자, 인프라 담당자의 승인 후 진행한다.

## 6.4 장애 대응 가이드 문서 작성

파일명: `incident_response_guide.md`

```
# 장애 대응 가이드

## 장애 등급

장애 등급은 서비스 영향도에 따라 구분한다.

### SEV-1

전체 서비스가 중단되었거나 핵심 기능이 동작하지 않는 상태이다.

SEV-1 발생 시 즉시 장애 대응 채널을 생성하고, 인프라 담당자와 서비스 담당자를 호출한다.

### SEV-2

일부 기능에 장애가 있거나 특정 사용자 그룹에 영향이 있는 상태이다.

SEV-2 발생 시 담당 팀에 알림을 전송하고 원인 분석을 시작한다.

### SEV-3

서비스 영향은 제한적이지만 반복적인 오류나 성능 저하가 확인되는 상태이다.

SEV-3 발생 시 운영 기록에 남기고 정기 점검 항목에 포함한다.

## 500 오류 증가 시 대응 절차

최근 10분간 500 오류가 평소보다 2배 이상 증가하면 장애 의심 상태로 분류한다.

대응 절차는 다음과 같다.

1. 최근 배포 이력을 확인한다.
2. 애플리케이션 로그에서 ERROR 로그를 확인한다.
3. 데이터베이스 연결 오류가 있는지 확인한다.
4. 외부 API 호출 실패 여부를 확인한다.
5. 필요 시 직전 버전으로 롤백한다.

## 데이터베이스 연결 장애 대응

데이터베이스 연결 실패 로그가 반복되면 다음을 확인한다.

1. 데이터베이스 인스턴스 상태를 확인한다.
2. 보안 그룹 인바운드 규칙을 확인한다.
3. 애플리케이션의 연결 문자열을 확인한다.
4. 커넥션 풀 고갈 여부를 확인한다.
5. 최근 네트워크 변경 사항을 확인한다.
```

# 7. S3 버킷 생성 및 문서 업로드

## 7.1 S3 버킷 생성

AWS 콘솔에서 다음 메뉴로 이동한다.

```
Amazon S3
→ Buckets
→ Create bucket
```

버킷 이름은 전역에서 유일해야 한다.

예시는 다음과 같다.

```
bedrock-rag-lab-계정ID-날짜
```

예를 들어 다음처럼 작성할 수 있다.

```
bedrock-rag-lab-123456789012-20260503
```

설정값은 다음과 같이 구성한다.

| 항목 | 설정 |
| --- | --- |
| AWS Region | Bedrock 실습 리전과 동일하게 선택 |
| Bucket type | General purpose |
| Object Ownership | ACLs disabled |
| Block Public Access | 전체 차단 유지 |
| Bucket Versioning | 비활성화 또는 활성화 선택 가능 |
| Default encryption | SSE-S3 기본값 사용 가능 |

중요한 점은 S3 버킷을 공개로 만들 필요가 없다는 것이다.

Bedrock 서비스 역할이 S3에 접근할 수 있도록 권한을 부여하면 된다.

---

## 7.2 폴더 생성

S3 버킷 안에 다음 폴더를 생성한다.

```
manual/
```

S3에서 폴더는 실제 디렉터리라기보다는 객체 키의 접두사(prefix)에 가깝다.

예를 들어 다음 객체는 `manual/` 아래에 있는 것처럼 보인다.

```
manual/server_operation_guide.md
manual/patch_schedule.md
manual/incident_response_guide.md
```

## 7.3 문서 업로드

다음 파일 3개를 S3에 업로드한다.

```
server_operation_guide.md
patch_schedule.md
incident_response_guide.md
```

업로드 후 S3 경로는 다음과 비슷해야 한다.

```
s3://bedrock-rag-lab-123456789012-20260503/manual/server_operation_guide.md
s3://bedrock-rag-lab-123456789012-20260503/manual/patch_schedule.md
s3://bedrock-rag-lab-123456789012-20260503/manual/incident_response_guide.md
```

## 7.4 CLI로 업로드하는 방법

콘솔 대신 AWS CLI를 사용하는 경우 다음 명령어를 사용할 수 있다.

```

```

# 9. IAM Role 설정

## 9.1 서비스 역할의 의미

Amazon Bedrock Knowledge Base가 S3 문서를 읽고, Embedding 모델을 호출하고, Vector Store에 데이터를 저장하려면 권한이 필요하다.

이 권한은 일반적으로 IAM Role을 통해 부여한다.

즉, 사용자가 직접 S3 파일을 읽는 것이 아니라 Bedrock 서비스가 사용자를 대신해 다음 작업을 수행한다.

```
Bedrock 서비스
    ↓
S3 문서 읽기
    ↓
Embedding 모델 호출
    ↓
Vector Store에 벡터 저장
```

---

## 9.2 자동 생성 역할 사용

실습에서는 콘솔에서 제공하는 자동 생성 역할을 사용한다.

다음 옵션을 선택한다.

```
Create and use a new service role
```

역할 이름은 자동으로 생성되거나 직접 입력할 수 있다.

예시:

```
AmazonBedrockExecutionRoleForKnowledgeBase_ops_lab
```

실습에서는 자동 생성 방식이 가장 간단하다.

다만 운영 환경에서는 최소 권한 원칙에 따라 다음 권한을 명확히 제한해야 한다.

* 특정 S3 버킷만 읽기 허용

* 특정 Prefix만 읽기 허용

* 필요한 Bedrock 모델만 호출 허용

* 특정 Vector Store만 접근 허용

---

## 9.3 권한 구조 이해

Bedrock Knowledge Base 서비스 역할에는 일반적으로 다음 권한이 필요하다.

| 권한 대상 | 필요한 이유 |
| --- | --- |
| S3 | 문서 파일 읽기 |
| Bedrock model | 문서를 임베딩으로 변환 |
| OpenSearch Serverless | 벡터 데이터 저장 및 검색 |
| CloudWatch Logs | 일부 로그 기록에 사용 가능 |
| KMS | 암호화 키 사용 시 필요 |

AWS 공식 문서도 Knowledge Base용 서비스 역할 생성과 데이터 소스, 벡터 스토어 접근 권한 구성을 별도로 안내한다.

# 11. 문서 분할 방식 설정

## 11.1 Chunking이란

RAG에서 문서를 그대로 통째로 검색하는 것은 효율적이지 않다.

예를 들어 20페이지짜리 운영 매뉴얼 전체를 하나의 단위로 검색하면, 사용자의 질문과 직접 관련 없는 내용까지 함께 들어갈 수 있다.

그래서 문서를 작은 조각으로 나눈다.

이 조각을 Chunk라고 한다.

```
긴 문서
  ↓
문서 조각 1
문서 조각 2
문서 조각 3
문서 조각 4
```

사용자가 질문하면 Knowledge Base는 전체 문서를 검색하는 것이 아니라 관련성이 높은 Chunk를 검색한다.

---

## 11.2 기본 Chunking 전략 사용

실습에서는 기본 Chunking 전략을 사용한다.

예시 설정:

```
Chunking strategy: Default
```

또는 콘솔에서 다음과 비슷한 옵션이 보이면 기본값을 유지한다.

```
Default chunking
Fixed-size chunking
Hierarchical chunking
Semantic chunking
```

초급 실습에서는 기본값으로 충분하다.

다만 문서가 길고 구조가 복잡한 경우에는 Chunk 크기와 Overlap을 조정해야 한다.

## 11.3 Chunk 크기 이해

Chunk 크기가 너무 작으면 문맥이 부족해질 수 있다.

예를 들어 다음 문장이 서로 다른 Chunk로 나뉘면 답변 품질이 떨어질 수 있다.

```
패치 작업 전에는 다음 항목을 확인한다.
1. 대상 서버 목록을 확인한다.
2. EBS 스냅샷을 생성한다.
```

반대로 Chunk가 너무 크면 관련 없는 내용이 함께 검색될 수 있다.

초기 실습에서는 기본값을 사용하고, 추후 고급 실습에서 Chunk 전략을 비교하는 것이 좋다.

---

# 12. Embedding 모델 선택

## 12.1 Embedding 모델의 역할

Embedding 모델은 텍스트를 숫자 벡터로 변환한다.

예를 들어 다음 문장을 생각해보자.

```
패치 전 EBS 스냅샷을 생성한다.
```

Embedding 모델은 이 문장을 사람이 읽는 문장이 아니라 벡터 형태로 변환한다.

```
[0.012, -0.231, 0.884, ...]
```

사용자 질문도 벡터로 변환된다.

```
패치 전에 백업을 해야 하나요?
```

이 질문도 벡터로 변환된다.

그 다음 벡터끼리 유사도를 비교한다.

의미가 비슷한 문장일수록 벡터 공간에서 가까운 위치에 배치된다.

---

## 12.2 Titan Text Embeddings V2 선택

Embedding 모델로 다음 모델을 선택한다.

```
Amazon Titan Text Embeddings V2
```

또는 콘솔에서 다음과 비슷한 모델 ID가 보일 수 있다.

```
amazon.titan-embed-text-v2:0
```

Titan Text Embeddings V2는 RAG 검색 작업에 사용할 수 있는 Amazon의 텍스트 임베딩 모델이며, 설정 가능한 출력 차원을 제공한다.

---

## 12.3 Embedding 모델과 답변 생성 모델의 차이

학생들이 자주 헷갈리는 부분이다.

| 구분 | 역할 |
| --- | --- |
| Embedding 모델 | 문서와 질문을 벡터로 변환 |
| 답변 생성 모델 | 검색된 문서를 읽고 자연어 답변 생성 |

Embedding 모델은 질문에 직접 답변하는 모델이 아니다.

예를 들어 사용자가 다음 질문을 한다.

```
패치 전에 무엇을 해야 하나요?
```

Embedding 모델은 이 질문에 답변하지 않는다.

이 질문을 벡터로 바꾸어 관련 문서를 찾을 수 있게 한다.

답변은 Claude, Nova, Llama 같은 Foundation Model이 생성한다.

---

# 13. Vector Store 생성

## 13.1 Vector Store란

Vector Store는 임베딩된 문서 조각을 저장하는 공간이다.

일반 데이터베이스가 다음과 같은 데이터를 저장한다면,

```
id, name, email, created_at
```

Vector Store는 다음과 같은 데이터를 저장한다.

```
문서 조각
문서 조각의 벡터
문서 출처
문서 메타데이터
```

사용자 질문이 들어오면 질문 벡터와 문서 벡터를 비교해서 의미적으로 가까운 문서 조각을 찾는다.

---

## 13.2 Quick create 사용

실습에서는 다음 옵션을 선택한다.

```
Quick create a new vector store
```

Vector Store 유형은 다음을 사용한다.

```
Amazon OpenSearch Serverless
```

Quick create를 사용하면 Bedrock이 Knowledge Base에서 사용할 OpenSearch Serverless 컬렉션과 인덱스 구성을 자동으로 생성한다.

실습에서는 수동으로 OpenSearch Serverless 컬렉션, 보안 정책, 인덱스 매핑을 구성하지 않아도 된다.

---

## 13.3 수동 생성과 Quick create 차이

| 방식 | 특징 |
| --- | --- |
| Quick create | 실습에 적합, 설정이 간단함 |
| Existing vector store | 기존 OpenSearch, Pinecone, Redis 등 사용 시 적합 |
| 수동 구성 | 운영 환경에서 세밀한 제어 가능 |

처음 실습에서는 Quick create를 사용한다.

운영 환경에서는 네트워크, 보안 정책, 암호화, 비용, 인덱스 구조를 고려해야 한다.

# 15. 데이터 동기화

## 15.1 Sync의 의미

Knowledge Base를 생성했다고 해서 S3 문서가 자동으로 바로 검색되는 것은 아니다.

S3에 있는 문서를 Knowledge Base로 가져오고, 문서 내용을 Chunk로 나누고, Embedding 모델로 벡터화하고, Vector Store에 저장해야 한다.

이 과정을 Sync라고 한다.

```
S3 문서
  ↓
문서 읽기
  ↓
Chunk 분할
  ↓
Embedding 생성
  ↓
Vector Store 저장
```

---

## 15.2 Sync 실행

Knowledge Base 상세 화면에서 Data source를 선택한다.

```
Data sources
→ s3-ops-manual-docs
→ Sync
```

Sync 버튼을 클릭한다.

동기화가 완료되면 상태가 다음과 비슷하게 표시된다.

```
Completed
```

---

## 15.3 Sync 실패 시 확인 항목

Sync가 실패하면 다음을 확인한다.

| 문제 | 확인할 내용 |
| --- | --- |
| S3 접근 실패 | Bedrock 서비스 역할에 S3 읽기 권한이 있는지 확인 |
| 모델 접근 실패 | Embedding 모델 접근 권한이 활성화되었는지 확인 |
| Vector Store 생성 실패 | OpenSearch Serverless 권한 확인 |
| 문서 형식 문제 | 지원되는 파일 형식인지 확인 |
| 리전 문제 | S3, Bedrock, Vector Store 리전 확인 |

# 16. Knowledge Base 테스트

## 16.1 테스트 화면 이동

Knowledge Base 상세 화면에서 테스트 메뉴를 연다.

```

---

## 16.2 답변 생성 기능 활성화

테스트 화면에서 다음 옵션을 활성화한다.

```
Generate responses
```

이 옵션을 켜면 Knowledge Base가 관련 문서만 검색하는 것이 아니라, 검색된 문서를 기반으로 자연어 답변까지 생성한다. AWS 문서에서도 Generate responses를 켜면 Bedrock이 데이터 소스를 기반으로 응답을 생성하고 footnote 형태로 출처를 표시한다고 안내한다.

---

## 16.3 답변 생성 모델 선택

답변 생성에 사용할 모델을 선택한다.

예시:

```
Anthropic Claude
Amazon Nova
Meta Llama
```

계정과 리전에 따라 보이는 모델이 다를 수 있다.

중요한 점은 Embedding 모델과 답변 생성 모델이 다르다는 것이다.

```
Embedding 모델:
문서와 질문을 벡터로 변환

답변 생성 모델:
검색된 문서 내용을 읽고 답변 생성
```

# 17. 테스트 질문 작성

## 17.1 단순 정보 확인 질문

다음 질문을 입력한다.

```
정기 서버 패치 작업은 언제 수행되나요?
```

기대 답변 예시는 다음과 같다.

```
정기 서버 패치 작업은 매월 둘째 주 화요일 22:00에 수행됩니다.
패치 작업 시간은 기본적으로 22:00부터 23:30까지입니다.
```

확인할 내용은 다음과 같다.

* `patch_schedule.md` 문서 내용이 반영되었는가

* 답변에 출처가 표시되는가

* 모델이 임의로 다른 일정을 만들어내지 않았는가

---

## 17.2 절차형 질문

다음 질문을 입력한다.

```
패치 작업 전에 무엇을 확인해야 하나요?
```

기대 답변 예시는 다음과 같다.

```
패치 작업 전에는 대상 서버 목록을 확인하고, 각 서버의 상태가 running인지 확인해야 합니다.
또한 패치 전 EBS 스냅샷을 생성하고, 최근 배포 작업 여부를 확인한 뒤 서비스 담당자에게 작업 시작을 알려야 합니다.
```

이 질문은 단순 키워드 검색보다 RAG의 효과를 보기 좋다.

질문에는 “스냅샷”이라는 단어가 없더라도, 문서의 의미를 기반으로 관련 내용을 찾을 수 있기 때문이다.

---

## 17.3 장애 대응 질문

다음 질문을 입력한다.

```
최근 10분간 500 오류가 증가하면 어떤 순서로 대응해야 하나요?
```

기대 답변 예시는 다음과 같다.

```
최근 10분간 500 오류가 평소보다 2배 이상 증가하면 장애 의심 상태로 분류합니다.
대응 절차는 최근 배포 이력 확인, 애플리케이션 ERROR 로그 확인, 데이터베이스 연결 오류 확인, 외부 API 호출 실패 여부 확인, 필요 시 직전 버전으로 롤백 순서입니다.
```

확인할 내용은 다음과 같다.

* `incident_response_guide.md`의 내용이 사용되었는가

# 18. 검색 결과와 생성 답변 구분하기

Knowledge Base 테스트에서 중요한 것은 두 가지를 구분하는 것이다.

```
검색된 문서 조각
생성된 답변
```

RAG는 단순히 모델이 답변하는 구조가 아니다.

먼저 관련 문서를 검색한다.

```
Retrieve
```

그 다음 검색된 문서를 기반으로 답변을 생성한다.

```
RetrieveAndGenerate
```

AWS 공식 API 문서에서도 `RetrieveAndGenerate`는 Knowledge Base를 질의하고, 검색된 결과를 기반으로 Foundation Model 또는 inference profile을 사용해 응답을 생성한다고 설명한다.

# 25. 자주 발생하는 오류와 해결 방법

## 25.1 Knowledge Base 생성 시 모델이 보이지 않는 경우

원인은 다음 중 하나일 수 있다.

* 해당 리전에서 모델을 지원하지 않음

* Model access가 활성화되지 않음

* 계정 권한이 부족함

해결 방법은 다음과 같다.

```
1. Amazon Bedrock → Model access 메뉴로 이동한다.
2. 사용할 모델 접근 권한을 활성화한다.
3. 다른 리전에서 동일한 실습을 시도한다.
4. IAM 권한을 확인한다.
```

---

## 25.2 Sync 실패

원인은 다음 중 하나일 수 있다.

* S3 경로가 잘못됨

* Bedrock 서비스 역할에 S3 읽기 권한이 없음

* 문서 파일 형식이 지원되지 않음

* OpenSearch Serverless 생성 또는 접근 권한 문제

확인 순서는 다음과 같다.

```
1. S3 URI가 정확한지 확인한다.
2. S3 버킷과 Bedrock 리전이 실습 의도와 맞는지 확인한다.
3. IAM Role에 S3 읽기 권한이 있는지 확인한다.
4. Model access가 활성화되어 있는지 확인한다.
5. OpenSearch Serverless 리소스가 생성되었는지 확인한다.
```

---

## 25.3 답변이 문서와 다르게 나오는 경우

가능한 원인은 다음과 같다.

* 문서가 Sync되지 않았음

* 질문과 관련된 Chunk가 제대로 검색되지 않았음

* 문서 내용이 모호함

* 답변 생성 모델이 추측함

* 출처 문서가 잘못 검색됨

해결 방법은 다음과 같다.

```
1. Data source Sync를 다시 실행한다.
2. 질문을 문서에 있는 표현과 비슷하게 바꿔본다.
3. 문서 제목과 소제목을 명확하게 작성한다.
4. 한 문서에 너무 많은 주제를 섞지 않는다.
5. "문서에 없는 내용은 답하지 말라"는 지침을 추가한다.
```

---

## 25.4 출처가 표시되지 않는 경우

확인할 내용은 다음과 같다.

```
1. Knowledge Base 테스트에서 Generate responses가 활성화되었는지 확인한다.
2. 질문과 관련된 문서가 실제로 검색되었는지 확인한다.
3. Sync가 완료되었는지 확인한다.
4. 문서 내용이 너무 짧거나 질문과 관련성이 낮지 않은지 확인한다.
```

# 26. 정리

이번 실습에서는 Amazon Bedrock Knowledge Base를 사용해 RAG 기반 지식 서비스를 구성했다.

핵심 흐름은 다음과 같다.

```
문서 작성
→ S3 업로드
→ Knowledge Base 생성
→ Embedding 모델 선택
→ Vector Store 생성
→ 데이터 동기화
→ 질문 테스트
→ 출처 확인
```

중요한 개념은 다음과 같다.

* RAG는 모델이 모르는 내부 문서를 검색해서 답변에 활용하는 구조이다.

* S3는 원본 문서 저장소 역할을 한다.

* Embedding 모델은 문서와 질문을 벡터로 변환한다.

* Vector Store는 벡터화된 문서 조각을 저장한다.

* Knowledge Base는 검색과 답변 생성을 연결한다.

* Sync를 실행해야 S3 문서가 검색 대상에 반영된다.

* 답변의 정확성은 반드시 출처 문서와 함께 검증해야 한다.

* 문서에 없는 내용은 답하지 않도록 테스트해야 한다.
