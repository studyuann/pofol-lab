13장 AWS 백업 및 복구 아키텍처

AWS Backup, Snapshot, 복구 전략

13.1 백업과 복구의 필요성

클라우드에서 인프라를 잘 설계했다고 해서 데이터 손실 위험이 사라지는 것은 아님.

오히려 시스템이 커질수록 데이터 보호와 복구 전략의 중요성은 더 커짐.

데이터 손실이나 복구가 필요한 대표 상황

  • 사용자의 실수로 데이터 삭제
  • 애플리케이션 오류로 잘못된 데이터 반영
  • 운영자의 설정 실수
  • 랜섬웨어 또는 악성 행위
  • 특정 리전 또는 계정 수준의 장애
  • 시스템 마이그레이션 실패
  • 장기간 보관 데이터 복구 필요

즉, 백업은 단순히 장애 대비용이 아니라

실수, 보안 사고, 운영 오류, 재해 상황을 포함한 데이터 보호 전략 전체의 일부임.

13.2 가용성과 백업의 차이

학생들이 자주 혼동하는 부분이 고가용성과 백업을 같은 것으로 보는 점임.

하지만 둘은 목적이 다름.

항목고가용성백업
목적서비스 중단 최소화데이터 복구 가능성 확보
대표 수단Multi-AZ, ELB, Auto ScalingSnapshot, Backup Vault, 보존 정책
대응 대상인프라/서비스 장애데이터 손실, 삭제, 손상
시간 관점실시간/즉시과거 시점 복구

예를 들어 RDS Multi-AZ는 장애 시 빠르게 서비스 지속성을 높여주지만,

어제 잘못 삭제한 데이터를 되돌리는 기능은 아님.

즉,

고가용성은 서비스를 계속 살아 있게 한다.
백업은 과거 데이터를 다시 되살릴 수 있게 한다.

이렇게 구분해서 이해해야 함.

13.3 백업 전략이 중요한 이유

백업은 단순히 많이 만들면 되는 것이 아님.

무엇을 얼마나 자주, 얼마나 오래, 어디에, 어떤 방식으로 저장할지 설계해야 함.

백업 전략에서 핵심 질문

  • 어떤 데이터를 보호해야 하는가
  • 얼마나 자주 백업해야 하는가
  • 얼마나 오래 보관해야 하는가
  • 어디에 저장해야 하는가
  • 복구는 얼마나 빨라야 하는가
  • 복구 시점은 어느 정도까지 허용되는가

즉, 백업은 스토리지 문제이기도 하지만, 실제로는 비즈니스 연속성과 복구 목표를 설계하는 문제임.

13.4 RPO와 RTO

백업 및 복구를 설명할 때 가장 중요한 개념이 RPO 와 RTO 임.

13.4.1 RPO (Recovery Point Objective)

RPO는 “얼마나 최근 시점의 데이터까지 복구되어야 하는가”를 의미함.

예를 들어 RPO가 1시간이면, 장애가 발생했을 때 최대 1시간 전 데이터까지만 잃는 것을 허용한다는 뜻임.

즉, RPO는 데이터 손실 허용 범위와 관련됨.

13.4.2 RTO (Recovery Time Objective)

RTO는 “장애 발생 후 얼마 안에 서비스를 복구해야 하는가”를 의미함.

예를 들어 RTO가 30분이면, 장애 후 30분 안에 복구가 완료되어야 함을 의미함.

즉, RTO는 복구 시간 허용 범위와 관련됨.

13.4.3 RPO와 RTO의 의미

이 두 값이 작을수록 더 강한 복구 체계가 필요함.

예

  • RPO 24시간 / RTO 8시간 → 비교적 느슨한 복구 전략
  • RPO 5분 / RTO 15분 → 훨씬 강한 복제, 자동화, 다중 환경 필요

즉, 백업 전략은 기술이 아니라 업무 중요도와 복구 목표에 따라 결정되어야 함.

13.5 AWS에서 보호 대상이 되는 대표 리소스

AWS에서 백업이 필요한 대표 자원

  • EBS 볼륨
  • RDS 데이터베이스
  • DynamoDB 테이블
  • EFS 파일 시스템
  • FSx 파일 시스템
  • EC2 관련 구성 일부
  • VMware 워크로드 등 일부 연계 자원

모든 AWS 리소스가 백업 대상인 것은 아니며,

특히 상태 저장 데이터가 있는 리소스가 핵심 보호 대상임.

즉, 백업은 서버보다도 데이터 계층 중심으로 생각하는 것이 중요함.

13.6 AWS Backup 개요

AWS Backup은 여러 AWS 서비스의 백업을 중앙에서 정책 기반으로 관리할 수 있게 해주는 관리형 백업 서비스임.

즉, 각 서비스별로 개별 백업 기능을 따로 관리하는 대신,

중앙 정책과 보관소를 통해 일관되게 백업을 운영할 수 있게 해줌.

핵심 역할

  • 백업 정책 정의
  • 주기적 백업 자동화
  • 보관 기간 관리
  • 중앙 백업 보관
  • 복구 작업 수행
  • 여러 계정/여러 리전 백업 관리 지원

즉, AWS Backup은 단순 백업 생성 기능이 아니라

중앙 집중형 백업 운영 체계라고 볼 수 있음.

13.7 AWS Backup이 필요한 이유

각 AWS 서비스는 자체 백업 기능을 가질 수 있음.

예를 들어 RDS는 자동 백업과 스냅샷 기능이 있고, EBS는 스냅샷이 있으며, DynamoDB도 백업 기능이 있음.

하지만 서비스가 늘어나면 다음 문제가 생김.

  • 백업 설정이 서비스별로 흩어짐
  • 보관 정책이 제각각임
  • 누락된 리소스가 생길 수 있음
  • 중앙 감사와 추적이 어려움
  • 계정/리전 단위 관리가 복잡함

AWS Backup은 이런 문제를 줄이기 위해

백업 정책과 운영을 중앙에서 통합할 수 있게 해줌.

13.8 AWS Backup의 핵심 구성 요소

AWS Backup을 이해할 때 중요한 개념

  • Backup Plan
  • Backup Rule
  • Backup Vault
  • Recovery Point
  • Resource Assignment

13.8.1 Backup Plan

백업 정책의 상위 정의임.

언제 백업할지, 얼마나 오래 보관할지, 어떤 보관소를 사용할지 등을 정의함.

즉, Backup Plan은 “백업 운영 정책서”에 해당함.

13.8.2 Backup Rule

Backup Plan 안에서 실제 스케줄과 보존 정책을 정의하는 세부 규칙임.

예를 들어

  • 매일 1회 백업
  • 30일 보관
  • 특정 Vault에 저장

같은 내용이 여기에 들어감.

13.8.3 Backup Vault

백업 데이터를 저장하는 논리적 보관소임.

즉, 생성된 백업 결과물이 모이는 저장 공간이라고 이해하면 됨.

13.8.4 Recovery Point

백업이 생성된 특정 시점의 복구 지점을 의미함.

즉, “이 시점으로 되돌릴 수 있다”는 단위임.

13.8.5 Resource Assignment

어떤 리소스에 어떤 백업 정책을 적용할지 정하는 연결 관계임.

예를 들어

  • 특정 태그가 붙은 RDS
  • 특정 EFS
  • 특정 DynamoDB 테이블

에 대해 같은 정책을 적용할 수 있음.

13.9 태그 기반 백업 관리

대규모 환경에서는 백업 대상을 하나씩 직접 지정하면 운영이 매우 번거로움.

그래서 AWS Backup은 태그 기반 리소스 선택이 중요함.

예

  • Backup=Daily
  • Environment=Prod

같은 태그를 기준으로 정책을 자동 적용할 수 있음.

장점

  • 신규 리소스에도 자동 정책 적용 가능
  • 운영 표준화 쉬움
  • 누락 가능성 감소

즉, 백업도 결국 리소스 분류와 표준화 체계 위에서 관리하는 것이 좋음.

13.10 백업 보관소(Backup Vault)의 의미

Vault는 단순히 파일 저장 위치가 아니라,

백업 자산을 중앙에서 통제하고 보존하며 감사하기 위한 논리적 경계로 볼 수 있음.

Vault를 통해 다음 관점이 중요해짐.

  • 어떤 백업을 어디에 보관하는가
  • 얼마나 오래 유지하는가
  • 누가 접근할 수 있는가
  • 삭제 보호가 필요한가

즉, Vault는 보관 정책과 보안 통제가 만나는 지점임.

13.11 스냅샷 개념

AWS 백업에서 자주 나오는 개념 중 하나가 Snapshot 임.

스냅샷은 특정 시점의 데이터 상태를 저장한 복사본임.

대표 예

  • EBS Snapshot
  • RDS Snapshot

스냅샷의 핵심 의미는 다음과 같음.

현재 데이터 상태를 특정 시점 기준으로 보존한다.

즉, 스냅샷은 백업의 한 형태이자 복구 기준점이 됨.

13.12 EBS Snapshot

EBS Snapshot은 EBS 볼륨의 특정 시점 상태를 저장하는 기능임.

운영체제 디스크 또는 데이터 디스크를 보호할 때 중요함.

특징

  • 증분 방식 저장
  • 다른 볼륨으로 복원 가능
  • 다른 AZ/환경에서 재사용 가능
  • AMI 생성과도 관련될 수 있음

즉, EBS Snapshot은 EC2 스토리지 보호의 핵심 수단 중 하나임.

13.13 RDS Backup과 Snapshot

RDS는 자체적으로 백업 기능을 제공함.

크게 보면 다음 관점으로 구분 가능함.

자동 백업

지정된 보존 기간 동안 자동으로 백업과 트랜잭션 로그를 관리해 특정 시점 복구를 지원함.

수동 스냅샷

운영자가 특정 시점을 별도로 보존하기 위해 만드는 백업임.

즉, RDS는 단순 스냅샷뿐 아니라 Point-in-Time Recovery와 연결되는 것이 중요함.

13.14 Point-in-Time Recovery 개념

Point-in-Time Recovery는 특정 스냅샷 시점이 아니라,

허용된 범위 안에서 원하는 시점으로 복구하는 개념임.

예를 들어

  • 오전 9시에 잘못된 데이터 삭제 발생
  • 오전 8시 57분 상태로 복구 필요

이런 경우 단순한 하루 1회 스냅샷만으로는 부족할 수 있음.

즉, RPO를 더 줄이려면 PITR 같은 기능이 중요함.

13.15 EFS와 파일 시스템 백업

EFS 같은 공유 파일 시스템도 백업 대상이 됨.

공유 저장소는 여러 서버가 동시에 접근하기 때문에 손상이나 삭제 영향 범위가 더 클 수 있음.

따라서 다음이 중요함.

  • 주기적 백업
  • 복구 시점 관리
  • 장기 보관 정책
  • 파일 시스템 복원 계획

즉, 파일 시스템 계층도 단순 저장소가 아니라 보호 대상 데이터 자산으로 봐야 함.

13.16 DynamoDB 백업

DynamoDB도 백업과 복구 기능을 제공함.

특히 서버리스 또는 NoSQL 기반 애플리케이션에서 중요함.

중요한 점

  • 테이블 수준 보호
  • 온디맨드 백업 가능
  • 특정 시점 복구 지원 가능
  • 백업 체계를 중앙 정책으로 통합 가능

즉, 서버리스 데이터 저장소라고 해서 백업이 필요 없는 것이 아니며,

오히려 자동화된 보호 체계가 더 중요할 수 있음.

13.17 백업 주기 설계

백업을 설계할 때 가장 중요한 것 중 하나가 주기임.

대표 질문

  • 하루 1회면 충분한가
  • 시간 단위가 필요한가
  • 실시간 복제가 필요한가
  • 백업 창은 언제가 적절한가

주기는 보통 다음에 따라 달라짐.

  • 데이터 변경 빈도
  • 업무 중요도
  • 허용 가능한 데이터 손실 범위(RPO)
  • 시스템 부하 특성

즉, 주기는 기술적으로 정하는 것이 아니라 업무 요구에 맞춰 정하는 것임.

13.18 보관 기간 설계

백업은 만들기만 하는 것이 아니라 얼마나 오래 보관할 것인가도 중요함.

대표 고려사항

  • 최근 복구는 얼마나 자주 필요한가
  • 규제상 장기 보관이 필요한가
  • 비용을 얼마나 허용할 수 있는가
  • 오래된 백업을 Glacier 성격으로 옮길 것인가

예를 들어

  • 일간 백업 30일
  • 주간 백업 12주
  • 월간 백업 12개월

같은 식의 다층 보관 전략을 사용할 수 있음.

즉, 보관 기간은 기술과 비용, 규정이 모두 연결되는 설계 요소임.

13.19 크로스 리전 백업

단일 리전 안에만 백업을 두면, 리전 단위 장애나 광범위 사고에는 취약할 수 있음.

이때 중요한 것이 Cross-Region Backup 임.

의미

  • 백업 사본을 다른 리전에 복제
  • 지역 재해 상황 대비
  • 복구 위치 다양성 확보

즉, 크로스 리전 백업은 단순 추가 복사가 아니라

재해 복구(Disaster Recovery) 전략과 연결됨.

13.20 크로스 계정 백업

백업을 같은 계정 안에만 보관하면, 계정 침해나 내부 실수에 취약할 수 있음.

이때 Cross-Account Backup 전략이 중요해질 수 있음.

의미

  • 운영 계정과 별도 백업 계정 분리
  • 삭제/변조 위험 감소
  • 중앙 보안 계정에서 통제 가능

즉, 중요한 환경일수록 백업은 원본 환경과 논리적으로도 분리하는 것이 좋음.

13.21 백업 보안의 중요성

백업은 원본 데이터를 보호하기 위한 것이지만,

백업 자체도 민감한 데이터일 수 있음.

따라서 백업 보안이 매우 중요함.

핵심 요소

  • 암호화
  • 접근 제어
  • 삭제 보호
  • 감사 추적
  • 계정 분리
  • 장기 보관 정책

즉, 백업은 “복사본”이 아니라 중요한 데이터 자산으로 다뤄야 함.

13.22 암호화와 백업

백업 데이터는 보통 원본만큼 중요하거나 더 민감할 수 있음.

따라서 저장 시 암호화가 중요함.

AWS에서는 보통 다음과 연결됨.

  • KMS 기반 암호화
  • 서비스별 암호화 통합
  • Vault/스냅샷 보관 시 암호화 유지

즉, 백업은 보존만이 아니라 기밀성 보호도 함께 고려해야 함.

13.23 복구 전략의 수준

복구 전략은 단일하지 않음.

업무 중요도에 따라 여러 수준으로 나뉨.

13.23.1 단순 백업 복구

장애 후 수동으로 복원하는 방식임.

비용은 적을 수 있지만 복구 시간이 길 수 있음.

13.23.2 스냅샷 기반 빠른 복구

주기적 스냅샷을 통해 비교적 빠르게 복원하는 방식임.

13.23.3 크로스 리전 백업 기반 DR

다른 리전에 백업을 유지해 대규모 재해에도 복구 가능성을 높이는 방식임.

13.23.4 웜 스탠바이 / 멀티 사이트 수준

백업을 넘어서 거의 즉시 전환 가능한 대기 환경을 유지하는 방식임.

이는 DR 장에서 더 확장될 수 있음.

즉, 백업은 복구 전략 전체의 일부이며,

RTO/RPO가 작아질수록 단순 백업만으로는 부족할 수 있음.

13.24 백업과 DR의 관계

백업은 Disaster Recovery와 밀접하게 관련되지만 완전히 같은 것은 아님.

  • 백업 : 데이터를 보존하고 복원 가능하게 함
  • DR : 재해 상황에서 서비스 전체를 다시 운영 가능하게 함

즉, DR은 데이터뿐 아니라 다음까지 포함함.

  • 네트워크
  • 애플리케이션
  • 데이터베이스
  • 인증
  • DNS
  • 운영 절차

따라서 백업은 DR의 핵심 요소이지만, DR 전체를 대체하지는 않음.

13.25 복구 테스트의 중요성

백업은 만들어 두기만 하면 끝이 아님.

실제로 복구가 가능한지, 얼마나 걸리는지, 절차가 맞는지 검증해야 함.

복구 테스트가 중요한 이유

  • 백업이 실제로 유효한지 확인
  • 복구 시간 측정 가능
  • 절차 문서 검증 가능
  • 권한/네트워크 문제 사전 발견
  • 운영자 숙련도 향상

즉, 백업은 “저장 여부”보다 복구 가능성 검증이 더 중요할 수 있음.

13.26 운영 관점의 백업 설계 포인트

1. 모든 리소스를 같은 방식으로 보호하면 안 됨

데이터 중요도에 따라 정책을 다르게 해야 함.

2. 태그 기반 표준화가 중요함

백업 누락을 줄이기 위해 정책 자동화를 활용해야 함.

3. 단일 리전/단일 계정 의존을 줄여야 함

중요 서비스일수록 크로스 리전, 크로스 계정 전략을 고려해야 함.

4. 백업과 복구를 같이 설계해야 함

백업만 있고 복구 절차가 없으면 운영 가치가 낮음.

5. 비용과 보존의 균형이 필요함

오래 보관할수록 비용이 늘어나므로 계층화와 정책이 필요함.

즉, 백업은 단순 저장이 아니라 정책, 보안, 운영, 비용의 균형 문제임.

13.27 멀티 티어 아키텍처와의 연결

앞에서 만든 멀티 티어 구조에 백업 계층을 연결하면 다음처럼 볼 수 있음.

Web / App Tier
   │
RDS / EFS / DynamoDB / EBS
   │
AWS Backup / Snapshot / Backup Vault
   │
Cross-Region / Cross-Account 복제

이 구조의 의미

  • 운영 데이터는 여러 서비스에 분산 저장됨
  • 각 서비스의 백업을 중앙 정책으로 관리 가능함
  • 백업은 단일 위치가 아니라 복수 위치 보호까지 고려 가능함

즉, 백업은 아키텍처의 마지막 부가 기능이 아니라

전체 시스템 신뢰성의 핵심 계층임.

13.28 AWS Backup의 의미 한 번에 정리

AWS Backup은 여러 AWS 서비스의 백업을 중앙에서 일관되게 관리하게 해주는 서비스임.

여기서 중요한 점은 다음과 같음.

  • 서비스별 백업 기능을 통합함
  • 정책 기반 자동화를 가능하게 함
  • 보관소 중심 관리가 가능함
  • 계정/리전 확장성을 고려할 수 있음
  • 감사와 표준화에 유리함

즉, AWS Backup은 단순한 스냅샷 생성기가 아니라

엔터프라이즈 백업 운영 플랫폼에 가까움.

13.29 서비스 역할 한 번에 정리

AWS Backup

여러 AWS 서비스의 백업을 중앙 정책 기반으로 관리한다.

Backup Plan

언제, 얼마나 자주, 얼마나 오래 백업할지 정의한다.

Backup Vault

백업 결과를 저장하는 논리적 보관소다.

Recovery Point

특정 시점으로 복구할 수 있는 백업 지점이다.

Snapshot

특정 시점의 데이터 상태를 저장한 복사본이다.

Cross-Region Backup

리전 단위 재해에 대비해 다른 리전에 백업을 복제한다.

Cross-Account Backup

계정 침해나 실수에 대비해 별도 계정에 백업을 보관한다.

13.31 한 줄 정리

고가용성은 서비스를 계속 운영하게 한다.
백업은 데이터를 다시 되살릴 수 있게 한다.
AWS Backup은 여러 서비스의 백업을 중앙 정책으로 관리하게 해준다.
