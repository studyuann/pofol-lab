7장 AWS 모니터링 및 크기 조정 아키텍처

CloudWatch, Elastic Load Balancing, Auto Scaling

7.1 모니터링과 크기 조정의 필요성

AWS에서 애플리케이션을 운영할 때 서버를 단순히 생성하는 것만으로는 충분하지 않음.

실제 운영 환경에서는 다음과 같은 문제가 항상 발생할 수 있음.

  • 트래픽 증가
  • 특정 인스턴스의 CPU 과부하
  • 메모리 부족
  • 디스크 사용량 증가
  • 애플리케이션 장애
  • 특정 인스턴스의 비정상 종료
  • 응답 지연 증가

이런 상황을 사람이 수동으로 계속 확인하고 대응하는 방식은 확장성이 낮고 장애 대응도 늦어짐.

따라서 AWS에서는 다음 3가지 축을 함께 사용함.

  • CloudWatch : 상태를 수집하고 관찰함
  • ELB : 트래픽을 여러 대상에 분산함
  • Auto Scaling : 인스턴스 수를 자동으로 조정함

즉, 이 장의 핵심은 다음과 같음.

관찰하고, 분산하고, 자동 확장한다.

7.2 운영 환경에서 단일 서버의 한계

초기 학습 단계에서는 EC2 인스턴스 1대로 웹 서버를 띄우는 실습을 많이 수행함.

하지만 실제 운영 환경에서 단일 서버 구조는 다음과 같은 한계를 가짐.

1. 단일 장애점(SPOF)

인스턴스 1대가 중단되면 서비스 전체가 중단됨.

2. 확장성 부족

트래픽이 증가해도 서버를 자동으로 늘릴 수 없음.

3. 유지보수 어려움

패치나 재부팅 시 서비스 중단이 발생할 수 있음.

4. 부하 집중

특정 시점에 요청이 몰리면 응답 지연이 커짐.

따라서 운영 환경에서는 보통 다음 구조를 목표로 설계함.

사용자
  │
Load Balancer
  │
여러 대의 EC2
  │
Auto Scaling

그리고 이 구조를 안정적으로 운영하기 위해 지속적인 관찰 수단이 필요하며, 그 역할을 CloudWatch가 담당함.

7.3 Amazon CloudWatch 개요

Amazon CloudWatch는 AWS 리소스와 애플리케이션의 상태를 모니터링하는 서비스임.

단순히 숫자를 보여주는 대시보드가 아니라, 운영 상태를 수집하고 시각화하고, 임계값을 기준으로 경보를 발생시키며, 자동 조치까지 연결할 수 있는 서비스임.

CloudWatch의 핵심 역할

  • 메트릭 수집
  • 로그 수집
  • 경보 생성
  • 대시보드 시각화
  • 이벤트 기반 자동화 연계

CloudWatch를 이해할 때는 다음 구성 요소를 구분해서 보는 것이 중요함.

  • Metrics
  • Logs
  • Alarms
  • Dashboards
  • Events / EventBridge 연계

7.4 CloudWatch Metrics

메트릭은 시간에 따라 변화하는 수치 데이터임.

예를 들어 EC2의 CPU 사용률, 네트워크 패킷 수, 디스크 읽기 횟수 같은 값이 메트릭에 해당함.

대표적인 예

  • CPUUtilization
  • NetworkIn
  • NetworkOut
  • DiskReadOps
  • DiskWriteOps
  • StatusCheckFailed

이 메트릭들은 시간 축을 따라 누적되며, 운영자는 이를 통해 현재 시스템 상태와 변화 추이를 확인할 수 있음.

7.4.1 메트릭의 의미

메트릭을 단순한 숫자로 보면 안 됨.

각 메트릭은 시스템 상태를 간접적으로 보여주는 신호임.

예를 들어

CPUUtilization

CPU 사용률이 높다는 것은 해당 인스턴스가 연산 작업을 많이 수행하고 있다는 뜻임.

웹 서버라면 요청량이 증가했을 수 있고, 배치 작업이 동작 중일 수도 있음.

NetworkIn / NetworkOut

네트워크 유입/유출량이 증가했다는 것은 트래픽이 증가하고 있다는 의미일 수 있음.

Status Check

인스턴스 상태 검사 실패는 하드웨어, 네트워크, 운영체제 수준의 이상 신호일 수 있음.

즉, CloudWatch는 단순 관찰 도구가 아니라 시스템 상태 해석 도구라고 볼 수 있음.

7.4.2 기본 메트릭과 커스텀 메트릭

CloudWatch 메트릭은 크게 두 종류로 볼 수 있음.

기본 메트릭

AWS 서비스가 자동으로 제공하는 메트릭임.

예를 들어 EC2 CPU 사용률, ALB 요청 수 같은 값이 이에 해당함.

커스텀 메트릭

사용자가 직접 수집해서 올리는 메트릭임.

예를 들어

  • 애플리케이션 처리 건수
  • 로그인 실패 횟수
  • 큐 적재 건수
  • 비즈니스 KPI

같은 값은 사용자가 직접 정의해서 보낼 수 있음.

즉, 기본 메트릭은 인프라 중심이고, 커스텀 메트릭은 애플리케이션/업무 중심이라고 볼 수 있음.

7.5 CloudWatch Logs

메트릭이 숫자 기반 상태 정보라면, 로그는 상세한 텍스트 기반 기록임.

예를 들어 애플리케이션 에러 메시지, 웹 서버 접근 로그, 시스템 로그 등이 이에 해당함.

CloudWatch Logs의 역할

  • 로그 중앙 수집
  • 로그 보관
  • 로그 검색
  • 로그 분석
  • 특정 패턴 감지

운영 환경에서는 로그가 여러 서버에 흩어져 있으면 분석이 매우 불편함.

CloudWatch Logs를 사용하면 여러 인스턴스의 로그를 중앙에서 관리할 수 있음.

7.5.1 로그와 메트릭의 차이

항목메트릭로그
형태숫자 기반텍스트 기반
목적상태 추세 파악원인 분석
예CPU 85%오류 메시지 stack trace
활용모니터링, 경보디버깅, 감사, 분석

즉,

  • 메트릭은 이상 징후를 감지하는 데 강함
  • 로그는 원인을 분석하는 데 강함

이라고 정리할 수 있음.

7.5.2 로그 그룹과 로그 스트림

CloudWatch Logs는 보통 다음 구조로 이해하면 됨.

  • Log Group : 관련 로그들의 상위 묶음
  • Log Stream : 개별 인스턴스/프로세스/실행 단위의 로그 흐름

예를 들어

/application/web
  ├ instance-1
  ├ instance-2
  └ instance-3

이런 구조로 볼 수 있음.

즉, 로그 그룹은 논리적 구분이고, 로그 스트림은 실제 발생 단위에 가깝다고 보면 됨.

7.6 CloudWatch Alarm

CloudWatch Alarm은 메트릭이 특정 조건을 만족할 때 경보를 발생시키는 기능임.

단순히 “상태를 본다”에서 끝나는 것이 아니라, 이상 상태를 자동으로 감지하는 단계로 넘어가는 것임.

예

  • CPU 사용률이 80% 이상
  • ALB 응답 지연이 2초 초과
  • UnHealthyHostCount가 1 이상
  • 네트워크 유입량이 급증

Alarm은 운영자가 항상 화면을 보고 있지 않아도 문제를 인지할 수 있게 만드는 핵심 장치임.

7.6.1 Alarm의 구성 요소

Alarm은 보통 다음 요소로 구성됨.

  • 대상 메트릭
  • 임계값(Threshold)
  • 비교 조건
  • 평가 기간(Evaluation Period)
  • 통계 방식(Average, Sum 등)
  • 알림/조치 대상

예를 들어 CPU 사용률 경보를 만든다고 하면 다음 요소를 정해야 함.

  • 어떤 인스턴스의 CPU를 볼 것인지
  • 몇 % 이상이면 이상으로 볼 것인지
  • 1분 평균인지, 5분 평균인지
  • 한 번 넘으면 경보인지, 여러 번 연속인지
  • 경보 시 누구에게 알릴지

즉, Alarm은 단순한 숫자 비교가 아니라 운영 정책을 수치로 모델링한 것임.

7.6.2 Alarm 상태

CloudWatch Alarm은 보통 다음 상태를 가짐.

  • OK
  • ALARM
  • INSUFFICIENT_DATA

OK

정상 상태임.

ALARM

임계값 조건을 만족해서 경보가 발생한 상태임.

INSUFFICIENT_DATA

아직 판단할 데이터가 부족한 상태임.

특히 교육 중 자주 헷갈리는 부분이 INSUFFICIENT_DATA임.

이 상태는 무조건 오류를 뜻하는 것이 아니라, 아직 충분한 샘플이 쌓이지 않았거나 메트릭이 수집되지 않은 상태일 수 있음.

7.7 CloudWatch Dashboard

Dashboard는 여러 메트릭과 그래프를 한 화면에 시각적으로 배치하는 기능임.

운영자가 시스템 상태를 빠르게 파악할 수 있도록 도와줌.

대시보드에 보통 포함하는 항목

  • EC2 CPU 사용률
  • ALB 요청 수
  • ALB 응답 시간
  • RDS CPU 및 연결 수
  • Auto Scaling 인스턴스 수
  • 에러 건수
  • 캐시 히트율

대시보드는 단순히 “예쁘게 보기 위한 화면”이 아니라,

운영자가 무엇을 중요하게 볼 것인가를 구조화한 관찰 도구임.

7.8 Elastic Load Balancing 개요

Elastic Load Balancing은 들어오는 트래픽을 여러 대상(Target)에 분산하는 서비스임.

운영 환경에서는 여러 대의 서버가 동시에 서비스를 제공하는 경우가 많으므로, 요청을 적절히 나누는 장치가 필요함.

ELB의 역할

  • 트래픽 분산
  • 장애 인스턴스 제외
  • 고가용성 지원
  • SSL/TLS 종료 가능
  • 애플리케이션 계층 라우팅 지원

즉, ELB는 단순히 “앞단 프록시”가 아니라 가용성과 확장성의 중심 구성요소임.

7.9 로드 밸런서가 필요한 이유

서버가 2대 이상 있다고 해서 자동으로 고가용성이 되는 것은 아님.

사용자 요청이 어느 서버로 갈지 제어할 수 있어야 하며, 장애가 난 서버로는 요청을 보내지 않아야 함.

로드 밸런서가 없다면 다음과 같은 문제가 있음.

  • 사용자가 특정 인스턴스 주소를 직접 알아야 함
  • 서버 추가/삭제 시 클라이언트 구성이 복잡해짐
  • 장애 서버를 자동 제외하기 어려움
  • SSL 인증서 관리가 분산됨

로드 밸런서를 두면 사용자 입장에서는 하나의 진입점만 보면 됨.

사용자
  │
Load Balancer
  ├ App Server 1
  ├ App Server 2
  └ App Server 3

이 구조를 통해 뒤쪽 인스턴스 수가 바뀌더라도 사용자 진입점은 유지됨.

7.10 ELB 종류

AWS의 로드 밸런서는 대표적으로 다음 종류가 있음.

  • ALB (Application Load Balancer)
  • NLB (Network Load Balancer)
  • GWLB (Gateway Load Balancer)

ARC 과정에서는 보통 ALB 중심으로 설명하는 것이 가장 자연스러움.

7.10.1 ALB

ALB는 7계층(Application Layer, HTTP/HTTPS) 로드 밸런서임.

특징

  • HTTP/HTTPS 트래픽 처리
  • 경로 기반 라우팅
  • 호스트 기반 라우팅
  • SSL 종료 가능
  • 웹 애플리케이션에 적합

예를 들어

  • /api/* 요청은 API 서버로
  • /images/* 요청은 이미지 서버로
  • admin.example.com은 관리자 서버로

보낼 수 있음.

즉, ALB는 단순 분산뿐 아니라 애플리케이션 인식 라우팅이 가능함.

7.10.2 NLB

NLB는 4계층(Network Layer, TCP/UDP) 로드 밸런서임.

특징

  • 매우 높은 성능
  • 낮은 지연시간
  • TCP/UDP 처리
  • 고정 IP 지원 가능

웹 애플리케이션보다는 네트워크 수준 처리나 매우 높은 처리량이 중요한 경우에 적합함.

7.10.3 Gateway Load Balancer

보안 장비나 네트워크 가상 어플라이언스를 투명하게 삽입할 때 사용함.

일반적인 웹 아키텍처 입문 단계에서는 깊게 다루지 않아도 됨.

7.11 Target Group

로드 밸런서는 직접 인스턴스를 향해 요청을 보내는 것이 아니라, 보통 Target Group을 통해 대상을 관리함.

Target Group의 역할

  • 대상 인스턴스/서비스 묶음 관리
  • Health Check 수행
  • 어떤 요청을 어디로 보낼지 연결

즉, 로드 밸런서와 인스턴스 사이의 중간 추상화 계층이라고 보면 됨.

장점

  • 인스턴스 교체가 쉬움
  • Auto Scaling과 연동이 쉬움
  • Health Check를 기준으로 정상 대상만 유지 가능함

7.12 Health Check

Health Check는 대상 서버가 정상적으로 요청을 처리할 수 있는지 확인하는 기능임.

로드 밸런서는 Health Check 결과를 바탕으로 정상 대상에게만 트래픽을 보냄.

예를 들어 인스턴스가 살아 있어도 애플리케이션이 죽어 있을 수 있음.

이 경우 단순히 서버가 켜져 있다는 이유만으로 요청을 보내면 안 됨.

따라서 Health Check는 보통 다음을 확인함.

  • 특정 포트 응답 여부
  • 특정 URL 응답 코드
  • 응답 시간
  • 연속 성공/실패 횟수

즉, Health Check는 가용성 판단 기준임.

7.12.1 Health Check의 중요성

Health Check를 제대로 설계하지 않으면 다음 문제가 발생함.

  • 장애 서버에도 계속 요청이 감
  • 실제로는 문제인데 정상으로 판단함
  • 너무 엄격해서 잠깐 느린 서버도 제외됨

따라서 Health Check는 단순 설정값이 아니라, 애플리케이션 특성을 반영해야 함.

예를 들어

  • 단순 정적 웹 서버면 /만 확인해도 될 수 있음
  • 실제 앱 상태를 보려면 /health 같은 전용 엔드포인트가 필요할 수 있음

7.13 고가용성과 로드 밸런서

로드 밸런서는 고가용성 구조의 핵심임.

특히 여러 AZ에 인스턴스를 분산 배치할 때 효과가 큼.

예

ALB
 ├ EC2 (AZ-a)
 └ EC2 (AZ-c)

이 구조에서는 한 AZ의 인스턴스가 장애를 일으켜도 다른 AZ의 정상 인스턴스가 계속 요청을 처리할 수 있음.

즉, 고가용성은 단순히 서버 수를 늘리는 것이 아니라

  • 여러 서버를 두고
  • 여러 AZ에 분산하고
  • 로드 밸런서로 연결하고
  • Health Check로 비정상 서버를 제외하는

조합으로 완성됨.

7.14 Auto Scaling 개요

Auto Scaling은 인스턴스 수를 자동으로 늘리거나 줄이는 기능임.

즉, 트래픽 양이나 상태 변화에 따라 서버 수를 동적으로 조정함.

이 기능이 필요한 이유는 다음과 같음.

  • 트래픽은 항상 일정하지 않음
  • 피크 시간과 비피크 시간이 다름
  • 항상 최대 부하 기준으로 서버를 유지하면 비용이 낭비됨
  • 갑작스러운 부하 증가에 수동 대응은 느림

따라서 Auto Scaling은 가용성과 비용 효율성을 동시에 달성하기 위한 핵심 기능임.

7.15 Auto Scaling Group

Auto Scaling은 보통 Auto Scaling Group(ASG) 단위로 동작함.

ASG는 동일한 설정을 가진 인스턴스 집합을 관리하는 논리 그룹임.

ASG가 관리하는 요소

  • 최소 인스턴스 수
  • 최대 인스턴스 수
  • 원하는 인스턴스 수
  • 배치할 서브넷/AZ
  • 사용할 시작 템플릿
  • 확장/축소 정책
  • Health Check 기준

즉, ASG는 단순히 “서버를 늘리는 기능”이 아니라 동일한 서버 군을 자동 관리하는 엔진이라고 볼 수 있음.

7.15.1 Desired / Min / Max Capacity

ASG에서 매우 중요한 3가지 값이 있음.

Desired Capacity

현재 유지하려는 인스턴스 수임.

Minimum Capacity

이 아래로는 절대 줄이지 않음.

Maximum Capacity

이 이상으로는 늘리지 않음.

예를 들어

  • Min = 2
  • Desired = 2
  • Max = 6

이라면 평소 2대를 유지하다가 부하가 높아지면 최대 6대까지 확장할 수 있음.

이 세 값은 Auto Scaling의 동작 범위를 정의하는 핵심 파라미터임.

7.16 Launch Template

ASG가 새 인스턴스를 생성하려면 어떤 이미지와 사양으로 만들지 정의해야 함.

그 역할을 하는 것이 Launch Template임.

포함 정보 예

  • AMI
  • 인스턴스 타입
  • 보안 그룹
  • IAM Role
  • User Data
  • Key Pair
  • EBS 설정

즉, Launch Template은 “새 서버를 어떤 형태로 복제할 것인가”를 정의하는 청사진임.

7.17 Scaling Policy

Scaling Policy는 언제 인스턴스를 늘리고 줄일지 정하는 정책임.

확장 정책이 없다면 ASG는 인스턴스 수를 어떻게 바꿔야 하는지 판단할 수 없음.

대표적인 방식

  • Target Tracking Scaling
  • Step Scaling
  • Scheduled Scaling

7.17.1 Target Tracking Scaling

가장 이해하기 쉬운 방식임.

특정 메트릭을 목표 값으로 유지하도록 자동 조정함.

예

  • 평균 CPU 사용률 50% 유지
  • ALB 요청 수 per target 일정 수준 유지

즉, 시스템이 특정 목표 상태를 유지하도록 자동으로 인스턴스 수를 조정하는 방식임.

이 방식은 개념적으로 가장 직관적이어서 교육 과정에서 설명하기 좋음.

7.17.2 Step Scaling

임계값 구간에 따라 다른 규모로 확장/축소하는 방식임.

예

  • CPU 60% 초과 시 1대 증가
  • CPU 80% 초과 시 2대 증가

즉, 조건에 따라 단계적으로 반응하도록 설계하는 방식임.

7.17.3 Scheduled Scaling

특정 시간에 맞춰 인스턴스 수를 변경하는 방식임.

예

  • 오전 9시 전에 4대로 늘림
  • 야간에는 2대로 줄임

트래픽 패턴이 예측 가능할 때 유용함.

7.18 Scale Out과 Scale In

Auto Scaling에서 반드시 구분해야 할 개념임.

Scale Out

인스턴스 수를 늘리는 것임.

Scale In

인스턴스 수를 줄이는 것임.

학생들이 흔히 “오토스케일링 = 늘어나는 것”으로만 이해하는데, 실제로는 줄이는 것도 매우 중요함.

특히 비용 최적화 측면에서는 Scale In이 핵심일 수 있음.

7.19 수평 확장과 수직 확장

확장을 이해할 때는 두 가지 방식을 구분해야 함.

수직 확장(Scale Up)

기존 인스턴스를 더 큰 사양으로 바꾸는 것임.

예

  • t3.micro → t3.large

장점

  • 구조가 단순함

한계

  • 물리적 상한이 있음
  • 재시작이나 변경 작업이 필요할 수 있음

수평 확장(Scale Out)

같은 인스턴스를 여러 대로 늘리는 것임.

예

  • 웹 서버 1대 → 3대

장점

  • 고가용성과 확장성에 유리함
  • ELB, Auto Scaling과 잘 맞음

운영 환경에서는 보통 수평 확장을 더 선호함.

7.20 CloudWatch와 Auto Scaling의 연계

CloudWatch와 Auto Scaling은 서로 독립된 서비스가 아니라 강하게 연결됨.

동작 흐름 예

CloudWatch가 CPU 사용률 상승 감지
   │
Alarm 또는 Scaling Policy 조건 만족
   │
Auto Scaling Group이 인스턴스 추가

즉,

  • CloudWatch는 관찰하고
  • Auto Scaling은 반응함

이 관계로 이해하면 됨.

7.21 ELB와 Auto Scaling의 연계

ELB와 Auto Scaling도 함께 동작해야 의미가 있음.

인스턴스 수가 늘어나도 로드 밸런서가 그 사실을 모르고 있으면 요청 분산이 되지 않음.

Auto Scaling Group과 Target Group을 연동하면 다음 흐름이 가능함.

  • 새 인스턴스 생성
  • 인스턴스 초기화
  • Health Check 통과
  • Target Group 등록
  • 트래픽 분산 시작

반대로 축소 시에는

  • 대상 제외
  • 연결 정리
  • 인스턴스 종료

순서로 처리됨.

즉, ELB와 ASG의 결합은 확장 가능한 서비스 운영의 기본 패턴임.

7.22 운영 관점의 설계 포인트

이 장의 서비스들은 각각 독립적으로 볼 수도 있지만, 실제 운영에서는 하나의 흐름으로 묶어서 설계해야 함.

7.22.1 모니터링 없는 확장은 위험함

인스턴스 수가 자동으로 늘어난다고 해도 왜 늘어났는지 모르면 운영 품질을 개선할 수 없음.

Auto Scaling만 보는 것이 아니라, 그 원인이 되는 메트릭과 로그를 함께 봐야 함.

즉

  • 확장 자체
  • 확장의 원인
  • 확장의 결과

를 함께 관찰해야 함.

7.22.2 Health Check는 매우 중요함

Health Check가 부정확하면 장애 인스턴스에 요청을 보내거나, 반대로 정상 인스턴스를 제외할 수 있음.

특히 ALB와 ASG가 함께 동작하는 구조에서는 Health Check가 전체 안정성에 큰 영향을 줌.

7.22.3 최소 인스턴스 수는 고가용성과 연결됨

예를 들어 최소 인스턴스 수를 1로 두면 Auto Scaling이 있어도 특정 순간에는 단일 서버 상태가 될 수 있음.

운영 환경에서는 보통 최소 2대를 서로 다른 AZ에 두는 것이 바람직함.

7.22.4 확장 정책은 애플리케이션 특성에 맞아야 함

CPU 기반 확장이 항상 정답은 아님.

어떤 애플리케이션은 CPU보다 요청 수, 큐 길이, 응답 시간, 동시 접속 수가 더 적절한 기준일 수 있음.

즉, 좋은 확장 정책은 서비스 병목 지점을 기준으로 잡아야 함.

7.23 멀티 티어 아키텍처와의 연결

이 장에서 다룬 내용을 3계층 구조에 연결하면 보통 다음과 같이 정리할 수 있음.

사용자
  │
ALB
  │
Auto Scaling Group의 Web/App EC2
  │
RDS / Redis / DynamoDB

이 구조에서

  • CloudWatch는 전체 상태를 관찰하고
  • ALB는 트래픽을 분산하며
  • Auto Scaling은 서버 수를 자동 조절함

즉, 이 장은 뒤에서 만들게 될 고가용성 멀티 티어 아키텍처의 핵심 운영 메커니즘을 설명하는 장이라고 볼 수 있음.

7.24 핵심 비교 정리

CloudWatch

  • 관찰하고 측정하는 서비스
  • 메트릭, 로그, 알람 중심
  • 이상 감지와 운영 가시성을 제공함

ELB

  • 요청을 여러 대상에 분산하는 서비스
  • 고가용성과 트래픽 분산의 핵심
  • Health Check를 통해 비정상 대상 제외 가능

Auto Scaling

  • 인스턴스 수를 자동 조정하는 서비스
  • 부하 대응과 비용 최적화에 핵심
  • CloudWatch와 연계해 자동 반응 가능

7.26 한 줄 정리

CloudWatch는 상태를 관찰한다.
ELB는 요청을 분산한다.

세 서비스를 함께 사용해야 가용성과 확장성이 살아난다.
