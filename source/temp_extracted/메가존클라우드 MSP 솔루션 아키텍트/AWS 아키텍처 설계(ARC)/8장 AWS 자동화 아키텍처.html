8장 AWS 자동화 아키텍처

CloudFormation, Elastic Beanstalk, AWS SDK

8.1 자동화의 필요성

AWS에서는 리소스를 콘솔에서 직접 생성할 수 있음.

초기 학습이나 빠른 테스트에는 이 방식이 편리함.

하지만 운영 환경이나 반복적인 배포 환경에서는 수작업 방식에 분명한 한계가 있음.

예를 들어 수작업 방식에서는 다음 문제가 자주 발생함.

  • 같은 환경을 다시 만들 때 설정이 달라짐
  • 누가 어떤 값을 넣었는지 추적하기 어려움
  • 실수로 잘못된 리소스를 생성할 수 있음
  • 운영 환경과 개발 환경이 서로 달라질 수 있음
  • 재현성과 일관성이 떨어짐
  • 복구 시간이 길어짐

즉, 사람 손으로 하나씩 만드는 방식은 처음에는 쉬워 보여도, 규모가 커질수록 품질과 속도에서 한계가 뚜렷해짐.

그래서 AWS 아키텍처에서는 자동화를 매우 중요하게 봄.

자동화는 단순 편의 기능이 아니라 운영 품질과 일관성을 확보하는 핵심 원칙임.

8.2 자동화의 핵심 목적

자동화는 다음 목적을 위해 사용함.

1. 반복 가능한 환경 구축

같은 인프라를 여러 번 만들어도 결과가 같아야 함.

2. 일관성 유지

개발, 테스트, 운영 환경이 최대한 동일한 구조를 가져야 함.

3. 배포 속도 향상

수작업보다 훨씬 빠르게 환경을 구성하고 변경할 수 있음.

4. 오류 감소

사람이 클릭하면서 발생하는 실수를 줄일 수 있음.

5. 변경 이력 관리

코드나 템플릿으로 남기면 누가 언제 무엇을 바꿨는지 추적하기 쉬움.

즉, 자동화는 “편하다”가 아니라

신뢰할 수 있는 인프라 운영 방식이라는 점이 중요함.

8.3 AWS 자동화 방식 개요

AWS에서는 자동화를 여러 수준에서 수행할 수 있음.

대표적인 방식

  • CloudFormation : 인프라 자체를 코드로 정의
  • Elastic Beanstalk : 애플리케이션 배포 자동화
  • AWS SDK : 코드에서 AWS 서비스 직접 제어

이 3가지는 자동화라는 공통점이 있지만 해결하는 문제가 다름.

서비스자동화 대상관점
CloudFormation인프라환경 생성과 구성
Elastic Beanstalk애플리케이션 배포플랫폼 관리 단순화
AWS SDK서비스 제어 로직애플리케이션 내부 연동

즉, 자동화라고 해서 모두 같은 층위의 자동화는 아님.

어떤 것은 인프라 자동화이고, 어떤 것은 애플리케이션 배포 자동화이며, 어떤 것은 애플리케이션 코드 차원의 자동화임.

8.4 Infrastructure as Code 개념

CloudFormation을 이해하려면 먼저 Infrastructure as Code(IaC) 개념을 이해해야 함.

IaC는 인프라 구성을 콘솔 클릭이 아니라 코드나 선언문 형태로 정의하는 방식임.

예를 들어 다음과 같은 리소스를 생각해보면

  • VPC
  • Subnet
  • Internet Gateway
  • EC2
  • Security Group
  • RDS

이것을 사람이 콘솔에서 하나씩 생성하는 대신, 템플릿 파일에 정의해 두고 같은 방식으로 반복 배포할 수 있음.

IaC의 핵심 장점

  • 재현 가능함
  • 버전 관리 가능함
  • 리뷰 가능함
  • 자동 배포 가능함
  • 표준화 가능함

즉, IaC는 인프라를 “문서”가 아니라 “실행 가능한 정의서”로 바꾸는 개념임.

8.5 Amazon CloudFormation 개요

CloudFormation은 AWS 리소스를 템플릿 파일로 정의하고, 그 템플릿을 바탕으로 인프라를 자동 생성·수정·삭제할 수 있게 해주는 서비스임.

쉽게 말하면 다음과 같음.

원하는 인프라 구조를 템플릿에 적는다.
CloudFormation이 그 구조대로 AWS 리소스를 만든다.

즉, CloudFormation은 AWS에서 제공하는 대표적인 IaC 도구임.

CloudFormation이 다룰 수 있는 대상 예

  • VPC
  • Subnet
  • Route Table
  • Security Group
  • EC2
  • ALB
  • Auto Scaling
  • RDS
  • S3
  • IAM 일부 리소스

즉, AWS 아키텍처를 구성하는 대부분의 핵심 리소스를 코드화할 수 있음.

8.6 CloudFormation의 기본 구조

CloudFormation은 보통 템플릿(template) 과 스택(stack) 개념으로 이해하면 됨.

템플릿

리소스를 어떻게 만들지 정의하는 설계 문서임.

YAML 또는 JSON 형식으로 작성함.

스택

템플릿을 실제로 실행해서 만들어진 리소스 집합임.

즉,

  • 템플릿은 설계도
  • 스택은 그 설계도로 실제 생성된 결과물

이라고 보면 됨.

예를 들어 하나의 템플릿에 다음이 정의되어 있을 수 있음.

  • VPC 1개
  • Public Subnet 2개
  • Private Subnet 2개
  • Internet Gateway 1개
  • Route Table 2개
  • EC2 2대

이 템플릿을 실행하면 하나의 스택이 생성되고, 그 안에서 모든 리소스가 관리됨.

8.7 CloudFormation의 장점

1. 재현성

같은 템플릿을 사용하면 같은 환경을 반복 생성할 수 있음.

2. 일관성

개발/테스트/운영 환경의 편차를 줄일 수 있음.

3. 버전 관리

템플릿 파일을 Git 같은 형상관리 도구에 저장할 수 있음.

4. 추적 가능성

어떤 리소스가 어떤 스택에 의해 생성되었는지 파악 가능함.

5. 변경 자동화

수정된 템플릿을 반영해 환경을 업데이트할 수 있음.

즉, CloudFormation은 리소스를 더 빨리 만드는 도구이기도 하지만,

그보다 더 중요한 것은 환경의 품질과 일관성을 높이는 도구라는 점임.

8.8 CloudFormation 템플릿 구성 요소

CloudFormation 템플릿은 여러 섹션으로 구성됨.

이 장에서는 문법 전체를 다루기보다 개념 중심으로 이해하는 것이 중요함.

대표 섹션

  • AWSTemplateFormatVersion
  • Description
  • Parameters
  • Resources
  • Outputs
  • Mappings
  • Conditions

이 중 가장 중요한 것은 다음 3개임.

Parameters

실행 시 입력받는 값

Resources

실제로 생성할 AWS 리소스 정의

Outputs

생성 결과로 외부에 보여줄 값

즉, 템플릿은

“입력값을 받아서 리소스를 만들고, 필요한 결과를 출력하는 구조”

로 이해하면 됨.

8.9 Parameters의 의미

Parameters는 템플릿을 더 유연하게 만들어줌.

만약 모든 값을 템플릿에 고정해 두면 재사용성이 떨어짐.

예를 들어 다음 항목은 환경마다 달라질 수 있음.

  • VPC CIDR
  • 인스턴스 타입
  • 키 페어 이름
  • DB 비밀번호
  • 리전별 AMI ID
  • 환경 이름(dev/prod)

이런 값을 Parameters로 분리하면 같은 템플릿을 여러 환경에서 재사용할 수 있음.

즉, Parameters는 템플릿을 “고정된 설계도”가 아니라

입력값에 따라 변형 가능한 설계도로 만들어줌.

8.10 Outputs의 의미

Outputs는 스택 생성 후 필요한 값을 외부에 보여주는 기능임.

예를 들어 다음 값은 생성 후 자주 확인해야 함.

  • ALB DNS 이름
  • EC2 Public IP
  • RDS Endpoint
  • VPC ID
  • Subnet ID

이런 값을 Outputs로 지정해 두면 스택 생성 결과를 쉽게 확인할 수 있음.

즉, Outputs는 생성된 인프라의 중요한 결과값을 정리해주는 기능임.

8.11 CloudFormation의 동작 방식

CloudFormation은 템플릿을 읽고 리소스 간 의존 관계를 파악한 뒤, 순서에 맞게 리소스를 생성함.

예를 들어

  • Subnet은 VPC가 먼저 있어야 생성 가능함
  • EC2는 Security Group과 Subnet이 있어야 생성 가능함
  • NAT Gateway는 Public Subnet과 Elastic IP가 있어야 함

CloudFormation은 이런 관계를 바탕으로 생성 순서를 조정함.

이 의미는 매우 중요함.

CloudFormation은 단순한 스크립트 실행기가 아니라,

리소스 관계를 이해하고 상태를 관리하는 선언형 도구임.

8.12 선언형 자동화와 절차형 자동화

CloudFormation을 설명할 때 종종 중요한 개념이 선언형(Declarative) 과 절차형(Imperative) 의 차이임.

선언형

“무엇을 만들고 싶은가”를 정의함.

예

  • VPC 1개
  • Public Subnet 2개
  • EC2 2대

절차형

“어떤 순서로 어떻게 만들 것인가”를 명령함.

CloudFormation은 선언형 방식에 가까움.

즉 사용자는 원하는 최종 상태를 정의하고, 실제 생성 과정과 순서는 CloudFormation이 관리함.

이 점 때문에 대규모 인프라 자동화에서 매우 유리함.

8.13 CloudFormation 변경 관리

인프라는 한 번 만들고 끝나는 것이 아니라 계속 변경됨.

예

  • 인스턴스 타입 변경
  • 서브넷 추가
  • 태그 수정
  • 보안 그룹 규칙 변경
  • ALB 추가

이때 CloudFormation은 기존 스택과 수정된 템플릿의 차이를 비교하여 필요한 변경을 적용함.

즉, CloudFormation은 단순 생성만 하는 것이 아니라

인프라의 변경 lifecycle까지 관리하는 도구임.

이 점이 IaC 도구로서 중요한 이유임.

8.14 CloudFormation의 한계와 주의점

CloudFormation이 매우 강력한 도구이지만 만능은 아님.

1. 템플릿 복잡도 증가

구조가 커질수록 템플릿이 길고 복잡해짐.

2. 오류 원인 파악이 어려울 수 있음

리소스 간 의존 관계 때문에 실패 원인 분석이 쉽지 않은 경우가 있음.

3. 잘못된 설계가 반복될 수 있음

자동화는 좋은 설계를 빠르게 반복할 수도 있지만, 잘못된 설계도 빠르게 반복할 수 있음.

즉, 자동화가 중요하지만 자동화 이전에 아키텍처 설계 자체가 올바른지가 먼저임.

8.15 Elastic Beanstalk 개요

Elastic Beanstalk는 애플리케이션을 쉽게 배포하고 운영할 수 있도록 도와주는 AWS 서비스임.

쉽게 말하면 다음과 같음.

코드를 올리면,
애플리케이션 실행에 필요한 인프라를 AWS가 비교적 자동으로 구성해 준다.

즉, Beanstalk는

“인프라를 아주 세밀하게 직접 설계하기보다, 애플리케이션 실행 환경을 빠르게 마련하고 싶을 때”

유용한 서비스임.

지원 예시

  • Java
  • Node.js
  • Python
  • PHP
  • .NET
  • Docker

즉, 개발자가 애플리케이션 코드에 더 집중할 수 있게 해주는 관리형 배포 플랫폼에 가까움.

8.16 Elastic Beanstalk의 역할

Beanstalk는 내부적으로 여러 AWS 리소스를 조합해 애플리케이션 실행 환경을 구성함.

예를 들어 상황에 따라 다음이 포함될 수 있음.

  • EC2
  • Auto Scaling
  • Load Balancer
  • Security Group
  • CloudWatch
  • S3

사용자는 직접 각 리소스를 하나씩 만들지 않아도, 비교적 높은 수준의 설정만으로 전체 실행 환경을 구성할 수 있음.

즉, Beanstalk는

애플리케이션 플랫폼 자동화 서비스

라고 보는 것이 적절함.

8.17 Beanstalk가 적합한 경우

1. 빠르게 애플리케이션을 배포하고 싶을 때

복잡한 인프라 세부 설정보다, 실행 환경을 빠르게 준비하는 것이 중요할 때 적합함.

2. 인프라보다 애플리케이션 개발에 집중할 때

개발팀이 인프라 세부 조정보다 코드 배포에 더 집중하고 싶은 경우 유용함.

3. 표준적인 웹 애플리케이션 배포

일반적인 웹앱 구조에서는 충분히 편리한 선택이 될 수 있음.

즉, Beanstalk는 “쉽고 빠른 배포”에 강점이 있음.

8.18 Beanstalk의 한계

Beanstalk는 편리하지만, 아키텍처를 세밀하게 통제하고 싶을 때는 제약이 생길 수 있음.

예를 들어

  • 세부 네트워크 구조를 정교하게 제어하고 싶을 때
  • 복잡한 멀티티어 구성이 필요할 때
  • 리소스를 세밀하게 표준화하고 싶을 때
  • 대규모 엔터프라이즈 IaC 체계에 맞추고 싶을 때

이 경우에는 CloudFormation이나 다른 IaC 도구가 더 적합할 수 있음.

즉, Beanstalk는 편의성이 높은 대신 세밀한 제어력은 상대적으로 낮을 수 있음.

8.19 CloudFormation과 Beanstalk의 차이

이 둘은 종종 같이 언급되지만 역할이 다름.

항목CloudFormationElastic Beanstalk
중심 대상인프라 전체애플리케이션 실행 환경
제어 수준매우 높음비교적 추상화됨
목적리소스 정의와 관리배포 단순화
사용 관점플랫폼/인프라 엔지니어애플리케이션 배포 중심

즉,

  • CloudFormation은 인프라 설계와 표준화에 강함
  • Beanstalk는 애플리케이션 배포 편의성에 강함

으로 구분하면 됨.

8.20 AWS SDK 개요

AWS SDK는 프로그래밍 언어에서 AWS 서비스를 직접 호출할 수 있게 해주는 개발 도구 모음임.

예를 들어 애플리케이션 코드에서 다음 작업을 수행할 수 있음.

  • S3에 파일 업로드
  • DynamoDB에 데이터 저장
  • SQS에 메시지 전송
  • SNS로 알림 발송
  • Lambda 호출
  • EC2 정보 조회

즉, SDK는 콘솔이나 CLI가 아니라 애플리케이션 내부 로직에서 AWS 서비스를 제어하는 수단임.

AWS는 다양한 언어용 SDK를 제공함.

예

  • Python (boto3)
  • Java
  • JavaScript
  • Go
  • .NET
  • PHP

8.21 SDK가 필요한 이유

콘솔은 사람이 직접 조작할 때 쓰고, CLI는 터미널에서 명령할 때 사용함.

하지만 애플리케이션은 사람 손이 아니라 코드 안에서 AWS 서비스를 호출해야 함.

예를 들어 사용자가 웹 페이지에서 이미지를 업로드했다고 가정하면, 애플리케이션은 다음 흐름을 수행할 수 있음.

  • 업로드 파일 수신
  • S3에 저장
  • 저장 위치를 DB에 기록
  • 업로드 완료 메시지 반환

이 흐름은 콘솔이 아니라 코드 안에서 처리되어야 하며, 그때 SDK가 사용됨.

즉, SDK는 애플리케이션과 AWS 서비스 사이의 프로그래밍 인터페이스임.

8.22 SDK와 API의 관계

AWS 서비스는 결국 API를 통해 동작함.

콘솔도 내부적으로는 API를 호출하고, CLI도 API를 호출함.

SDK 역시 마찬가지로 API 호출을 개발자가 쉽게 사용할 수 있도록 감싼 도구임.

즉,

콘솔, CLI, SDK는 모두 결국 AWS API를 사용한다.

차이는 사용 방식임.

  • 콘솔 : 사람이 화면에서 사용
  • CLI : 사람이 터미널에서 사용
  • SDK : 애플리케이션 코드에서 사용

이 구조를 이해하면 AWS 서비스 제어 방식 전체를 체계적으로 볼 수 있음.

8.23 SDK 사용 시 인증 구조

애플리케이션이 SDK로 AWS 서비스를 호출하려면 인증 정보가 필요함.

이때 가장 중요한 원칙은 애플리케이션 코드에 Access Key를 직접 넣지 않는 것임.

운영 환경에서는 보통 IAM Role을 사용함.

예

  • EC2에 IAM Role 연결
  • Lambda 실행 역할 사용
  • ECS Task Role 사용

즉, 애플리케이션은 실행 환경에 부여된 역할을 통해 안전하게 AWS API를 호출해야 함.

이 부분은 자동화와 보안이 만나는 지점이라서 매우 중요함.

8.24 자동화 수준별 구분

자동화를 구조적으로 보면 다음처럼 정리할 수 있음.

인프라 자동화

  • VPC
  • Subnet
  • EC2
  • ALB
  • RDS
  • IAM 일부

대표 도구

  • CloudFormation

플랫폼/배포 자동화

  • 애플리케이션 실행 환경 준비
  • 버전 배포
  • 환경 관리

대표 도구

  • Elastic Beanstalk

애플리케이션 로직 자동화

  • 코드에서 AWS 서비스 호출
  • 비즈니스 흐름에 AWS 기능 포함

대표 도구

  • AWS SDK

이 구분을 명확히 해 두면 학생들이 서비스 역할을 헷갈리지 않음.

8.25 자동화와 운영 품질의 관계

자동화는 단지 “사람 일을 줄여준다”가 아님.

실제로는 운영 품질과 직결됨.

1. 일관된 환경

같은 코드로 같은 환경을 생성하므로 편차가 줄어듦.

2. 빠른 복구

문제가 생긴 환경을 다시 빠르게 재구성할 수 있음.

3. 변경 추적

변경 이력을 코드로 남길 수 있음.

4. 표준화

여러 팀이 같은 기준으로 리소스를 생성할 수 있음.

즉, 자동화는 아키텍처 설계 원칙 중

운영 우수성(Operational Excellence) 과 깊게 연결됨.

8.26 멀티 티어 아키텍처와 자동화의 연결

ARC 과정에서는 최종적으로 멀티 티어 아키텍처를 구성하게 됨.

이때 자동화가 없으면 다음 리소스를 수작업으로 모두 만들어야 함.

  • VPC
  • Subnet
  • Route Table
  • Internet Gateway
  • NAT Gateway
  • Security Group
  • ALB
  • Auto Scaling Group
  • EC2
  • RDS
  • S3

이 구조를 수작업으로 반복 구축하는 것은 매우 비효율적임.

따라서 실제 교육 흐름에서는 자동화를 통해 다음을 가능하게 해야 함.

  • 동일한 실습 환경 반복 생성
  • 학생별 환경 표준화
  • 최종 종합 아키텍처 재현
  • 변경 및 삭제의 일관성 확보

즉, 자동화는 후반부 종합 아키텍처 실습을 가능하게 만드는 핵심 기반임.

8.27 핵심 비교 정리

CloudFormation

  • 인프라를 코드로 정의함
  • 재현성과 표준화에 강함
  • AWS IaC의 대표 도구임

Elastic Beanstalk

  • 애플리케이션 배포와 운영 환경 구성을 단순화함
  • 빠른 웹 애플리케이션 배포에 적합함
  • 세밀한 제어보다는 편의성에 강점이 있음

AWS SDK

  • 애플리케이션 코드에서 AWS 서비스를 직접 호출함
  • S3 업로드, DynamoDB 저장, SQS 전송 같은 기능 구현에 사용함
  • 애플리케이션 로직과 AWS 서비스를 연결하는 핵심 수단임

8.29 한 줄 정리

CloudFormation은 인프라를 코드로 만든다.
Elastic Beanstalk는 애플리케이션 배포를 단순화한다.
AWS SDK는 애플리케이션 코드에서 AWS 서비스를 제어한다.
세 도구는 자동화의 대상과 수준이 서로 다르다.
