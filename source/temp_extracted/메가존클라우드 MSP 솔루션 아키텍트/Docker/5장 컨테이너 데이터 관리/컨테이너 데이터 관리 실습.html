컨테이너 데이터 관리 실습

실습 목표

이 실습을 통해 다음을 직접 확인한다.

  • 컨테이너 데이터가 왜 기본적으로 휘발성인지 이해한다
  • 컨테이너 삭제 시 데이터가 사라지는 상황을 재현한다
  • Bind Mount와 Volume의 차이를 실습으로 비교한다
  • 여러 컨테이너가 동일한 데이터를 공유하는 구조를 이해한다
  • 웹 서버 확장(Scale-out) 시 데이터 관리가 왜 중요한지 체득한다

실습 환경

  • OS: Ubuntu
  • Docker 설치 완료
  • 사용 이미지:
    • busybox
    • nginx:alpine
    • mysql:8.0

실습 1. 컨테이너 데이터의 휘발성 확인

1-1. 컨테이너 내부에 파일 생성

docker run -it --name ct1 busybox sh
mkdir /data
echo "hello container" > /data/test.txt
cat /data/test.txt

1-2. 컨테이너 삭제 후 데이터 확인

exit
docker rm ct1
docker run -it busybox sh
cat /data/test.txt

결과

No such file or directory

핵심 포인트

  • 컨테이너 내부 데이터는 컨테이너 수명과 동일
  • 컨테이너는 데이터 저장소가 아님

실습 2. Bind Mount 기본 사용

2-1. 호스트 디렉터리 준비

mkdir -p ~/bind-test
echo "hello from host" > ~/bind-test/index.html

2-2. Bind Mount로 컨테이너 실행

docker run -it \
  -v ~/bind-test:/data \
  busybox sh
ls /data
cat /data/index.html
echo "created in container" > /data/container.txt
exit

호스트에서 확인:

ls ~/bind-test

핵심 포인트 (Bind Mount)

  • 호스트 디렉터리와 컨테이너 디렉터리가 1:1로 연결
  • 즉시 반영
  • 호스트 경로 의존성 큼

👉 개발/실습 환경에 적합

⭐ 실습 3. 2개의 웹서버에서 Bind Mount 공유하기 (핵심 실습)

실습 시나리오

하나의 웹 콘텐츠 디렉터리를두 개의 웹 서버 컨테이너가 동시에 공유한다.

이는 다음 상황을 가정한다.

  • 웹 서버 수평 확장(Scale-out)
  • 정적 파일을 여러 서버에서 동일하게 제공

3-1. 호스트 웹 콘텐츠 디렉터리 준비

mkdir -p ~/web-content
cat <<EOF > ~/web-content/index.html
<h1>Hello from Shared Bind Mount</h1>
<p>Initial Content</p>
EOF

3-2. 첫 번째 웹 서버 실행 (web1)

docker run -d \
  --name web1 \
  -p 8081:80 \
  -v ~/web-content:/usr/share/nginx/html \
  nginx:alpine

3-3. 두 번째 웹 서버 실행 (web2)

docker run -d \
  --name web2 \
  -p 8082:80 \
  -v ~/web-content:/usr/share/nginx/html \
  nginx:alpine

3-4. 각 웹 서버 접속 확인

curl http://127.0.0.1:8081
curl http://127.0.0.1:8082

기대 결과

  • 두 요청 모두 동일한 HTML 출력

3-5. 콘텐츠 수정 → 실시간 반영 확인

호스트에서:

cat <<EOF > ~/web-content/index.html
<h1>Updated Content</h1>
<p>Both web servers see this immediately</p>
EOF

다시 접속:

curl http://127.0.0.1:8081
curl http://127.0.0.1:8082

핵심 확인

  • 한 곳에서 수정 → 두 컨테이너에 즉시 반영
  • 데이터는 컨테이너가 아니라 외부에 존재

실습 4. Bind Mount의 한계

문제점 정리

  • 호스트 경로 의존
  • 실수 시 호스트 파일 손상 가능
  • 다른 서버로 옮기기 어려움
  • 컨테이너 오케스트레이션 환경(K8s)과 직접적 호환성 낮음

👉 그래서 운영 환경에서는 Volume 사용 권장

실습 5. Docker Volume 사용하기

5-1. Volume 생성

docker volume create myvol

5-2. Volume 사용 컨테이너 실행

docker run -it \
  --name vol1 \
  -v myvol:/data \
  busybox sh
echo "hello volume" > /data/vol.txt
exit

5-3. 컨테이너 삭제 후 재확인

docker rm vol1
docker run -it -v myvol:/data busybox sh
cat /data/vol.txt

핵심 포인트 (Volume)

  • 컨테이너 수명과 데이터 수명 분리
  • Docker가 위치/관리 책임
  • 운영 환경 표준 방식

실습 6. 데이터베이스 컨테이너와 Volume

6-1. Volume 없이 MySQL 실행

docker run -d \
  --name mysql1 \
  -e MYSQL_ROOT_PASSWORD=pass \
  mysql:8.0
docker exec -it mysql1 mysql -uroot -ppass
CREATE DATABASE testdb;
EXIT;
docker rm -f mysql1

→ 데이터 소멸

6-2. Volume 사용 MySQL

docker volume create mysql-data
docker run -d \
  --name mysql2 \
  -e MYSQL_ROOT_PASSWORD=pass \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0
docker exec -it mysql2 mysql -uroot -ppass
CREATE DATABASE prod;
EXIT;
docker rm -f mysql2
docker run -d \
  --name mysql2 \
  -e MYSQL_ROOT_PASSWORD=pass \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0

→ 데이터 유지 확인

핵심 요약

  • 컨테이너는 상태를 가지지 않는다
  • 데이터는 컨테이너 외부에서 관리
  • Bind Mount:
    • 개발/실습에 매우 유용
    • 다중 컨테이너 공유 가능
    • 운영 환경에서는 주의
  • Volume:
    • 운영 환경 표준
    • 컨테이너 수명과 데이터 수명 분리
