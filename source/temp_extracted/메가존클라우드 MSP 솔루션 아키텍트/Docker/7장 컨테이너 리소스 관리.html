7장. 컨테이너 리소스 관리

CPU · Memory · cgroup 기반 제어

7장 학습 목표

  • 컨테이너가 호스트 자원을 공유한다는 의미를 이해한다.
  • cgroup이 실제 리소스 제어 주체임을 설명할 수 있다.
  • CPU quota/period 구조를 이해한다.
  • Memory 제한과 OOM 발생 원리를 설명할 수 있다.
  • swap 설정이 성능에 미치는 영향을 이해한다.
  • 운영 환경에서 리소스 제한이 왜 필수인지 판단할 수 있다.

7.1 왜 컨테이너에 리소스 제한이 필요한가

7.1.1 컨테이너는 가볍지만 기본적으로 제한이 없다

컨테이너는:

  • 커널 공유
  • 하이퍼바이저 없음
  • 빠른 실행
  • 낮은 오버헤드

하지만 기본 상태에서는:

  • CPU 무제한
  • Memory 무제한
  • PID 무제한

즉,

제한을 설정하지 않으면 호스트 전체 자원을 사용할 수 있다.

7.1.2 실제 장애 시나리오

사례 1 – CPU 폭주

docker run -d ubuntu yes > /dev/null

CPU 100% 점유

다른 서비스 응답 지연 발생

사례 2 – 메모리 누수

docker run -it ubuntu python3
a = "x" * 500 * 1024 * 1024   => 약 500M 메모리 필요

메모리 무제한 사용 →

호스트 OOM → 전체 서비스 중단

핵심 교훈

컨테이너는 가볍지만 공짜가 아니다.

반드시 제한을 설정해야 한다.

7.2 cgroup(Control Group) 구조

7.2.1 cgroup이란

Linux 커널 기능

프로세스 그룹 단위로 자원 제한 가능

제어 가능 자원:

  • CPU
  • Memory
  • Block I/O
  • PIDs
  • HugePages

7.2.2 Docker 내부 동작

컨테이너 실행 시:

  1. 전용 cgroup 생성
  1. 해당 컨테이너 프로세스 묶음
  1. 설정값을 cgroup 파일에 기록

7.2.3 직접 확인 (cgroup v2 기준)

컨테이너 실행 후:

docker inspect <컨테이너ID> --format '{{.Id}}'

호스트에서:

cd /sys/fs/cgroup/
ls

메모리 확인:

cat memory.max
cat memory.current

CPU 확인:

cat cpu.max

7.3 CPU 리소스 제한

7.3.1 CPU는 “시간”을 제한한다

Docker는 CFS(Completely Fair Scheduler)를 사용한다.

기본 기준 시간:

100ms (0.1초)

이를 period라고 한다.

7.3.2 quota / period 구조

공식:

quota = period × cpus 값

기본 period = 100ms

예 --cpus=1

  • 100ms 동안 100ms 사용 가능
  • 1코어 100%

예 --cpus=0.5

  • 100ms 동안 50ms 사용 가능
  • 1코어 50%

예 --cpus=2

  • 100ms 동안 200ms 사용 가능
  • 2코어 100%

7.3.3 실습 – CPU 50% 제한

docker run -d --name cpu_test --cpus=0.5 ubuntu sleep infinity

부하 발생:

docker exec -it cpu_test bash
yes > /dev/null

호스트에서:

docker stats
또는
htop

→ 약 50% 근처 확인

7.3.4 CPU Shares (상대 우선순위)

docker run -d --cpu-shares=512 nginx
  • 기본값 1024
  • 경쟁 상황에서만 의미
  • 단독 실행 시 효과 없음

7.3.5 cpuset-cpus (코어 고정)

docker run -d --cpuset-cpus="0" nginx
  • 특정 코어만 사용
  • NUMA(Non-Uniform Memory Access) 환경에서 중요

7.4 Memory 리소스 제한

7.4.1 메모리는 가장 위험한 자원

CPU는 느려질 뿐

Memory는 넘치면 프로세스 종료

7.4.2 기본 메모리 제한

docker run -d --memory=256m ubuntu sleep infinity

의미:

  • 최대 RAM 256MB
  • 초과 시 reclaim 후 OOM

7.4.3 swap 설정

swap 허용

docker run -d \
  --memory=256m \
  --memory-swap=512m \
  ubuntu
  • RAM 256MB
  • RAM+swap 총합 512MB

swap 완전 금지

docker run -d \
  --memory=256m \
  --memory-swap=256m \
  ubuntu

→ swap 사용 불가

7.4.4 실습 – OOM 유도

docker run -d --name mem_test --memory=100m ubuntu sleep infinity
docker exec -it mem_test bash
apt update && apt install -y stress
stress --vm 1 --vm-bytes 200M --timeout 10

확인:

docker ps -a

→ Exited (137)

7.4.5 Exit Code 137 의미

128 + 9 (SIGKILL)

OOM Killer가 프로세스 강제 종료

7.5 리소스 확인 명령

docker stats

docker stats
  • CPU %
  • Memory / Limit
  • 네트워크
  • Block I/O

docker inspect

docker inspect mem_test

확인 항목:

  • CpuQuota
  • CpuPeriod
  • Memory

7.6 실행 중 리소스 변경

docker update --cpus=0.3 --memory=200m mem_test
  • 재시작 없이 즉시 적용

운영 중 긴급 대응에 매우 유용

7.7 장애 분석 실습

OOM 발생 로그 확인

dmesg | grep -i oom

또는

journalctl -k | grep -i oom

7.8 운영 설계 기준

기본 원칙

  • 모든 컨테이너에 Memory 제한 설정
  • CPU quota 설정
  • swap 정책 명확히
  • DB/Cache는 여유 있게

권장 예시

웹 서버:

CPU 0.5
Memory 512MB

DB 서버:

CPU 2
Memory 4GB

7장 핵심 정리

  • 컨테이너는 프로세스 집합
  • cgroup이 실제 제어 주체
  • CPU는 시간 기반 quota 제한
  • 기본 기준 시간은 100ms
  • Memory 초과 시 OOM Killer 작동
  • swap 허용 여부는 성능에 큰 영향
  • 운영 환경에서는 리소스 제한이 필수
