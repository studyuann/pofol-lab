2장. Standard 모드와 Autopilot 모드

1. 장 개요

GKE는 클러스터 전체를 Autopilot 모드 또는 Standard 모드로 운영할 수 있고, 이 선택은 노드 관리, 스케일링, 보안 기본값, 클러스터 설정 변경 가능 범위, 비용 모델, 운영 책임에 직접 영향을 준다.

2. 학습 목표

  • GKE Standard와 Autopilot의 기본 차이를 설명할 수 있음
  • 두 모드의 운영 책임 분배를 비교할 수 있음
  • 노드 관리, 보안 기본 설정, 확장, 비용 모델 관점에서 차이를 설명할 수 있음
  • 어떤 상황에서 Autopilot이 적합하고 어떤 상황에서 Standard가 적합한지 판단할 수 있음
  • Standard 클러스터에서 Autopilot 워크로드를 실행하는 개념을 설명할 수 있음
  • 샘플 워크로드 배포 시 어떤 모드를 선택할지 근거를 들어 설명할 수 있음

3. 선수 지식

  • Kubernetes 기본 오브젝트
  • kubectl 사용 경험
  • 노드와 스케줄링 기본 개념
  • 온프레미스 Kubernetes 또는 EKS 경험
  • GCP 기본 네트워크와 IAM 개념

4. 핵심 키워드

  • GKE Standard
  • GKE Autopilot
  • Managed Infrastructure
  • Node Management
  • ComputeClass
  • Cluster Mode
  • Security Defaults
  • Scaling
  • Responsibility Split
  • Cost Model

5. GKE 운영 모드란 무엇인가

Google Cloud는 GKE 클러스터를 운영할 때 Autopilot 또는 Standard 모드를 선택하게 한다.

쉽게 이해하면

  • Autopilot: “플랫폼이 더 많이 관리하는 GKE”
  • Standard: “운영자가 더 많이 제어하는 GKE”

Autopilot은 Google이 대부분의 프로덕션 워크로드에 적합하도록 최적화한 모드이고, Kubernetes 매니페스트를 기준으로 컴퓨팅 리소스를 프로비저닝한다. 반면 Standard는 노드풀, 노드 설정, 보안 정책, 확장 방식 등을 사용자가 직접 더 많이 구성하는 모드다.

6. Standard 모드란 무엇인가

Standard 모드는 GKE에서 더 많은 제어와 유연성을 제공하는 운영 모드다.

Standard 클러스터에서는 사용자가 클러스터 인프라를 제어하고, 대부분의 설정을 변경할 수 있으며, 노드풀을 직접 구성하고 노드 설정, 보안 정책, 스케일링을 직접 설정한다.

6.1 Standard 모드의 특징

  • 사용자가 노드풀을 직접 설계할 수 있음
  • 노드 구성과 머신 타입 선택의 유연성이 큼
  • 보안 정책, 제약, 네트워크 설정을 더 세밀하게 조정할 수 있음
  • 운영 부담이 더 큼
  • 필요 시 일부 워크로드만 Autopilot 방식으로 혼합 운영할 수 있음

6.2 어떤 조직에 잘 맞는가

  • 이미 Kubernetes 운영 경험이 충분한 조직
  • 노드 구조를 세밀하게 통제해야 하는 환경
  • 특정 하드웨어, 특정 스케줄링 정책, 세밀한 클러스터 설정이 중요한 경우
  • 온프레미스 Kubernetes와 유사한 통제 수준을 유지하고 싶은 경우

7. Autopilot 모드란 무엇인가

Autopilot은 Google이 노드 인프라, 스케일링, 보안 기본 구성, 사전 설정된 기능들을 더 많이 관리하는 GKE 운영 모드다.

Autopilot은 대부분의 프로덕션 워크로드를 실행하도록 최적화되어 있으며, 사용자가 워크로드를 배포하면 GKE가 리소스와 하드웨어를 프로비저닝·구성·관리한다. 또한 가장 간소화된 환경을 위해 Autopilot 클러스터 사용을 권장한다.

7.1 Autopilot 모드의 특징

  • Google이 노드와 인프라 관리를 더 많이 수행함
  • 자동 스케일링과 효율적 스케줄링이 강하게 통합됨
  • 보안 기본값과 권장 구성이 기본 적용됨
  • 운영자가 인프라 세부 설정을 직접 손대는 범위가 줄어듦
  • 대부분의 일반적인 프로덕션 워크로드를 빠르게 운영하기 좋음

7.2 어떤 조직에 잘 맞는가

  • 플랫폼팀 인력이 제한적이고 운영 자동화를 더 활용하고 싶은 조직
  • “노드 운영”보다 “서비스 운영”에 집중하고 싶은 환경
  • 표준적인 웹 애플리케이션, API 서비스, 일반적인 마이크로서비스 워크로드
  • 운영 표준화와 보안 기본값을 빠르게 적용하고 싶은 경우

8. Standard와 Autopilot의 가장 중요한 차이

Autopilot과 Standard의 가장 큰 차이를 인프라 구성 자동화 수준과 운영 책임 범위다.

8.1 운영 책임 분배

Standard

  • 클러스터 운영자 책임이 큼
  • 노드와 노드풀 설계에 깊이 관여
  • 클러스터 설정 변경 자유도가 큼

Autopilot

  • GKE가 더 많은 인프라 운영을 담당
  • 사용자는 워크로드 명세와 서비스 운영에 집중
  • 제어권은 줄지만 운영 단순성이 커짐

8.2 보안 기본값

Autopilot은 Google이 보안 모범사례와 제약을 기본 적용하는 방향이 강하다.

8.3 유연성과 제약

Standard는 세밀한 제어가 가능하지만, 그만큼 사용자가 더 많은 설계와 운영 책임을 진다.

Autopilot은 제약이 있지만, 그 제약은 운영 단순성과 표준화를 얻기 위한 교환이라고 보면 된다.

9. 비용 관점 차이

9.1 Standard

  • 노드풀과 노드 단위 자원 설계가 중요함
  • 용량을 미리 잡는 사고가 더 익숙함
  • 사용자는 노드 활용률 최적화에 더 신경 써야 함

9.2 Autopilot

  • 워크로드 명세를 기준으로 리소스가 더 직접적으로 연결됨
  • 과도한 프로비저닝을 줄이는 방향이 강함
  • “클러스터 인프라 관리”보다 “워크로드 요청량 설계”가 더 중요해짐

10. Autopilot을 선택하면 좋은 경우

아래와 같은 경우에는 Autopilot이 매우 잘 맞는다.

대표 시나리오

  • 일반적인 웹 서비스, API 서버, 마이크로서비스
  • 플랫폼팀 규모가 작고, 애플리케이션 팀 생산성이 더 중요한 경우
  • 빠르게 안전한 기본값을 적용하고 싶은 경우
  • 표준적인 Kubernetes 워크로드를 많이 운영하는 경우
  • 노드 운영보다 배포와 서비스 운영이 중요한 경우

11. Standard를 선택하면 좋은 경우

아래와 같은 경우에는 Standard가 더 적합할 수 있다.

대표 시나리오

  • 노드풀을 세밀하게 분리·튜닝해야 하는 경우
  • 특정 하드웨어나 특수 스케줄링 요구가 있는 경우
  • 클러스터 보안과 정책을 직접 강하게 제어하고 싶은 경우
  • 기존 온프레미스 Kubernetes 운영 감각을 더 많이 유지하고 싶은 경우
  • GKE의 유연성을 최대한 활용하고 싶은 경우

12. 장 요약

  • GKE는 클러스터 운영 모드로 Autopilot 과 Standard 를 제공한다.
  • Autopilot은 Google이 노드, 스케일링, 보안 기본 구성, 인프라 운영을 더 많이 관리하는 모드다. 일반적으로 세밀한 제어가 꼭 필요하지 않다면 Google은 Autopilot 사용을 권장한다.
  • Standard는 사용자가 노드풀, 보안 정책, 스케일링, 클러스터 설정을 더 많이 직접 제어하는 모드다.
  • 두 모드의 가장 큰 차이는 운영 책임 분배와 인프라 구성 자동화 수준이다.
  • Standard 클러스터에서는 ComputeClass를 통해 일부 워크로드를 Autopilot 방식으로 실행할 수도 있다.
  • Autopilot은 릴리스 채널 등록이 필수이며, 버전 운영과 유지보수 전략도 더 플랫폼 중심으로 흘러간다.

Autopilot은 운영 자동화와 표준화에 강하고, Standard는 유연성과 제어에 강하다.
