1장. GCP 개요와 글로벌 인프라 구조

1. 장 개요

이 장에서는 Google Cloud Platform(GCP)의 인프라 구조와 운영 관점을 살펴본다.

또한 AWS와 비교했을 때 어떤 차이가 있는지도 함께 이해한다.

처음 GCP를 보면 다음과 같은 점에서 AWS와 비슷해 보인다.

  • 컴퓨팅 서비스가 있음
  • 스토리지 서비스가 있음
  • 네트워크 서비스가 있음
  • 데이터베이스 서비스가 있음

즉, 겉으로 보면 두 플랫폼 모두 종합 클라우드 서비스처럼 보인다.

하지만 실제로 콘솔에서 리소스를 생성하고 운영하기 시작하면 체감 방식이 다르게 느껴진다.

이 차이는 단순히 서비스 이름 때문이 아니라, 클라우드를 구성하고 관리하는 기본 구조와 설계 철학의 차이에서 나온다.

AWS를 먼저 학습한 경우 보통 다음 개념이 익숙하다.

  • Account 중심 운영
  • Region 중심 리소스 배치
  • VPC를 리전 단위 네트워크로 이해
  • 세부 서비스를 조합해 아키텍처 설계

반면 GCP는 다음 개념이 더 강하게 드러난다.

  • Project 중심 운영
  • 글로벌 네트워크 기반 인프라
  • 글로벌 VPC 개념
  • 조직 계층 구조를 통한 자원 통제

즉, GCP도 클라우드 서비스이므로 제공 기능의 큰 범주는 AWS와 유사하다.

다만 리소스를 어디에 두고, 어떤 단위로 운영하며, 어떤 구조로 통제할 것인가에 대한 사고방식이 다르다고 이해하면 된다.

이 장의 목적은 단순히 GCP 서비스 이름을 나열하는 데 있지 않다.

핵심은 GCP를 어떤 틀로 이해해야 하는지를 잡는 데 있다.

2. 학습 목표

  • GCP의 전체 서비스 구조를 큰 범주로 설명할 수 있음
  • Region, Zone, Multi-region의 의미를 설명할 수 있음
  • GCP의 글로벌 인프라 철학을 AWS와 비교해 설명할 수 있음
  • Organization, Folder, Project의 의미를 설명할 수 있음
  • Project가 GCP의 핵심 운영 단위인 이유를 설명할 수 있음
  • GCP VPC가 글로벌 리소스라는 의미를 설명할 수 있음

3. 선수 지식

  • 클라우드 기본 개념
  • 가상머신, 네트워크, 스토리지, 데이터베이스의 기본 개념
  • AWS의 Account, Region, AZ, VPC 개념
  • 콘솔에서 기본 리소스를 생성해 본 경험

4. 핵심 키워드

  • Google Cloud
  • Region
  • Zone
  • Multi-region
  • Global Infrastructure
  • Resource Hierarchy
  • Organization
  • Folder
  • Project
  • Global VPC

5. GCP란 무엇인가

GCP는 Google이 자사 서비스를 운영하면서 축적한 인프라와 플랫폼 기술을 외부에 제공하는 클라우드 서비스다.

쉽게 말하면 Google이 대규모 서비스를 운영하기 위해 사용해 온 기술 기반을 기업과 개발자도 사용할 수 있도록 서비스화한 것이다.

GCP는 다음과 같은 영역의 서비스를 제공한다.

  • 컴퓨팅
  • 네트워킹
  • 스토리지
  • 데이터베이스
  • 보안
  • 운영 및 모니터링
  • 데이터 분석
  • 인공지능 및 머신러닝
  • 컨테이너 및 서버리스

즉, GCP 역시 AWS와 마찬가지로 종합 클라우드 플랫폼이다.

다만 GCP를 설명할 때 자주 강조되는 특징이 있다.

  • 글로벌 백본 네트워크 기반
  • 프로젝트 중심 운영
  • VPC의 글로벌 설계
  • 데이터 분석, AI, 컨테이너 분야의 강점
  • 비교적 일관된 사용자 경험 지향

여기서 중요한 것은 어느 플랫폼이 더 낫다는 비교가 아니다.

핵심은 설계 철학의 차이다.

AWS와 GCP의 감각 차이

AWS는 매우 많은 서비스와 세부 옵션을 제공하고, 이를 조합해서 아키텍처를 설계하는 느낌이 강하다.

반면 GCP는 글로벌 네트워크와 프로젝트 중심 구조를 바탕으로, 비교적 일관된 틀 안에서 자원을 배치하는 느낌이 강하다.

즉, AWS는 세밀하게 분화된 서비스를 조합하는 플랫폼처럼 느껴질 수 있고,

GCP는 글로벌 구조 위에서 일관되게 자원을 운영하는 플랫폼처럼 느껴질 수 있다.

6. GCP의 서비스 범주 이해

GCP에는 많은 서비스가 존재한다.

하지만 처음 학습할 때는 개별 서비스 이름을 외우기보다 큰 범주로 나누어 이해하는 것이 중요하다.

6.1 컴퓨팅

컴퓨팅은 애플리케이션을 실제로 실행하는 영역이다.

대표 서비스는 다음과 같다.

  • Compute Engine
  • Google Kubernetes Engine(GKE)
  • Cloud Run
  • App Engine

Compute Engine

가상머신(VM)을 생성해서 사용하는 서비스다.

운영체제, CPU, 메모리, 디스크, 네트워크 인터페이스 등을 직접 구성할 수 있다.

AWS의 EC2와 가장 유사하다.

GKE

Google Kubernetes Engine의 약자다.

쿠버네티스 클러스터를 관리형으로 운영할 수 있게 해주는 서비스다.

AWS의 EKS와 비교할 수 있다.

Cloud Run

컨테이너 이미지를 기반으로 애플리케이션을 실행하는 서버리스 서비스다.

인프라 관리보다 애플리케이션 실행 자체에 집중할 수 있다.

App Engine

코드 중심으로 애플리케이션을 배포하고 운영하는 플랫폼 서비스다.

AWS 비교

  • EC2 ↔ Compute Engine
  • EKS ↔ GKE
  • ECS Fargate / App Runner ↔ Cloud Run

이 과정에서는 주로 Compute Engine 중심으로 접근하면 된다.

6.2 네트워킹

네트워킹은 클라우드 내부와 외부의 통신 구조를 설계하는 영역이다.

대표 서비스는 다음과 같다.

  • VPC
  • Cloud Load Balancing
  • Cloud DNS
  • Cloud VPN
  • Interconnect
  • Firewall Rules

VPC

클라우드 안에서 네트워크를 구성하는 기본 단위다.

IP 대역, 서브넷, 라우팅, 방화벽 정책 등이 이 구조를 기반으로 동작한다.

Cloud Load Balancing

트래픽을 여러 백엔드 인스턴스나 서비스로 분산하는 로드밸런서 서비스다.

Cloud DNS

도메인 이름을 IP 주소와 연결하는 DNS 서비스다.

Cloud VPN

온프레미스와 GCP, 또는 다른 클라우드와 GCP를 VPN으로 연결할 때 사용한다.

Interconnect

전용선 기반의 안정적인 네트워크 연결이 필요할 때 사용하는 서비스다.

Firewall Rules

트래픽 허용 및 차단 정책을 정의하는 보안 제어 수단이다.

AWS 비교

  • VPC ↔ VPC
  • ELB ↔ Cloud Load Balancing
  • Route 53 ↔ Cloud DNS
  • Site-to-Site VPN ↔ Cloud VPN

여기서 가장 중요한 포인트는 GCP VPC는 글로벌 리소스라는 점이다.

6.3 스토리지

스토리지는 데이터를 저장하는 영역이다.

대표 서비스는 다음과 같다.

  • Cloud Storage
  • Persistent Disk
  • Filestore

Cloud Storage

객체 스토리지 서비스다.

파일, 이미지, 로그, 백업 파일, 정적 웹 콘텐츠 등을 저장할 때 사용한다.

AWS의 S3와 유사하다.

Persistent Disk

VM에 연결하는 블록 스토리지다.

운영체제 디스크나 애플리케이션 데이터 디스크로 사용한다.

AWS의 EBS와 유사하다.

Filestore

공유 파일 시스템이 필요할 때 사용하는 관리형 파일 스토리지 서비스다.

AWS의 EFS와 비교할 수 있다.

AWS 비교

  • S3 ↔ Cloud Storage
  • EBS ↔ Persistent Disk
  • EFS ↔ Filestore

6.4 데이터베이스

데이터베이스는 구조화된 데이터를 저장하고 관리하는 영역이다.

대표 서비스는 다음과 같다.

  • Cloud SQL
  • AlloyDB
  • Firestore
  • Bigtable

Cloud SQL

관리형 관계형 데이터베이스 서비스다.

MySQL, PostgreSQL, SQL Server 등을 운영할 수 있다.

AWS의 RDS와 유사하다.

AlloyDB

PostgreSQL 호환 고성능 데이터베이스 서비스다.

고성능 처리와 확장성이 필요한 환경에서 자주 사용된다.

Firestore

문서형 NoSQL 데이터베이스다.

유연한 데이터 구조가 필요한 애플리케이션에서 많이 사용한다.

Bigtable

대규모 분산 NoSQL 데이터 저장소다.

매우 큰 규모의 데이터 처리와 고성능 읽기/쓰기가 중요한 환경에서 사용한다.

AWS 비교

  • RDS ↔ Cloud SQL
  • Aurora ↔ AlloyDB 일부 비교 가능
  • DynamoDB ↔ Firestore 또는 Bigtable을 용도에 따라 비교 가능

6.5 운영 및 모니터링

운영 영역은 시스템 상태를 관찰하고, 로그를 분석하고, 장애를 탐지하는 데 사용된다.

대표 서비스는 다음과 같다.

  • Cloud Monitoring
  • Cloud Logging

AWS 비교

  • CloudWatch ↔ Cloud Monitoring / Cloud Logging

AWS에서는 CloudWatch로 묶어 생각하는 경우가 많지만,

GCP에서는 다음처럼 나누어 이해하면 쉽다.

  • 메트릭, 상태, 알림 중심 → Cloud Monitoring
  • 로그 수집, 조회, 분석 중심 → Cloud Logging

6.6 보안 및 거버넌스

보안과 거버넌스는 권한, 정책, 감사, 조직 관리와 관련된 영역이다.

대표 서비스는 다음과 같다.

  • IAM
  • Resource Manager
  • Organization Policy
  • Cloud Audit Logs

AWS 비교

  • IAM ↔ IAM
  • AWS Organizations ↔ Organization / Folder / Project 구조
  • SCP ↔ Organization Policy 일부 비교 가능

이 영역에서 가장 중요한 개념은 리소스 계층 구조(Resource Hierarchy)다.

GCP에서는 리소스를 생성하는 것만이 아니라, 조직 구조 안에 배치하고 그 구조를 따라 권한과 정책을 상속시키는 방식으로 운영한다.

7. GCP 글로벌 인프라 구조

GCP를 이해할 때 반드시 알아야 할 개념은 다음 네 가지다.

  • Region
  • Zone
  • Multi-region
  • Global Infrastructure

이 개념들은 단순 용어가 아니라,

리소스를 어디에 배치하고 어떤 방식으로 고가용성을 설계할지 결정하는 기준이 된다.

7.1 Region이란 무엇인가

Region은 Google Cloud 리소스를 배치하는 지리적으로 분리된 영역이다.

예시는 다음과 같다.

  • asia-northeast3
  • us-central1
  • europe-west1

하나의 Region은 여러 개의 Zone으로 구성된다.

Region이 필요한 이유

  • 사용자와 가까운 위치에 서비스를 배치해 지연시간을 줄이기 위해
  • 국가나 지역별 데이터 저장 요구사항을 반영하기 위해
  • 장애 도메인을 분리하기 위해
  • 운영 환경과 재해복구 환경을 나누기 위해

즉, Region은 서울, 도쿄, 오하이오, 프랑크푸르트처럼

클라우드 자원을 배치하는 큰 지리적 권역으로 이해하면 된다.

AWS 비교

AWS도 Region 개념을 사용하므로 큰 틀에서는 유사하다.

다만 GCP는 리전 자체보다 글로벌 네트워크 위에서 리전이 어떻게 연결되고 활용되는가를 더 강하게 의식하게 만든다.

7.2 Zone이란 무엇인가

Zone은 Region 내부의 배치 단위이자 장애 격리 단위다.

예시는 다음과 같다.

  • asia-northeast3-a
  • asia-northeast3-b
  • asia-northeast3-c

즉, 하나의 Region 안에 여러 개의 Zone이 존재한다.

Zone이 중요한 이유

Zone은 단순한 하위 구역이 아니다.

실제 장애 격리와 배치 전략에서 매우 중요한 역할을 한다.

예를 들어 VM을 하나의 Zone에만 배치하면 해당 Zone에 장애가 발생했을 때 서비스 가용성이 떨어질 수 있다.

반면 여러 Zone에 분산 배치하면 하나의 Zone 장애가 전체 서비스 장애로 이어질 가능성을 줄일 수 있다.

AWS 비교

AWS에서는 Availability Zone(AZ)이라고 부른다.

GCP에서는 Zone이라고 부른다.

  • AWS: Region / Availability Zone
  • GCP: Region / Zone

개념은 거의 유사하지만, 명칭 차이 때문에 처음에는 혼동하기 쉽다.

7.3 Multi-region이란 무엇인가

Multi-region은 여러 Region에 걸쳐 서비스를 운영하거나 데이터를 분산 저장하는 개념이다.

즉, 하나의 리전에만 의존하지 않고 여러 지역을 고려하는 구조다.

Multi-region이 필요한 경우

  • 전 세계 사용자를 대상으로 서비스를 제공할 때
  • 특정 리전 장애에 대비해야 할 때
  • 데이터 복제와 재해복구 전략이 필요할 때
  • 여러 지역에서 일정한 성능을 제공해야 할 때

핵심 포인트

모든 서비스가 동일한 방식으로 Multi-region을 제공하는 것은 아니다.

  • 어떤 서비스는 글로벌 단위로 동작함
  • 어떤 서비스는 리전 기반임
  • 어떤 서비스는 멀티리전 옵션을 제공함

따라서 GCP를 설계할 때는 항상 이 서비스가 글로벌인지, 리전인지, 존인지를 먼저 확인해야 한다.

7.4 Global Infrastructure의 의미

GCP를 설명할 때 자주 나오는 표현이 글로벌 인프라다.

이 말은 단순히 전 세계에 데이터센터가 많다는 의미만은 아니다.

실제로는 다음과 같은 뜻을 가진다.

  • Google의 글로벌 네트워크를 기반으로 서비스가 동작함
  • 일부 네트워크 자원은 특정 리전이 아니라 글로벌 범위에서 설계됨
  • 로드밸런싱, 백엔드 연결, 멀티리전 서비스 구성에서 이 장점이 드러남

쉽게 말해 AWS는 처음 학습할 때 리전 중심으로 인프라를 바라보는 감각이 강하다.

반면 GCP는 글로벌 구조 안에서 리전과 서비스가 배치된다는 감각이 더 강하다.

8. GCP 리소스 계층 구조

GCP를 이해할 때 서비스 목록보다 먼저 알아야 할 것이 리소스 계층 구조다.

이 구조를 이해하지 못하면 다음 질문에 답하기 어렵다.

  • 권한은 어디에 주는가
  • 프로젝트는 어떻게 나누는가
  • 조직 정책은 어디에 적용하는가
  • 비용과 운영 경계는 어디서 구분하는가

GCP는 리소스를 계층 구조 안에 배치한다.

그리고 그 계층을 따라 정책과 권한이 상속된다.

기본 구조는 다음과 같다.

  • Organization
    • Folder
      • Project
        • Resources

즉, 실제 리소스는 대부분 Project 안에 생성되지만,

그 위에 Organization과 Folder라는 관리 계층이 존재한다.

8.1 Organization

Organization은 GCP 리소스 계층의 최상위 관리 단위다.

쉽게 말하면 회사 전체, 기관 전체, 학교 전체를 대표하는 최상위 컨테이너다.

역할

  • 모든 프로젝트를 감싸는 최상위 루트 역할
  • 조직 차원의 정책 적용
  • 폴더와 프로젝트를 관리하는 기준점
  • 중앙 통제와 거버넌스의 출발점

8.2 Folder

Folder는 Organization 아래에서 프로젝트를 논리적으로 묶는 중간 계층이다.

부서, 팀, 환경, 목적에 따라 프로젝트를 그룹화할 때 사용한다.

사용하는 이유

프로젝트가 많아지면 Project만 나열해서는 관리가 어렵다.

그래서 다음과 같은 기준으로 묶는다.

  • 부서별 구분
  • 팀별 구분
  • 개발/운영 환경 구분
  • 공통 인프라와 서비스별 구분

예시 구조

  • Organization
    • 교육사업부
      • dev
      • prod
    • 플랫폼팀
      • 공통네트워크
      • 보안
    • 데이터팀
      • 분석
      • 백업

Folder에도 권한과 정책을 적용할 수 있고, 이 설정은 하위 Project로 상속될 수 있다.

즉, Folder는 단순 분류용이 아니라 운영과 정책의 중간 단위다.

8.3 Project

Project는 GCP에서 가장 중요한 실질 운영 단위다.

대부분의 리소스는 특정 Project 안에 생성된다.

또한 다음 요소도 Project와 강하게 연결된다.

  • API 활성화
  • IAM 권한
  • 비용 집계
  • 서비스 사용 이력
  • 리소스 생성과 삭제
  • 쿼터 관리

왜 중요한가

AWS에서는 Account가 강한 운영 경계다.

하지만 GCP에서는 Project가 훨씬 자주 등장하는 핵심 경계다.

즉, GCP에서는 다음 질문이 매우 중요하다.

  • 지금 어느 Project에서 작업 중인가
  • 이 API는 어느 Project에서 활성화했는가
  • 이 VM은 어느 Project에 생성되는가
  • 비용은 어느 Project에 집계되는가

AWS 비교

  • AWS: Account 중심 운영 경계
  • GCP: Project 중심 운영 경계

AWS에서는 환경 분리를 위해 계정을 여러 개 사용하는 경우가 많고,

GCP에서는 하나의 Organization 아래에 여러 Project를 두고 운영 경계를 나누는 경우가 많다.

8.4 권한 상속 구조

GCP는 상위 계층에서 부여한 권한과 정책이 하위 계층으로 상속될 수 있다.

즉, 권한은 다음 위치에 부여할 수 있다.

  • Organization
  • Folder
  • Project

이 구조가 중요한 이유는 권한을 사용자마다 개별적으로 부여하는 방식만으로는 관리가 매우 복잡해지기 때문이다.

따라서 GCP에서는 다음 관점으로 생각해야 한다.

  • 어느 조직 단위에
  • 어떤 역할(Role)을
  • 어느 범위까지 줄 것인가

즉, 사람 중심이 아니라 구조 중심으로 권한을 설계해야 한다.

9. GCP 운영의 핵심 질문: 왜 Project가 중심인가

GCP를 사용할 때 반복해서 확인하게 되는 항목은 대부분 Project와 연결된다.

  • 현재 프로젝트가 무엇인가
  • API가 활성화된 프로젝트가 어디인가
  • VM이 속한 프로젝트가 무엇인가
  • 로그와 권한이 어느 프로젝트 기준으로 보이는가

즉, GCP에서는 Project를 모르면 운영이 어렵다고 볼 수 있다.

Project가 핵심인 이유

  1. 대부분의 리소스 생성 위치가 Project 기준임
  1. API 활성화가 Project 기준임
  1. 권한 부여가 Project 기준으로 자주 이루어짐
  1. 비용과 운영 범위도 Project 기준으로 구분되는 경우가 많음
  1. CLI와 콘솔에서도 현재 Project 선택이 매우 중요함

따라서 GCP 실습에서는 항상 다음 순서를 습관화해야 한다.

  1. 현재 Project 확인
  1. 필요한 API 활성화 여부 확인
  1. 리전/존 확인
  1. 리소스 생성

10. GCP 네트워크 철학의 핵심: VPC는 글로벌 리소스

AWS를 먼저 학습한 사람이 GCP에서 가장 크게 다르게 느끼는 부분 중 하나가 이 개념이다.

10.1 AWS에서의 일반적인 이해

AWS에서는 보통 다음과 같이 이해한다.

  • VPC는 리전 단위 자원
  • 서브넷은 VPC 안에서 AZ 단위로 배치
  • 네트워크가 특정 리전에 속해 있다는 감각이 강함

즉, 서울 리전에 VPC 하나, 도쿄 리전에 VPC 하나처럼 생각하는 것이 자연스럽다.

10.2 GCP에서의 방식

GCP에서는 VPC가 글로벌 리소스다.

이 말은 다음을 의미한다.

  • VPC 자체는 특정 리전에 묶이지 않음
  • 하나의 VPC 안에 여러 리전의 서브넷을 둘 수 있음
  • 서브넷은 리전 자원임
  • 방화벽 규칙과 라우팅도 글로벌 관점에서 이해해야 함

즉, GCP에서는 VPC가 먼저 있고, 그 안에 리전별 서브넷이 들어간다고 생각하면 된다.

예시

하나의 VPC 안에 다음과 같은 서브넷을 둘 수 있다.

  • 서울 리전용 서브넷
  • 도쿄 리전용 서브넷
  • 미국 리전용 서브넷

즉, 네트워크 틀은 하나인데 그 안에서 여러 리전의 서브넷을 운영할 수 있는 구조다.

이 차이가 주는 의미

  • 멀티리전 설계가 자연스러움
  • 네트워크를 리전별로 계속 분리하지 않아도 됨
  • 대신 프로젝트 구조, 권한 구조, 공유 네트워크 구조를 함께 고려해야 함

10.3 Shared VPC

GCP에서는 Shared VPC 개념도 중요하다.

이 기능은 여러 프로젝트의 리소스가 하나의 공통 VPC를 사용할 수 있게 해준다.

즉, 네트워크는 중앙에서 관리하고 서비스 리소스는 프로젝트별로 분리하는 구조를 만들 수 있다.

이 구조는 다음과 같은 환경에서 유용하다.

  • 조직 차원에서 네트워크 표준화를 하고 싶을 때
  • 여러 프로젝트가 공통 네트워크를 사용해야 할 때
  • 보안팀이나 플랫폼팀이 네트워크를 중앙 통제해야 할 때

11. AWS와의 비교 정리

11.1 조직 구조 비교

AWS

  • Organizations
  • OU
  • Account

GCP

  • Organization
  • Folder
  • Project

핵심 차이

AWS는 Account가 매우 강한 운영 경계다.

반면 GCP는 Project가 실질 운영 경계로 자주 사용된다.

즉, AWS는 계정을 여러 개 나누는 감각이 강하고,

GCP는 하나의 Organization 아래에 Project를 여러 개 두는 감각이 강하다.

11.2 인프라 위치 구조 비교

AWS

  • Region
  • Availability Zone

GCP

  • Region
  • Zone

핵심 차이

용어만 다르고 개념은 거의 유사하다.

다만 GCP에서는 Zone을 단일 장애 도메인으로 보고 다중 Zone 설계를 적극적으로 고려하는 것이 중요하다.

11.3 네트워크 구조 비교

AWS

  • VPC는 리전 리소스

GCP

  • VPC는 글로벌 리소스
  • Subnet은 리전 리소스

핵심 차이

GCP는 네트워크 자체를 더 글로벌한 관점에서 바라보게 만든다.

11.4 운영 관점 비교

AWS에서 자주 묻는 질문

  • 어느 계정인가
  • 어느 리전인가
  • 어느 VPC인가

GCP에서 자주 묻는 질문

  • 어느 프로젝트인가
  • 어느 리전/존인가
  • 어느 VPC/서브넷인가

즉, GCP는 현재 Project 확인이 가장 먼저 나오는 경우가 많다는 점이 중요하다.

12. 정리

  • GCP도 AWS처럼 컴퓨팅, 스토리지, 네트워크, 데이터베이스 등 다양한 서비스를 제공하는 종합 클라우드 플랫폼임
  • 하지만 운영 관점에서는 Project 중심 구조가 매우 강하게 작동함
  • GCP는 글로벌 네트워크 기반 인프라를 강조하며, 일부 자원은 글로벌 관점에서 이해해야 함
  • Region과 Zone은 배치와 장애 격리의 기본 단위임
  • 리소스 계층 구조는 Organization → Folder → Project → Resources 형태로 이해하면 됨
  • VPC는 글로벌 리소스이며, 서브넷은 리전 리소스임

즉, GCP를 이해할 때는 서비스 이름보다 먼저 프로젝트 중심 운영, 글로벌 인프라, 리소스 계층 구조를 함께 이해해야 한다.

13. 실습: GCP 콘솔과 글로벌 인프라 구조 확인

13.1 실습 목표

이 실습에서는 다음 내용을 확인한다.

  • GCP 콘솔 구조 이해
  • 현재 프로젝트 확인
  • Region과 Zone 구조 확인
  • 프로젝트와 서비스 메뉴의 연결 방식 파악
  • Windows 환경에서 gcloud CLI 설치 및 초기 설정
  • Cloud Shell과 로컬 gcloud CLI의 차이 이해

13.2 실습 준비

필요 사항은 다음과 같다.

  • GCP 로그인 가능한 계정
  • 교육용 프로젝트 또는 개인 프로젝트
  • Windows 10 또는 Windows 11 환경
  • 인터넷 연결
  • Google Cloud Console 접속 가능한 브라우저
  • 관리자 권한으로 프로그램 설치 가능한 환경

Cloud Shell에는 gcloud CLI가 기본 제공된다.

반면 로컬 PC에서 GCP 명령을 사용하려면 Google Cloud CLI를 직접 설치해야 한다.

13.3 실습 0: Windows에 gcloud CLI 설치

이 과정은 로컬 PC에서 GCP 명령어를 실행하기 위한 준비 단계다.

  • Cloud Shell: 브라우저에서 바로 사용하는 Google 제공 CLI 환경
  • gcloud CLI: 내 PC에 직접 설치해 사용하는 로컬 CLI 도구

실무에서는 둘 다 사용하지만,

반복 실습이나 로컬 파일과 연계된 작업에서는 로컬 gcloud CLI가 더 편리한 경우가 많다.

13.3.1 설치 진행

Windows에서는 설치 프로그램 방식과 압축 파일 방식으로 설치할 수 있다.

학습용 실습에서는 설치 프로그램 방식이 가장 간단하다.

진행 순서는 다음과 같다.

  1. Google Cloud CLI 다운로드 페이지 접속
  1. Windows용 설치 프로그램 다운로드
  1. 설치 파일 실행
  1. 안내에 따라 설치 진행

설치 시 확인할 항목은 다음과 같다.

  • PATH 등록 여부
  • 필요한 구성요소 설치 여부
  • 셸 관련 옵션 적용 여부

설치가 끝나면 명령 프롬프트 또는 PowerShell을 새로 열어야 한다.

13.3.2 설치 확인

설치 후 다음 명령으로 정상 설치 여부를 확인한다.

gcloud version

이 명령은 현재 설치된 gcloud CLI 버전과 구성요소 정보를 출력한다.

정상적으로 설치되었다면 다음과 같은 정보를 확인할 수 있다.

  • Google Cloud CLI 버전
  • 포함된 구성요소 버전
  • Python 관련 정보

13.3.3 설치 오류 시 확인 사항

gcloud 명령이 인식되지 않으면 다음 항목을 확인한다.

  1. 명령 프롬프트 또는 PowerShell을 다시 열었는지 확인
  1. PATH 설정이 정상 반영되었는지 확인
  1. 재설치한 경우 재부팅이 필요한지 확인

즉, 설치 후에도 명령이 동작하지 않으면 환경 변수 반영 문제이거나 셸 재실행 문제일 가능성이 크다.

13.4 실습 0-1: gcloud 초기화

설치가 끝났다면 gcloud CLI 초기 설정을 수행한다.

명령어

gcloud init

설명

gcloud init은 gcloud CLI를 처음 사용할 때 수행하는 초기 설정 명령이다.

이 명령은 다음 작업을 수행한다.

  • Google 계정 인증
  • 기본 프로젝트 선택
  • 기본 설정 저장
  • 필요 시 기본 Compute Engine zone 선택

즉, 설치만으로는 바로 실습할 수 없고,

인증과 프로젝트 선택까지 완료해야 실제 사용이 가능하다.

13.4.1 실행 흐름

gcloud init을 실행하면 보통 다음 순서로 진행된다.

  1. 브라우저 로그인 창 열림
  1. Google 계정 로그인
  1. 권한 허용
  1. 사용할 프로젝트 선택
  1. 기본 zone 선택 여부 확인
  1. 설정 저장

이후 gcloud 명령은 이 초기 설정을 기준으로 동작한다.

13.4.2 브라우저 없이 초기화해야 하는 경우

브라우저 팝업이 막히거나 원격 접속 환경이라 브라우저 인증이 어려운 경우에는 다음 명령을 사용할 수 있다.

gcloud init--console-only

이 옵션은 브라우저 대신 명령줄 기반으로 인증을 진행할 때 사용한다.

13.5 실습 1: 현재 프로젝트 확인

콘솔에서 확인

  1. Google Cloud Console 접속
  1. 상단 프로젝트 선택 드롭다운 클릭
  1. 현재 선택된 프로젝트 이름과 프로젝트 ID 확인
  1. 여러 프로젝트가 있다면 이름과 ID가 각각 다름을 확인

설명

프로젝트 이름은 사람이 보기 쉬운 표시용 이름이다.

반면 프로젝트 ID는 실제 명령이나 서비스 식별에서 자주 사용된다.

즉, GCP 실습에서는 이름만 보는 것이 아니라 프로젝트 ID를 정확히 확인하는 습관이 중요하다.

13.6 실습 2: 리전과 존 확인

콘솔에서 확인

  1. Compute Engine 메뉴 이동
  1. VM 인스턴스 생성 화면 진입
  1. Region, Zone 선택 항목 확인
  1. asia-northeast3 계열과 다른 지역 옵션 비교

설명

  • Region은 지리적 범위
  • Zone은 Region 내부의 배치 단위
  • 리소스마다 Global / Regional / Zonal 속성이 다름

즉, GCP에서는 단순히 어느 리전인지뿐 아니라,

해당 자원이 글로벌 자원인지, 리전 자원인지, 존 자원인지까지 함께 이해해야 한다.

13.7 실습 3: Cloud Shell 또는 로컬 CLI에서 현재 프로젝트 확인

Cloud Shell과 로컬 gcloud CLI 모두에서 동일하게 실행할 수 있다.

명령어

gcloud config list

설명

이 명령은 현재 gcloud CLI의 설정값을 출력한다.

특히 다음 항목을 확인한다.

  • 현재 로그인한 계정
  • 현재 기본 프로젝트
  • 기타 설정값

즉, 이 명령은 내가 지금 어떤 기준으로 GCP 작업을 수행하는지 확인하는 기본 점검 명령이다.

현재 프로젝트만 확인

gcloud config get-value project

이 명령은 현재 기본 프로젝트 ID만 출력한다.

이 명령이 중요한 이유는 gcloud CLI의 대부분의 작업이 현재 기본 프로젝트를 기준으로 동작하기 때문이다.

예를 들어 다음과 같은 문제가 발생할 수 있다.

  • VM이 잘못된 프로젝트에 생성됨
  • API가 다른 프로젝트에서 활성화됨
  • 권한 오류처럼 보이지만 실제로는 프로젝트 선택이 잘못된 경우가 있음

따라서 GCP에서는 작업 전에 현재 프로젝트 확인이 필수 습관이다.

13.8 실습 4: 프로젝트 변경

명령어

gcloud config set project [PROJECT_ID]

설명

이 명령은 이후 실행할 gcloud 명령의 기본 프로젝트를 변경한다.

중요한 포인트는 다음과 같다.

  • config, set, project 사이에는 공백이 있어야 함
  • [PROJECT_ID]는 실제 프로젝트 ID로 바꿔 입력해야 함
  • 프로젝트 이름보다 프로젝트 ID를 사용하는 것이 일반적임

예시:

gcloud config set project my-gcp-project-123

변경 후에는 반드시 다시 확인하는 것이 좋다.

gcloud config get-value project

이렇게 확인하는 습관을 들이면 다른 프로젝트에 리소스를 잘못 생성하는 실수를 줄일 수 있다.

13.9 실습 5: 사용 가능한 리전 확인

명령어

gcloud compute regions list

설명

현재 사용 가능한 Region 목록을 확인하는 명령이다.

출력 결과를 통해 다음을 파악할 수 있다.

  • 리전 이름
  • 상태
  • 설명 또는 관련 메타 정보

이 명령을 통해 GCP가 하나의 지역이 아니라 여러 지역에 걸쳐 서비스를 운영하고 있음을 직접 확인할 수 있다.

13.10 실습 6: 사용 가능한 존 확인

명령어

gcloud compute zones list

설명

Zone 목록을 확인하는 명령이다.

예를 들어 다음과 같은 형식을 볼 수 있다.

  • asia-northeast3-a
  • asia-northeast3-b
  • asia-northeast3-c

이 출력 결과를 통해 다음 사실을 알 수 있다.

  • 하나의 Region 안에 여러 Zone이 존재함
  • Region과 Zone은 서로 다른 개념임
  • VM 같은 자원은 특정 Zone에 생성되는 경우가 많음

즉, GCP에서 리소스를 만들 때는 어느 Region인지뿐 아니라 어느 Zone에 배치할 것인지까지 고려해야 한다.

13.11 실습 체크 포인트

실습이 끝났다면 다음 항목을 점검한다.

  • 내 Windows PC에서 gcloud version이 정상 실행되는가
  • gcloud init을 통해 로그인과 초기 설정을 마쳤는가
  • 현재 기본 프로젝트를 확인할 수 있는가
  • 프로젝트를 변경하고 다시 확인할 수 있는가
  • Region과 Zone 목록을 CLI로 조회할 수 있는가
  • Cloud Shell과 로컬 CLI의 차이를 설명할 수 있는가

13.12 보충 설명: Cloud Shell과 로컬 gcloud CLI의 차이

학생들이 자주 헷갈리는 부분이므로 구분해서 이해하는 것이 좋다.

Cloud Shell

  • 브라우저에서 바로 실행되는 Google 제공 셸 환경
  • gcloud CLI가 기본 설치되어 있음
  • 별도 설치 없이 바로 사용 가능
  • 간단한 실습이나 긴급 작업에 편리함

로컬 gcloud CLI

  • 내 PC에 직접 설치하는 CLI 도구
  • 로컬 파일, 스크립트, Git 작업과 연계하기 쉬움
  • 반복 실습이나 자동화에 유리함
  • 처음 한 번은 설치와 초기 설정이 필요함

즉, 기능보다 실행 위치와 작업 방식의 차이로 이해하면 된다.

13.13 추가 명령어

인증된 계정 확인

gcloud auth list

이 명령은 현재 로컬 시스템에 저장된 인증 계정 목록을 출력한다.

또한 어떤 계정이 활성 계정인지도 함께 확인할 수 있다.

도움말 확인

gcloud help

이 명령은 gcloud CLI 전체 도움말을 보여준다.

특정 명령의 사용법을 자세히 보고 싶다면 다음처럼 입력할 수 있다.

gcloud help compute instances create

이 형식은 gcloud 아래의 명령 계층 구조를 따라 세부 사용법을 확인할 때 유용하다.
