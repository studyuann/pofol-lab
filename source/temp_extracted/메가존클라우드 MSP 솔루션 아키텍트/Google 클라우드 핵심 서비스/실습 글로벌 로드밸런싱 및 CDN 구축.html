실습. 글로벌 로드밸런싱 및 CDN 구축

Anycast IP와 Google 전용 네트워크를 활용한 고가용성 인프라 실습

1. 실습 개요

GCP에서 2대의 가상 머신(GCE)을 백엔드로 구성하고, 글로벌 외부 HTTP(S) 부하 분산기와 Cloud CDN을 결합하여 가용성과 응답 속도를 최적화한다.

학습 목표

  • Compute Engine(GCE)을 사용하여 웹 서버 2대를 구축한다.
  • 인스턴스 그룹(Instance Group)으로 백엔드 자원을 구조화한다.
  • 애니캐스트(Anycast) IP를 할당받아 전 세계 단일 진입점을 만든다.
  • Cloud CDN을 활성화하여 엣지 로케이션의 캐싱 동작을 확인한다.

2. 실습 준비물

  • GCP 계정 (프로젝트 생성 완료 상태)
  • 방화벽 설정: default-allow-http (80번 포트 허용)

3. 단계별 실습 절차

Step 1: 백엔드 VM 인스턴스 구성

먼저 부하분산기의 백엔드가 될 웹 서버 2대를 생성한다.

1. VM 인스턴스 2대 생성

  • 이름: web-server-1, web-server-2
  • 리전: asia-northeast3(서울) 권장
  • 머신 유형: 실습용 소형 인스턴스 사용
  • 부팅 디스크: Ubuntu 계열 또는 Debian 계열 사용 가능
  • 방화벽: HTTP 트래픽 허용 체크 권장

2. Startup Script 설정

인스턴스 생성 화면에서 고급 옵션 > 관리 > 자동화(Startup script) 영역에 아래 스크립트를 입력한다.

#!/bin/bash
apt-get update
apt-get install -y nginx

HOSTNAME=$(hostname)

cat <<EOF > /var/www/html/index.html
<h1>This is Server: ${HOSTNAME}</h1>
<p>Loaded from backend VM</p>
EOF

cat <<EOF > /etc/nginx/conf.d/cache-control.conf
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    root /var/www/html;
    index index.html;
    location / {
        add_header Cache-Control "public, max-age=60";
        try_files \$uri \$uri/ =404;
    }
}
EOF

rm -f /etc/nginx/sites-enabled/default
systemctl restart nginx

보완 설명

기존 스크립트도 동작은 하지만, Cloud CDN 테스트까지 고려하면 응답 헤더에 Cache-Control을 명시적으로 넣는 편이 더 안정적임. Cloud CDN은 백엔드 서비스에서 CDN을 활성화한 뒤 캐시 정책에 따라 객체를 캐싱하며, 캐시 동작은 백엔드 설정과 원본 응답 헤더의 영향을 받음.

Step 2: 인스턴스 그룹 생성

로드밸런서는 개별 VM이 아니라 인스턴스 그룹을 대상으로 트래픽을 전달한다.

1. 메뉴 이동

  • Compute Engine > 인스턴스 그룹
  • 인스턴스 그룹 만들기 클릭

2. 설정

  • 그룹 유형: 비관리형 인스턴스 그룹
  • 이름: 예시 web-servers-ig
  • 네트워크/영역: VM이 있는 영역과 동일하게 선택
  • 인스턴스 추가: web-server-1, web-server-2

보완 설명

실습은 비관리형 인스턴스 그룹으로 진행해도 충분함. 다만 운영 환경에서는 자동 복구, 자동 확장, 템플릿 기반 관리가 가능한 관리형 인스턴스 그룹(MIG) 이 더 일반적임. Cloud CDN은 인스턴스 그룹을 백엔드로 사용하는 외부 애플리케이션 부하분산기와 함께 사용할 수 있음.

Step 3: 부하 분산기 생성

이번 단계에서는 Cloud CDN은 아직 켜지지 않은 상태로 먼저 부하분산기를 생성한다.

1. 메뉴 이동

  • 네트워크 서비스 > 부하 분산
  • 부하 분산기 만들기

2. 유형 선택

다음과 같이 선택한다.

  • 애플리케이션 부하 분산기(HTTP/S)
  • 외부용(Public facing / external)
  • 전역(Global)
  • Global external Application Load Balancer

이 부하분산기는 단일 외부 IP를 통해 전역 사용자 요청을 받아 백엔드 서비스로 전달하는 L7 프록시형 로드밸런서임.

3. 백엔드 구성

  • 백엔드 유형: 인스턴스 그룹
  • 백엔드 서비스 생성
  • 백엔드로 web-servers-ig 선택
  • 프로토콜: HTTP
  • 포트: 80

4. 상태 확인(Health Check) 생성

상태 확인은 매우 중요함. 로드밸런서는 정상 응답을 반환하는 인스턴스에만 트래픽을 전달한다.

  • 유형: HTTP
  • 포트: 80
  • 요청 경로: /

5. 프론트엔드 구성

  • 프로토콜: HTTP
  • IP 버전: IPv4
  • IP 주소: 새 고정 IP 예약
  • 이름: 예시 web-lb-ip
  • 포트: 80

6. 검토 후 생성

설정을 검토한 뒤 부하분산기를 생성한다.

Step 4: 부하분산기 동작 먼저 검증

이유는 Cloud CDN을 먼저 켜면 캐시 때문에 백엔드 서버가 번갈아 응답하는 모습이 잘 보이지 않을 수 있기 때문임.

1. 프론트엔드 IP 접속

브라우저에서 다음과 같이 접속한다.

http://[부하분산기_프론트엔드_IP]

2. 새로고침 반복

여러 번 새로고침하여 다음과 같은 응답이 교대로 보이는지 확인한다.

  • This is Server: web-server-1
  • This is Server: web-server-2

보완 설명

로드밸런싱 검증은 CDN 활성화 전에 먼저 하는 것이 좋음. CDN이 활성화되면 첫 요청 이후 응답이 엣지 캐시에 저장될 수 있어서, 이후 요청은 백엔드까지 가지 않을 수 있음. 그러면 두 서버가 번갈아 나오는 현상이 눈에 잘 안 띌 수 있음. Cloud CDN은 백엔드 서비스 수준에서 활성화되며, 캐시된 응답은 엣지에서 바로 전달될 수 있음.

Step 5: 생성된 부하분산기에 Cloud CDN 연결

이제 이미 만들어진 부하분산기에 Cloud CDN을 붙인다.

1. 메뉴 이동

  • 네트워크 서비스 > 부하 분산
  • 방금 만든 부하분산기 이름 클릭

2. 편집 모드 진입

  • 상단의 수정(Edit) 클릭
  • Backend configuration 단계로 이동

공식 문서 기준으로 기존 부하분산기 수정은 Load balancing > 해당 LB 선택 > Edit > Backend Configuration > backend service 편집 흐름으로 진행한다.

3. 백엔드 서비스 편집

  • 연결된 백엔드 서비스(Edit) 클릭
  • 설정 화면에서 Enable Cloud CDN 또는 Cloud CDN 사용 설정 체크

4. 캐시 모드 설정

실습에서는 다음 중 하나를 권장한다.

  • Cache static content
  • 또는 기본 캐시 모드 유지

정적 HTML 파일을 서비스하는 구조이므로 실습 목적에는 충분함. index.html 같은 정적 콘텐츠는 CDN 캐시 테스트에 적합하다. Cloud CDN은 백엔드 서비스 설정에서 캐시 모드와 TTL 관련 옵션을 조정할 수 있다.

5. 저장 및 업데이트

  • 변경 사항 저장
  • Review and finalize
  • Update

Step 6: Cloud CDN 캐싱 확인

이제 캐시가 실제로 적용되는지 확인한다.

1. 헤더 확인 명령 실행

Cloud Shell 또는 로컬 터미널에서 실행한다.

curl -I http://[부하분산기_프론트엔드_IP]

2. 응답 헤더 확인

다음과 비슷한 헤더를 확인한다.

x-cache: HIT

또는 환경에 따라 Cloud CDN 관련 캐시 상태 헤더가 표시될 수 있다. 최초 요청은 MISS일 수 있고, 반복 요청 시 HIT로 바뀌는 흐름을 확인하면 됨.

보완 설명

캐시는 첫 요청 직후 바로 HIT가 되지 않을 수 있음. 최초 요청은 원본 서버에서 받아와 엣지에 저장하는 과정이라 MISS가 보일 수 있음. 이후 동일한 객체 요청에서 HIT가 보이면 캐싱이 동작하는 것임.

실습 문서에는 특정 헤더 이름을 하나로 단정하기보다 **“캐시 상태가 MISS → HIT로 바뀌는지 확인”**이라고 적는 편이 더 안전함. 콘솔/플랫폼 변화나 헤더 노출 방식 차이 때문에 환경별로 다르게 보일 수 있기 때문임.

Step 7: 고가용성(Failover) 테스트

부하분산기와 상태 확인이 정상 동작하는지 확인한다.

1. 인스턴스 하나 중지

  • web-server-1 인스턴스를 중지

2. 잠시 대기 후 재접속

다시 아래 주소로 접속한다.

http://[부하분산기_프론트엔드_IP]

3. 결과 확인

  • 서비스가 계속 응답하는지 확인
  • 남아 있는 web-server-2가 요청을 처리하는지 확인

보완 설명

이 테스트는 상태 확인(Health Check) 이 제대로 동작하는지 검증하는 과정임. 로드밸런서는 비정상 백엔드를 자동으로 제외하고 정상 백엔드로만 트래픽을 전달한다. 백엔드 서비스는 상태 확인과 함께 동작하며, 어떤 백엔드가 요청을 처리할지 결정하는 핵심 구성 요소다.

4. 결과 검증 및 테스트

① 로드밸런싱 확인

Cloud CDN을 붙이기 전에 먼저 검증한다.

  • 부하분산기 프론트엔드 IP 접속
  • 새로고침 반복
  • web-server-1, web-server-2가 번갈아 보이는지 확인

② Cloud CDN 캐싱 확인

Cloud CDN 활성화 후 아래 명령 실행

curl -I http://[부하분산기_프론트엔드_IP]

확인 포인트

  • 첫 요청: MISS 가능
  • 재요청: HIT 확인 가능
  • Cache-Control 헤더도 함께 확인 가능

③ 장애 조치 확인

  • web-server-1 중지
  • 일정 시간 후 재접속
  • web-server-2만으로도 정상 서비스되는지 확인
