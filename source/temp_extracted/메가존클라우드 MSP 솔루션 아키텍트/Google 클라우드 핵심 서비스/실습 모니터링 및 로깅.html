Monitoring에서 VM 메트릭 확인

실습 목적

Google Cloud Monitoring의 Metrics Explorer에서 VM 인스턴스의 CPU 사용률 같은 메트릭을 직접 확인해본다.

이 실습을 통해 특정 VM의 상태를 시계열 그래프로 확인하는 방법을 익힌다.

콘솔 흐름

  1. Google Cloud Console에 접속한다.
  1. 왼쪽 메뉴에서 Monitoring으로 이동한다.
  1. Metrics Explorer 메뉴를 선택한다.
  1. Resource type에서 VM Instance 또는 gce_instance 계열을 선택한다.
  1. Metric에서 CPU 사용률 관련 항목을 선택한다.

확인 포인트

  • web-vm-01 또는 현재 실습 중인 VM이 목록에 보이는지 확인한다.
  • CPU 사용률 그래프가 시간축 기준으로 표시되는지 확인한다.
  • 특정 인스턴스만 보도록 필터링할 수 있는지 확인한다.

설명

Monitoring의 Metrics Explorer는 GCP 리소스의 상태를 메트릭 기반으로 시각화하는 도구다.

여기서 Resource type은 어떤 자원의 메트릭을 볼 것인지를 의미하고, Metric은 그 자원에서 어떤 항목을 볼 것인지를 의미한다.

예를 들어 VM Instance를 선택하면 Compute Engine 가상 머신 기준의 메트릭을 볼 수 있고, CPU utilization을 선택하면 CPU 사용률을 그래프로 확인할 수 있다.

이 그래프는 특정 시점의 값만 보여주는 것이 아니라, 일정 시간 동안 변화한 흐름을 보여주기 때문에 부하 테스트 전후 비교에 매우 유용하다.

VM CPU 부하 발생하기

실습 목적

VM에서 인위적으로 CPU 사용률을 높여 Monitoring 그래프 변화가 실제로 어떻게 나타나는지 확인한다.

VM 접속

gcloud compute ssh web-vm-01 --zone=asia-northeast3-a

명령어 설명

gcloud compute ssh는 Google Cloud CLI를 이용해 Compute Engine 인스턴스에 SSH로 접속할 때 사용하는 명령이다.

  • gcloud

    Google Cloud 명령줄 도구다.

  • compute ssh

    Compute Engine VM에 SSH 접속을 수행하는 하위 명령이다.

  • web-vm-01

    접속 대상 인스턴스 이름이다.

  • --zone=asia-northeast3-a

    해당 VM이 존재하는 리전을 포함한 zone을 지정한다.

    같은 이름의 인스턴스가 다른 zone에 있을 수 있으므로 zone 지정은 매우 중요하다.

CPU 부하 예시

yes > /dev/null &
yes > /dev/null &

명령어 설명

yes 명령은 기본적으로 y 문자를 계속 반복 출력하는 명령이다.

원래는 화면에 계속 문자열을 출력하지만, 여기서는 > /dev/null을 붙였기 때문에 출력 결과를 전부 버리게 된다.

각 요소의 의미는 다음과 같다.

  • yes

    문자열을 무한 반복 출력한다.

  • >

    표준 출력을 다른 곳으로 리다이렉션한다.

  • /dev/null

    리눅스에서 아무 데이터도 저장하지 않고 버리는 특수 장치 파일이다.

  • &

    해당 명령을 백그라운드에서 실행한다.

즉, yes > /dev/null &는

계속 연산을 수행하지만 결과는 버리고, 백그라운드에서 쉬지 않고 동작하는 프로세스를 만드는 방식이다.

이런 프로세스를 여러 개 실행하면 CPU 사용률이 상승한다.

위 예시에서는 두 개를 동시에 실행했으므로 VM의 vCPU 수에 따라 CPU 사용률이 눈에 띄게 올라갈 수 있다.

부하 종료

pkill yes

명령어 설명

pkill은 프로세스 이름을 기준으로 실행 중인 프로세스를 종료하는 명령이다.

  • pkill yes

    이름이 yes인 프로세스를 찾아 모두 종료한다.

실습이 끝난 뒤 이 명령을 반드시 실행해야 불필요한 CPU 사용이 지속되지 않는다.

확인 포인트

  • CPU 부하를 발생시키기 전과 후의 그래프 차이가 보이는지 확인한다.
  • Metrics Explorer에서 CPU 사용률이 상승하는지 확인한다.
  • 부하 종료 후 CPU 사용률이 다시 낮아지는지 확인한다.

대시보드 생성

실습 목적

자주 확인하는 메트릭을 한 화면에 모아 볼 수 있도록 Monitoring Dashboard를 생성한다.

콘솔 흐름

  1. Monitoring 메뉴로 이동한다.
  1. Dashboards를 선택한다.
  1. 새 대시보드를 생성한다.
  1. 차트 추가를 선택한다.
  1. Compute Engine CPU 사용률 차트를 추가한다.
  1. 필요하면 네트워크 사용량 차트도 추가한다.

추천 차트

  • VM CPU Utilization
  • VM Network Bytes Sent
  • VM Network Bytes Received
  • Cloud SQL CPU
  • Load Balancer Request Count

설명

대시보드는 여러 메트릭을 한 번에 확인할 수 있도록 구성하는 화면이다.

운영 환경에서는 CPU, 메모리, 네트워크, 디스크, 데이터베이스, 로드밸런서 요청 수 등을 한 곳에 모아서 보는 경우가 많다.

실습 단계에서는 먼저 VM CPU와 네트워크 정도만 추가해도 충분하다.

이후 시스템이 커지면 Cloud SQL, Load Balancer, Uptime Check 결과 같은 항목도 함께 넣어 운영 시야를 넓힐 수 있다.

확인 포인트

  • 대시보드가 정상적으로 생성되는지 확인한다.
  • 추가한 차트가 실시간 또는 시계열 형태로 보이는지 확인한다.
  • 여러 차트를 한 화면에서 동시에 비교할 수 있는지 확인한다.

Alerting Policy 생성

실습 목적

특정 메트릭 값이 임계치를 넘었을 때 자동으로 경고를 발생시키는 Alerting Policy를 생성한다.

예시 목표

VM CPU 사용률이 80% 이상일 때 알림이 발생하도록 설정한다.

콘솔 흐름

  1. Monitoring 메뉴로 이동한다.
  1. Alerting을 선택한다.
  1. 새 정책을 생성한다.
  1. 조건을 추가한다.
  1. Resource type으로 VM Instance를 선택한다.
  1. Metric으로 CPU utilization을 선택한다.
  1. Threshold를 0.8 또는 80% 수준으로 설정한다.
  1. 지속 시간 조건을 설정한다.
  1. 알림 채널은 실습 환경에 따라 생략하거나 개념만 확인한다.

설명

Alerting은 단순 조회가 아니라 이상 상태를 자동 감지하는 기능이다.

예를 들어 CPU 사용률이 잠깐 80%를 넘는 것은 큰 문제가 아닐 수 있으므로, 보통은 일정 시간 이상 지속될 때만 경고가 발생하도록 설정한다.

여기서 Threshold 값은 메트릭 표현 방식에 따라 0.8처럼 소수로 표시될 수도 있고, 화면에서는 80%처럼 보일 수도 있다.

즉, 0.8은 80%와 같은 의미다.

운영 환경에서는 이메일, SMS, Pub/Sub, Slack 연동 같은 알림 채널을 연결하지만, 실습에서는 정책 생성 흐름과 임계치 개념만 이해해도 충분하다.

확인 포인트

  • CPU utilization 기준 조건이 정상적으로 설정되는지 확인한다.
  • 임계치와 지속 시간이 함께 설정되는지 확인한다.
  • 정책 생성 후 목록에서 확인 가능한지 본다.

Log Explorer에서 VM 로그 확인

실습 목적

Cloud Logging의 Log Explorer에서 VM 관련 로그를 조회하고,

로그가 보이지 않을 때 Service Account 권한, Ops Agent 설치 여부, 리소스/시간 범위 필터를 기준으로 원인을 점검하는 방법을 익힌다. Log Explorer는 저장된 로그를 조회, 필터링, 분석하는 도구이며, 리소스와 시간 범위를 좁혀 장애 분석에 활용할 수 있다.

실습 개요

이번 실습은 단순히 Log Explorer만 여는 것이 아니라, 아래 순서로 진행한다.

  1. VM에 연결된 Service Account를 확인한다.
  1. 해당 Service Account에 로그/메트릭 전송 역할이 있는지 확인한다.
  1. VM에 Ops Agent가 설치되어 있는지 확인한다.
  1. 필요하면 Ops Agent를 설치한다.
  1. Log Explorer에서 특정 VM 로그를 필터링해서 확인한다.
  1. 시간 범위와 리소스 조건을 바꿔가며 결과 차이를 확인한다.

Ops Agent는 기본적으로 로그와 메트릭을 함께 수집하며, 추가 설정을 통해 애플리케이션 로그 수집도 확장할 수 있다.

사전 확인 1: VM에 연결된 Service Account 확인

콘솔 흐름

  1. Compute Engine > VM 인스턴스로 이동한다.
  1. 대상 VM을 클릭한다.
  1. 세부정보 탭에서 서비스 계정 항목을 확인한다.

확인 포인트

  • VM에 서비스 계정이 연결되어 있는지 확인한다.
  • 실습에서 사용할 서비스 계정이 맞는지 확인한다.

설명

VM이 Cloud Logging과 Cloud Monitoring으로 데이터를 보내려면,

VM 내부 에이전트가 메타데이터 서버를 통해 서비스 계정 자격 증명을 사용하게 된다. 따라서 VM에 적절한 서비스 계정이 붙어 있어야 하고, 그 서비스 계정에 필요한 IAM 역할이 있어야 함.

사전 확인 2: Service Account 권한 확인

필요한 권한

실습용 서비스 계정에는 최소 아래 역할이 필요하다.

  • roles/logging.logWriter
  • roles/monitoring.metricWriter

콘솔 흐름

  1. IAM 및 관리자 > IAM으로 이동한다.
  1. VM에 연결된 서비스 계정을 찾는다.
  1. 아래 역할이 포함되어 있는지 확인한다.
    • 로그 작성자(Logging Logs Writer)
    • 모니터링 측정항목 작성자(Monitoring Metric Writer)

확인 포인트

  • 두 역할이 모두 있는지 확인한다.
  • 없다면 역할을 추가한다.

설명

권한이 없으면 에이전트가 설치되어 있어도 로그나 메트릭 전송이 실패할 수 있음.

따라서 Log Explorer에 아무 로그도 안 보이는 경우, 에이전트 설치 여부와 함께 서비스 계정 권한도 같이 봐야 함.

사전 확인 3: Ops Agent 설치 여부 확인

방법 1. 콘솔에서 확인

  1. Compute Engine > VM 인스턴스로 이동한다.
  1. 대상 VM 클릭
  1. 관측 가능성(Observability) 탭으로 이동한다.
  1. 에이전트 상태를 확인한다.

방법 2. SSH 접속 후 확인

sudo systemctl status google-cloud-ops-agent

확인 포인트

  • active (running) 상태인지 확인한다.
  • 서비스가 없거나 실패 상태면 설치가 필요하다.

설명

Ops Agent가 설치되지 않았거나 실행 중이 아니면, Log Explorer에서 VM 내부 로그를 기대한 만큼 볼 수 없음. 특히 애플리케이션 로그나 시스템 로그 수집은 에이전트 상태에 직접 영향을 받는다. 문제 발생 시 에이전트 상태와 수집 상태를 먼저 점검해야 한다.

Step 1: Ops Agent 설치

방법 1. 콘솔에서 설치

  1. Compute Engine > VM 인스턴스로 이동한다.
  1. 대상 VM 클릭
  1. 관측 가능성(Observability) 탭 선택
  1. Install Ops Agent 클릭

Google 문서에 따르면 기존 VM에서도 이 방식으로 Ops Agent 설치가 가능하다. 설치는 가능한 경우 OS policy 기반으로 진행된다.

방법 2. SSH 접속 후 수동 설치

SSH로 VM에 접속한 뒤 아래 명령을 실행한다.

curl-sSO https://dl.google.com/cloudagents/add-google-cloud-ops-agent-repo.sh
sudobash add-google-cloud-ops-agent-repo.sh--also-install

설치 후 상태 확인

sudo systemctl status google-cloud-ops-agent

확인 포인트

  • 설치가 완료되었는지 확인한다.
  • 서비스가 실행 중인지 확인한다.

설명

Ops Agent는 기존 VM에도 나중에 설치 가능하며, 설치 후 기본적으로 로그와 메트릭 수집을 시작한다. 필요하면 설정 파일을 수정하여 수집 대상을 더 확장할 수 있다.

Step 2: Log Explorer에서 VM 로그 확인

콘솔 흐름

  1. Logging 메뉴로 이동한다.
  1. Log Explorer에 진입한다.
  1. Resource 선택에서 VM Instance를 선택한다.
  1. 특정 인스턴스를 선택한다.
  1. 최근 1시간 또는 최근 24시간 로그를 확인한다.

기본 필터 예시

resource.type="gce_instance"

특정 VM만 조회하는 필터 예시

resource.type="gce_instance"
resource.labels.instance_id="INSTANCE_ID"

Log Explorer는 리소스 종류, 로그 이름, 심각도, 시간 범위 등을 기준으로 로그를 필터링할 수 있으며, 쿼리 언어를 이용해 조건을 직접 작성할 수 있다.

Step 3: 시간 범위 변경 후 비교

실습 절차

  1. 시간 범위를 최근 1시간으로 설정한다.
  1. 로그 개수를 확인한다.
  1. 시간 범위를 최근 24시간으로 변경한다.
  1. 표시되는 로그 수와 내용이 달라지는지 확인한다.

확인 포인트

  • 최근 1시간에는 로그가 없고 24시간에는 있을 수 있는지 확인한다.
  • 시간 범위에 따라 결과가 크게 달라지는지 확인한다.

설명

실무에서 로그가 “안 보인다”는 말은 실제로 로그가 없는 경우도 있지만,

시간 범위가 너무 좁아서 안 보이는 경우도 많음. 따라서 로그 분석에서는 시간 범위부터 먼저 의심하는 습관이 중요함. Log Explorer는 시간 선택과 필터 조합으로 조회 결과가 크게 달라질 수 있다.

Step 4: 로그가 안 보일 때 점검

점검 순서

1. Service Account 권한 확인

  • roles/logging.logWriter
  • roles/monitoring.metricWriter

2. Ops Agent 설치 여부 확인

sudo systemctl status google-cloud-ops-agent

3. 에이전트 오류 로그 확인

sudo journalctl -u google-cloud-ops-agent -n100 --no-pager

Google 문서는 에이전트가 실행 중이어도 수집 또는 전송 문제가 있을 수 있으므로, 설치 문제와 데이터 수집 문제를 분리해서 점검하라고 안내한다.

4. 시간 범위 확대

  • 최근 1시간 → 최근 24시간 → 최근 7일 순으로 확대

5. 필터 단순화

처음에는 아래처럼 최소 조건으로 조회한다.

resource.type="gce_instance"

그다음 점차 인스턴스 ID, 로그 이름, 심각도 등을 추가한다. Log Explorer 쿼리는 좁힐수록 편하지만, 처음부터 조건을 너무 많이 넣으면 아무 결과도 안 나올 수 있다.

nginx 관련 로그 확인 예시

실습 목적

VM 내부 서비스 상태를 바꾼 뒤 Logging에서 관련 흔적을 찾는 방법을 익힌다.

VM 접속

gcloud compute ssh web-vm-01 --zone=asia-northeast3-a

nginx 재시작

sudo systemctl restart nginx

명령어 설명

  • sudo

    관리자 권한으로 명령을 실행한다.

  • systemctl

    systemd 기반 리눅스에서 서비스 상태를 제어하는 명령이다.

  • restart

    서비스를 재시작한다.

  • nginx

    대상 서비스 이름이다.

즉, sudo systemctl restart nginx는

nginx 서비스를 관리자 권한으로 재시작하는 명령이다.

원문에 있던 sudo systemctlrestart nginx는 띄어쓰기가 빠져 있었음.

반드시 systemctl restart처럼 띄어서 입력해야 정상 실행된다.

설명

서비스를 재시작하면 VM 내부에서는 시스템 로그나 에이전트 로그에 관련 흔적이 남을 수 있다.

이후 Log Explorer에서 시간 범위를 아주 좁게 설정한 뒤 nginx, restart, systemd 관련 키워드를 확인하면 실습 효과가 좋다.

확인 포인트

  • nginx 재시작 직후 로그 변화가 보이는지 확인한다.
  • 시간 범위를 좁히면 관련 로그를 더 쉽게 찾을 수 있는지 확인한다.
  • 인스턴스 기준 필터와 키워드 검색을 함께 사용할 수 있는지 확인한다.

에러 로그와 키워드 검색

실습 목적

Log Explorer에서 텍스트 검색과 필터를 이용해 필요한 로그를 빠르게 찾는 방법을 익힌다.

예시 검색 키워드

  • error
  • nginx
  • denied
  • restart

설명

로그가 많아지면 눈으로 하나씩 확인하는 것은 사실상 어렵다.

그래서 키워드 검색과 리소스 필터, 시간 범위를 함께 사용하는 방식이 중요하다.

예를 들어 다음과 같이 접근할 수 있다.

  • error

    오류 메시지 중심으로 찾을 때 사용한다.

  • nginx

    웹 서버 관련 로그만 빠르게 좁힐 때 사용한다.

  • denied

    권한 거부, 접근 거부 관련 이벤트를 찾을 때 유용하다.

  • restart

    서비스 재시작 흔적을 찾을 때 유용하다.

이런 검색은 단순 문자열 검색일 수도 있고, Log Explorer의 쿼리 필터를 이용한 정교한 검색으로 확장할 수도 있다.

실무에서는 리소스 + 시간 범위 + 키워드를 조합하는 방식이 가장 기본적이다.

확인 포인트

  • 키워드 입력 시 관련 로그만 좁혀지는지 확인한다.
  • 시간 범위와 함께 사용했을 때 검색 정확도가 높아지는지 확인한다.
  • 여러 키워드로 바꿔가며 로그 성격이 달라지는지 확인한다.

Uptime Check 개념 확인

실습 목적

외부 사용자 관점에서 서비스의 가용성을 점검하는 Uptime Check 개념을 이해한다.

예시 대상

  • http://[EXTERNAL_IP]

콘솔 흐름

  1. Monitoring 메뉴로 이동한다.
  1. Uptime checks를 선택한다.
  1. 새 체크를 생성한다.
  1. HTTP 대상을 입력한다.
  1. 응답 상태 확인 조건을 지정한다.

설명

Uptime Check는 내부 VM 메트릭을 보는 기능이 아니라, 외부에서 서비스에 실제로 접속이 되는지 확인하는 기능이다.

즉, CPU나 메모리 상태가 정상이어도 웹 페이지가 응답하지 않으면 사용자 입장에서는 장애다.

이런 관점을 확인하는 도구가 Uptime Check다.

예를 들어 외부 IP로 노출된 웹 서버에 대해 HTTP 요청을 보내고, 응답 코드가 200번대인지 확인하도록 설정할 수 있다.

이후 실패가 반복되면 Alerting과 연계해 가용성 장애를 빠르게 감지할 수 있다.

확인 포인트

  • 외부 IP 기반으로 HTTP 대상 설정이 가능한지 확인한다.
  • 상태 코드 기준 점검이 가능한지 확인한다.
  • 내부 메트릭과 외부 가용성 점검의 차이를 이해한다.

실습 정리

핵심은 다음과 같다.

  • Monitoring은 CPU, 네트워크 같은 수치형 상태를 본다.
  • Metrics Explorer는 개별 메트릭을 시계열로 분석할 때 사용한다.
  • Dashboard는 여러 메트릭을 한 화면에 모아 본다.
  • Alerting은 임계치 초과 상황을 자동 감지한다.
  • Logging / Log Explorer는 실제 이벤트와 오류 메시지를 추적한다.
  • Uptime Check는 외부 사용자 관점에서 서비스 응답 여부를 확인한다.

즉, 운영 관점에서는

메트릭으로 이상을 감지하고, 로그로 원인을 추적하며, Uptime Check로 외부 가용성을 확인하는 구조로 이해하면 된다.
