1장 고급 멀티 티어 아키텍처와 설계 원칙

1.1 고급 아키텍처 설계란 무엇인가

AWS에서 아키텍처를 설계한다는 것은 단순히 서비스를 나열하고 연결해서 동작시키는 작업이 아님.

기초 단계에서는 “서비스를 만들 수 있는가”, “기능이 동작하는가”가 중요했음.

하지만 고급 단계에서는 “왜 이 구조를 선택했는가”, “장애와 확장, 보안, 운영, 비용까지 함께 고려했는가”가 더 중요해짐.

즉, 고급 아키텍처 설계는 다음 질문에 답할 수 있어야 함.

  • 왜 이 서비스를 선택했는가
  • 왜 이 계층을 분리했는가
  • 장애가 발생하면 어디까지 영향이 전파되는가
  • 확장이 필요할 때 어떤 계층을 먼저 확장할 것인가
  • 보안 경계를 어디에 둘 것인가
  • 운영 자동화가 가능한 구조인가
  • 비용이 증가할 때 어디가 원인인가
  • 조직 규모가 커져도 유지 가능한 구조인가

즉, 고급 아키텍처 설계는 서비스 사용법을 아는 수준이 아니라, 구조적 의사결정을 설명할 수 있는 수준을 의미함.

1.2 왜 단순한 구조로는 한계가 생기는가

초기 서비스나 소규모 환경에서는 하나의 서버에 웹 서버, 애플리케이션, 데이터 저장 기능을 함께 올려서도 운영할 수 있음.

이 방식은 빠르게 시작할 수 있다는 장점이 있음.

하지만 시스템 규모가 커지면 다음 문제가 발생함.

  • 웹 요청 처리와 애플리케이션 로직이 섞여 역할이 불명확해짐
  • 데이터베이스가 애플리케이션과 같은 보안 경계에 놓이게 됨
  • 특정 기능만 확장하고 싶어도 전체 서버를 함께 키워야 함
  • 한 부분의 장애가 전체 장애로 확산되기 쉬움
  • 배포 시 전체 시스템 영향 범위가 커짐
  • 운영 책임이 뒤엉켜 문제 분석이 어려워짐

즉, 단순 구조는 시작은 쉬우나 규모가 커질수록 확장성, 보안성, 운영성, 복원성 측면에서 한계가 드러남.

1.3 멀티 티어 아키텍처의 기본 개념

멀티 티어 아키텍처는 애플리케이션을 역할별로 여러 계층으로 나누어 설계하는 방식임.

가장 대표적인 형태는 3계층 구조임.

사용자
  │
Presentation / Web Tier
  │
Application Tier
  │
Data Tier

이 구조는 단순히 서버를 여러 대 두는 방식이 아님.

핵심은 역할 분리, 보안 경계 분리, 확장 단위 분리, 장애 영향 범위 분리에 있음.

1.4 각 계층의 역할

1.4.1 Web Tier

Web Tier는 외부 요청을 가장 먼저 수신하는 계층임.

일반적으로 사용자와 가장 가까운 위치에 있으며, 외부 노출이 허용되는 계층이기도 함.

대표 구성 요소

  • Route 53
  • CloudFront
  • WAF
  • ALB
  • Nginx / Apache 웹 서버
  • 정적 콘텐츠 진입점

주요 역할

  • 사용자 요청 수신
  • TLS 종료
  • 정적/동적 요청 분기
  • 요청 라우팅
  • 외부 노출 지점 최소화
  • 1차 보안 통제

즉, Web Tier는 애플리케이션의 “입구” 역할을 담당함.

1.4.2 Application Tier

Application Tier는 실제 비즈니스 로직이 수행되는 계층임.

사용자의 요청을 받아 계산, 검증, 처리, 응답 생성 작업을 수행함.

대표 구성 요소

  • EC2 기반 애플리케이션 서버
  • ECS / Fargate 기반 컨테이너 애플리케이션
  • EKS 기반 워크로드
  • Lambda 함수
  • 내부 API 서비스

주요 역할

  • 인증 및 인가 처리
  • 비즈니스 규칙 실행
  • API 응답 생성
  • 외부 서비스 연동
  • 데이터 계층과의 통신

즉, App Tier는 서비스의 핵심 기능을 수행하는 “두뇌” 역할을 담당함.

1.4.3 Data Tier

Data Tier는 데이터를 저장하고 조회하는 계층임.

애플리케이션 상태와 핵심 비즈니스 데이터를 보관하므로 가장 민감한 계층에 속함.

대표 구성 요소

  • Amazon RDS
  • Amazon Aurora
  • Amazon DynamoDB
  • Amazon ElastiCache for Redis
  • Amazon S3
  • Amazon EFS

주요 역할

  • 트랜잭션 데이터 저장
  • 세션/캐시 저장
  • 객체 저장
  • 공유 파일 저장
  • 데이터 영속성 보장

즉, Data Tier는 서비스의 “기억 장치” 역할을 담당함.

1.5 계층 분리가 필요한 이유

멀티 티어 구조는 보기 좋게 나누기 위한 구성이 아니라, 실제 운영과 장애 대응을 위한 핵심 설계 원칙임.

1.5.1 책임 분리

계층별 역할이 다르면 변경 범위를 제어하기 쉬워짐.

예를 들어

  • Web Tier는 요청 수신과 전달만 담당
  • App Tier는 비즈니스 로직만 담당
  • Data Tier는 저장과 조회만 담당

이렇게 나누면 특정 계층에서 문제가 발생했을 때 원인을 좁히기 쉬움.

또한 배포, 성능 튜닝, 보안 정책 적용도 계층별로 다르게 가져갈 수 있음.

즉, 책임 분리는 운영 복잡도를 낮추는 첫 번째 원칙임.

1.5.2 보안 경계 분리

모든 리소스를 외부와 직접 통신하게 두면 공격 표면이 넓어짐.

따라서 일반적으로는 다음과 같이 설계함.

  • 인터넷과 직접 통신하는 계층은 최소화
  • App Tier는 Private Subnet에 배치
  • DB는 Public IP 없이 내부 통신만 허용
  • Security Group으로 계층 간 접근만 허용
  • Secrets는 코드나 로컬 파일이 아니라 별도 서비스에 저장

예를 들어 App 서버만 DB에 접근 가능하게 하고, 사용자는 DB에 직접 도달할 수 없도록 설계함.

즉, 멀티 티어 구조는 방어 심층화(Defense in Depth) 를 구현하기 쉬운 구조임.

1.5.3 독립 확장

서비스 부하는 모든 계층에 동일하게 발생하지 않음.

예를 들어

  • 사용자 접속 증가 → ALB / App Tier 확장 필요
  • 읽기 요청 급증 → 캐시 또는 Read Replica 확장 필요
  • 파일 업로드 증가 → S3 중심 설계 필요
  • 정적 콘텐츠 증가 → CloudFront 캐시 활용 필요

단일 구조에서는 전체 시스템을 함께 키워야 하지만, 계층이 분리되어 있으면 병목이 발생한 부분만 선택적으로 확장 가능함.

즉, 멀티 티어 구조는 수평 확장과 자원 최적화의 기반이 됨.

1.5.4 장애 격리

단일 서버 구조에서는 한 부분이 고장 나면 전체 시스템이 함께 영향을 받기 쉬움.

반면 멀티 티어 구조에서는 장애 영향을 계층 단위로 격리할 수 있음.

예시

  • App 인스턴스 1대 장애 → ALB가 정상 인스턴스로 우회
  • 한 AZ 장애 → Multi-AZ 배치로 일부 서비스 지속
  • Redis 장애 → 일시적으로 DB 직접 조회로 fallback
  • 배치 작업 지연 → API 처리 계층과 분리되어 사용자 영향 최소화

즉, 멀티 티어 구조는 장애를 없애는 구조가 아니라, 장애의 영향을 제한하는 구조임.

1.6 AWS에서 멀티 티어 아키텍처를 구현하는 방식

AWS에서 멀티 티어 구조는 특정 서비스 하나로 구현되지 않음.

여러 서비스를 계층 역할에 맞게 조합해서 구현함.

대표 구성 요소

  • VPC
  • Public / Private Subnet
  • Route Table
  • Internet Gateway / NAT Gateway
  • Security Group / NACL
  • Route 53
  • CloudFront
  • WAF
  • ALB / NLB
  • EC2 / ECS / EKS / Lambda
  • RDS / Aurora / DynamoDB / ElastiCache / S3 / EFS
  • CloudWatch
  • Auto Scaling
  • Backup 서비스

즉, 멀티 티어 아키텍처는 AWS 서비스를 나열한 결과가 아니라,

각 서비스에 명확한 역할을 부여해 계층별로 배치한 결과물임.

1.7 대표적인 AWS 멀티 티어 아키텍처 예시

전형적인 구조는 다음과 같음.

사용자
  │
Route 53
  │
CloudFront
  │
AWS WAF
  │
ALB
  │
App Tier (EC2 / ECS / EKS / Lambda)
  │
Data Tier (RDS / Aurora / DynamoDB / Redis / S3)

이를 AWS 인프라 관점에서 조금 더 세분화하면 다음과 같이 볼 수 있음.

각 요소의 의미

  • Route 53: DNS 질의 응답 및 서비스 진입점 제공
  • CloudFront: 전 세계 사용자 대상 콘텐츠 캐싱 및 전송 가속
  • WAF: 웹 계층 보안 통제
  • ALB: HTTP/HTTPS 요청 분산 및 경로 기반 라우팅
  • App Tier: 실제 비즈니스 로직 처리
  • Data Tier: 영속 데이터, 캐시, 객체 저장소 담당

즉, 고급 멀티 티어 아키텍처는 네트워크, 보안, 컴퓨팅, 데이터, 운영 요소가 함께 결합된 구조임.

1.8 AWS Well-Architected Framework와 설계 판단 기준

고급 아키텍처 설계에서는 AWS Well-Architected Framework를 단순 암기 대상으로 보면 안 됨.

이 프레임워크는 실제 설계 판단 기준으로 사용해야 함.

AWS Well-Architected Framework는 다음 6개 Pillar 로 구성됨.

  • Operational Excellence
  • Security
  • Reliability
  • Performance Efficiency
  • Cost Optimization
  • Sustainability

즉, Well-Architected는 “좋은 구조인지 아닌지”를 판단하는 체크리스트이자 설계 관점임.

1.8.1 Operational Excellence

운영 우수성은 시스템을 효율적으로 운영하고, 변화에 대응하며, 반복 가능한 방식으로 관리할 수 있는가를 보는 관점임.

주요 질문

  • 인프라를 수작업이 아니라 IaC로 관리하는가
  • 표준화된 배포 방식이 있는가
  • 로그와 메트릭, 추적 정보를 수집하는가
  • 운영자가 문제를 빠르게 탐지할 수 있는가
  • 반복 작업을 자동화했는가

핵심은 사람이 기억에 의존해 운영하지 않는 구조를 만드는 것임.

1.8.2 Security

보안은 IAM 설정만 의미하지 않음.

네트워크, 데이터, 애플리케이션, 운영 전반을 함께 고려해야 함.

주요 질문

  • 어떤 계층이 외부에 노출되는가
  • 최소 권한 원칙이 지켜지는가
  • 데이터가 암호화되는가
  • 비밀정보를 안전하게 저장하는가
  • 로그와 감사 추적이 남는가
  • 침해 가능성을 줄이는 구조인가

보안은 기능 추가가 아니라 처음부터 구조 안에 포함되어야 하는 설계 기준임.

1.8.3 Reliability

신뢰성은 장애를 견디고 복구할 수 있는 능력을 의미함.

주요 질문

  • 단일 장애점이 존재하는가
  • 다중 AZ 구성이 되어 있는가
  • 자동 복구가 가능한가
  • 백업과 복원 절차가 준비되어 있는가
  • 장애 조치(failover)가 가능한가
  • 장애 시 시스템이 완전히 멈추지 않는가

즉, 신뢰성은 “장애가 없을 것”을 가정하는 것이 아니라,

장애가 발생해도 계속 운영 가능한 구조인가를 보는 관점임.

1.8.4 Performance Efficiency

성능 효율성은 무조건 큰 인스턴스를 쓰는 것이 아님.

필요한 성능을 가장 적절한 방식으로 확보하는 것이 중요함.

주요 질문

  • CDN으로 지연 시간을 줄일 수 있는가
  • 캐시를 도입할 수 있는가
  • 서버리스가 더 적합한가
  • 컨테이너가 더 적합한가
  • 병렬 처리가 가능한 구조인가
  • 읽기 부하를 분산할 수 있는가

즉, 성능 효율성은 기술 선택과 구조 선택의 문제임.

1.8.5 Cost Optimization

비용 최적화는 단순히 저렴한 서비스를 선택하는 것이 아님.

필요한 수준의 성능과 가용성을 유지하면서 불필요한 낭비를 줄이는 설계가 중요함.

주요 질문

  • 과도하게 큰 인스턴스를 계속 유지하고 있지 않은가
  • Auto Scaling으로 사용량에 따라 증감할 수 있는가
  • 관리형 서비스를 사용해 운영비를 줄일 수 있는가
  • 스토리지 계층화를 적용할 수 있는가
  • 캐시로 DB 비용을 줄일 수 있는가

즉, 비용 최적화는 “싸게 하자”가 아니라

구조적으로 낭비를 줄이자는 관점임.

1.8.6 Sustainability

지속 가능성은 자원을 효율적으로 사용해 환경 영향을 줄이는 관점임.

주요 질문

  • 과도한 리소스를 계속 켜두고 있지 않은가
  • 사용량에 따라 자동으로 줄어드는 구조인가
  • 서버리스나 관리형 서비스를 활용해 효율을 높일 수 있는가
  • 데이터 보관 정책을 정리해 불필요한 저장을 줄이고 있는가

즉, Sustainability는 단지 친환경 구호가 아니라

효율적인 자원 사용과 운영 방식 개선으로 이어지는 설계 관점임.

1.9 고급 아키텍처 설계 시 반드시 던져야 할 질문

고급 아키텍트는 서비스를 많이 아는 사람이라기보다,

설계 전에 올바른 질문을 먼저 던질 수 있는 사람이어야 함.

핵심 질문은 다음과 같음.

1.9.1 외부에 직접 노출되어야 하는 계층은 어디인가

모든 서버가 인터넷과 직접 통신하면 안 됨.

일반적으로 외부 노출은 ALB, CloudFront, WAF 같은 진입 계층으로 제한함.

1.9.2 어떤 계층을 Private으로 둘 것인가

App Tier와 Data Tier는 가능하면 Private Subnet에 두는 것이 일반적임.

이렇게 해야 직접 접근 경로를 줄이고 공격 표면을 최소화할 수 있음.

1.9.3 병목은 어디에서 먼저 발생할 것인가

웹 서버, 애플리케이션 서버, DB, 캐시, 네트워크 중 어디가 한계에 먼저 도달할지 예상해야 함.

그래야 사전에 확장 전략을 세울 수 있음.

1.9.4 장애 시 어떤 방식으로 유지할 것인가

고급 설계에서는 장애를 가정해야 함.

예를 들어 다음 상황을 각각 따로 검토해야 함.

  • 인스턴스 1대 장애
  • 특정 AZ 장애
  • DB 장애
  • 캐시 장애
  • 외부 API 장애
  • 운영자 실수

즉, “장애가 나면 어떻게 될까”가 아니라

“장애가 나더라도 무엇이 계속 살아남아야 하는가” 를 먼저 생각해야 함.

1.9.5 상태를 어디에 저장할 것인가

애플리케이션 서버 내부에 상태를 저장하면 교체와 확장이 어려워짐.

따라서 상태 저장 위치를 명확히 분리해야 함.

예시

  • 세션 정보 → Redis
  • 업로드 파일 → S3 또는 EFS
  • 비즈니스 데이터 → RDS / DynamoDB
  • 설정값/비밀값 → Systems Manager Parameter Store / Secrets Manager

1.9.6 관리형 서비스로 대체 가능한가

직접 설치하고 운영하는 방식이 항상 최선은 아님.

예를 들어

  • 직접 DB 설치 대신 RDS
  • 직접 Redis 운영 대신 ElastiCache
  • 직접 서버 확장 대신 Auto Scaling
  • 직접 배포 자동화 대신 관리형 CI/CD 서비스 활용

고급 설계에서는 “내가 운영할 수 있는가”보다

“굳이 내가 직접 운영해야 하는가” 를 먼저 검토해야 함.

1.10 상태 비저장(Stateless) 설계의 중요성

고급 아키텍처에서는 Web Tier와 App Tier를 가능하면 Stateless 하게 설계하는 것이 매우 중요함.

Stateless 설계란, 특정 요청을 처리하는 데 필요한 상태가 서버 로컬 메모리나 로컬 디스크에 강하게 묶여 있지 않은 구조를 말함.

이 방식이 중요한 이유

  • Auto Scaling이 쉬움
  • 장애 발생 시 다른 인스턴스로 대체하기 쉬움
  • 무중단 배포가 쉬움
  • 동일 역할 인스턴스를 여러 대 두기 쉬움
  • 특정 서버에 세션이 고정되지 않음

예를 들어 로그인 세션을 웹 서버 메모리에 저장하면, 해당 서버가 내려갔을 때 사용자가 다시 로그인해야 할 수 있음.

반면 Redis 같은 외부 저장소에 세션을 저장하면 여러 인스턴스가 같은 상태를 공유할 수 있음.

즉, 현대적 아키텍처에서는 서버가 상태를 오래 들고 있기보다

처리 로직에 집중하고, 상태는 외부 저장소에 위임하는 구조를 선호함.

1.11 고급 아키텍처에서 자주 사용하는 설계 원칙

이 과정 전체에서 공통으로 적용할 설계 원칙을 먼저 정리하면 다음과 같음.

1.11.1 단일 장애점을 만들지 않음

서버 1대, AZ 1개, NAT Gateway 1개, 수동 승인 프로세스 1개 등

하나에만 의존하는 구조는 위험함.

1.11.2 외부 노출을 최소화함

인터넷과 직접 통신하는 리소스는 꼭 필요한 것만 두고,

나머지는 내부 경계 뒤로 숨기는 것이 기본 원칙임.

1.11.3 상태를 처리 계층에서 분리함

애플리케이션 서버가 상태를 독점하면 확장과 교체가 어려워짐.

세션, 파일, 비밀값, 핵심 데이터는 외부 저장소로 분리하는 것이 유리함.

1.11.4 수평 확장을 우선 고려함

큰 서버 1대를 계속 키우는 수직 확장보다,

동일 역할의 서버 여러 대를 두는 수평 확장이 고가용성과 운영 측면에서 더 유리한 경우가 많음.

1.11.5 관리형 서비스를 우선 검토함

직접 운영이 반드시 필요한 특별한 이유가 없다면,

AWS 관리형 서비스를 우선 검토하는 것이 일반적으로 더 안정적이고 운영 부담이 적음.

1.11.6 자동화를 전제로 설계함

좋은 구조는 콘솔 클릭 순서를 기억하는 구조가 아님.

누가 다시 구축해도 동일한 결과를 재현할 수 있어야 함.

즉,

  • IaC
  • CI/CD
  • 자동 배포
  • 자동 복구
  • 자동 확장
  • 자동 백업

을 기본 전제로 생각해야 함.

1.11.7 관측 가능성(Observability)을 함께 설계함

운영 중 문제가 생겼을 때 보이지 않는 시스템은 관리하기 어려움.

따라서 처음부터 다음 요소를 함께 설계해야 함.

  • 메트릭 수집
  • 로그 수집
  • 분산 추적
  • 경보
  • 대시보드

즉, “운영 후에 붙이는 모니터링”이 아니라

처음부터 보이게 설계하는 것이 중요함.

1.12 엔터프라이즈 환경에서 추가로 고려해야 할 요소

실습 환경에서는 하나의 AWS 계정과 단순한 VPC만으로도 충분할 수 있음.

하지만 실제 조직 환경에서는 고려해야 할 범위가 더 넓어짐.

대표 요소

  • 멀티 계정 구조
  • 중앙 보안 정책
  • 공용 네트워크 허브 구조
  • 중앙 감사 로그 수집
  • 백업 표준화
  • 비용 배부와 가시성 확보
  • 공통 서비스 공유 구조
  • 표준 계정 생성 및 거버넌스

예를 들어 조직 전체 관점에서는 단일 애플리케이션의 ALB 하나보다,

여러 계정에 배포된 수십 개 시스템을 어떻게 통제하고 표준화할 것인가가 더 중요한 이슈가 될 수 있음.

즉, 고급 아키텍처는 애플리케이션 한 개의 구조를 넘어서

조직 전체 운영 구조와 거버넌스까지 포함하는 설계 문제로 확장됨.

1.13 현대적 플랫폼에서 멀티 티어 구조를 구현하는 방법

멀티 티어 구조는 EC2 기반으로만 구현되는 것이 아님.

본질은 계층 분리에 있고, 구현 방식은 다양하게 선택할 수 있음.

App Tier 예시

  • EC2 기반 애플리케이션 서버
  • ECS / Fargate 기반 컨테이너
  • EKS 기반 쿠버네티스 워크로드
  • Lambda 기반 서버리스 함수

Data Tier 예시

  • RDS / Aurora
  • DynamoDB
  • ElastiCache for Redis
  • S3
  • EFS

즉, 멀티 티어 아키텍처의 핵심은 특정 서비스 이름이 아니라

각 계층의 역할을 어떻게 분리하고 연결할 것인가에 있음.

1.14 장 요약

  • 고급 아키텍처 설계는 구조적 의사결정의 문제임
  • 멀티 티어 아키텍처는 역할, 보안, 확장, 장애 범위를 분리하는 구조임
  • Web / App / Data Tier는 각각 진입, 처리, 저장 역할을 담당함
  • 계층 분리는 책임 분리, 보안 경계 형성, 독립 확장, 장애 격리를 가능하게 함
  • AWS Well-Architected Framework는 6개 Pillar로 구성됨
  • 고급 설계에서는 장애, 상태 저장 위치, 외부 노출 범위, 관리형 서비스 활용 여부를 먼저 검토해야 함
  • Stateless 설계와 수평 확장은 현대적 아키텍처의 핵심 원칙임
  • 엔터프라이즈 환경에서는 멀티 계정, 거버넌스, 중앙 통제가 추가로 중요해짐

1.15 한 줄 정리

고급 멀티 티어 아키텍처 설계는 AWS 서비스를 많이 아는 것이 아니라,
계층 분리를 기반으로 보안, 가용성, 확장성, 운영성, 비용, 지속 가능성까지 함께 고려해
왜 이 구조를 선택했는지 설명할 수 있는 능력이다.
