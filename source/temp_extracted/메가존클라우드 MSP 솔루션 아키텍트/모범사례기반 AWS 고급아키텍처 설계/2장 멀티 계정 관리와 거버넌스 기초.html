2장 멀티 계정 관리와 거버넌스 기초

2.1 멀티 계정이 필요한 이유

AWS를 처음 학습할 때는 보통 하나의 계정 안에서 모든 리소스를 생성함.

실습용으로는 이 방식이 가장 단순하고 이해하기도 쉬움.

하지만 실제 조직 환경에서는 하나의 계정에 모든 것을 넣는 방식이 금방 한계를 드러냄.

대표적인 문제는 다음과 같음.

  • 운영 환경과 개발 환경이 뒤섞임
  • 실수로 운영 리소스를 변경할 위험이 커짐
  • 비용 구분이 어려움
  • 보안 권한을 세밀하게 나누기 어려움
  • 로그와 감사 데이터를 안전하게 분리하기 어려움
  • 여러 팀이 같은 계정을 쓰면 책임 경계가 모호해짐

즉, AWS 계정은 단순 로그인 단위가 아니라 보안 경계이자 관리 경계임.

그래서 엔터프라이즈 환경에서는 멀티 계정 구조가 사실상 기본이 됨.

2.2 AWS 계정을 어떻게 바라봐야 하는가

초급 단계에서는 AWS 계정을 “리소스를 만드는 공간” 정도로 이해하기 쉬움.

하지만 고급 아키텍처에서는 AWS 계정을 다음처럼 봐야 함.

  • 보안 경계
  • 비용 경계
  • 운영 경계
  • 권한 경계
  • 감사 경계

즉, 계정을 적절히 분리한다는 것은 단순 정리가 아니라

위험을 나누고 책임을 분리하는 설계라고 봐야 함.

2.3 단일 계정 구조의 한계

단일 계정 구조는 작은 팀이나 초기 실습에는 적합할 수 있음.

하지만 아래와 같은 상황부터는 빠르게 복잡해짐.

  • 개발자와 운영자가 같은 계정을 사용함
  • 여러 프로젝트가 동시에 존재함
  • 운영/테스트/개발 환경을 분리해야 함
  • 보안팀과 플랫폼팀이 따로 존재함
  • 비용을 조직별로 구분해야 함

이 경우 하나의 계정 안에서 IAM만으로 모든 문제를 해결하려 하면 정책이 점점 복잡해지고, 실수 가능성도 커짐.

즉, 단일 계정 구조는 단순하지만

규모가 커질수록 안전성과 운영성이 떨어질 수 있음.

2.4 멀티 계정 구조의 핵심 목적

멀티 계정 구조는 단순히 계정을 많이 만드는 것이 아님.

목적은 명확해야 함.

1. 환경 분리

운영, 개발, 테스트를 분리함.

2. 보안 분리

민감한 리소스와 권한을 격리함.

3. 비용 가시성

팀별, 프로젝트별 비용 구분이 쉬워짐.

4. 운영 책임 분리

어떤 계정이 어떤 용도인지 명확해짐.

5. 사고 영향 범위 축소

하나의 계정에서 사고가 나더라도 전체 영향이 줄어듦.

즉, 멀티 계정의 본질은 복잡성을 늘리는 것이 아니라 위험을 나누는 것임.

2.5 대표적인 멀티 계정 구조

엔터프라이즈 환경에서는 보통 다음 같은 구조를 많이 사용함.

관리 루트
 ├ 보안 계정
 ├ 로그 아카이브 계정
 ├ 공유 서비스 계정
 ├ 운영 계정
 ├ 개발 계정
 └ 테스트 계정

이 구조는 모든 조직에 반드시 동일하게 적용되는 것은 아니지만, 기본 사고방식은 매우 중요함.

즉, “모든 것을 한 계정에 넣지 않는다”는 원칙부터 잡는 것이 중요함.

2.6 운영 계정과 개발 계정 분리

가장 기본적인 멀티 계정 분리 방식은 운영 계정과 비운영 계정 분리임.

이유는 다음과 같음.

  • 운영 계정은 더 강한 보안과 변경 통제가 필요함
  • 개발 계정은 더 자유로운 실험과 빠른 변경이 필요함
  • 두 환경의 목적이 다름
  • 장애와 실수의 영향 범위를 분리할 수 있음

즉, 운영 계정은 안정성과 통제가 중요하고,

개발 계정은 유연성과 속도가 중요함.

그래서 둘을 같은 공간에서 운영하는 것은 바람직하지 않음.

2.7 보안 계정과 로그 아카이브 계정의 의미

고급 환경에서는 보안 관련 기능을 별도 계정으로 분리하는 경우가 많음.

2.7.1 보안 계정

보안 계정은 조직 전체의 보안 도구와 중앙 통제를 담당하는 계정임.

예

  • 중앙 보안 모니터링
  • 보안 정책 집계
  • 보안 이벤트 분석
  • 일부 중앙 감사 기능

의미는 다음과 같음.

운영 워크로드 계정과 보안 통제 계정을 분리한다.

즉, 보호 대상과 통제 도구를 같은 계정에만 두지 않겠다는 사고방식임.

2.7.2 로그 아카이브 계정

조직 전체의 로그를 장기간 안전하게 보관하는 계정임.

예

  • CloudTrail 로그
  • Config 기록
  • VPC Flow Logs
  • 보안 감사 로그

이 계정을 별도로 두는 이유는 매우 중요함.

  • 운영 계정이 침해되더라도 로그 보존 가능성을 높임
  • 로그 변조 가능성을 줄임
  • 장기 감사와 추적이 쉬워짐

즉, 로그는 단순 파일이 아니라 감사 증적이므로 원본 환경과 분리해 두는 것이 좋음.

2.8 공유 서비스 계정의 의미

공유 서비스 계정은 조직 공통으로 사용하는 리소스를 모아 두는 계정임.

예

  • 공용 네트워크 허브
  • 공용 보안 도구
  • 공용 이미지 저장소
  • 일부 중앙 관리 시스템

이런 계정을 따로 두는 이유는 다음과 같음.

  • 여러 워크로드 계정이 같은 공통 서비스를 사용할 수 있음
  • 공통 자원의 운영 책임이 분리됨
  • 아키텍처가 더 표준화됨

즉, 공유 서비스 계정은 멀티 계정 구조에서 공통 기반 계층 역할을 함.

2.9 IAM을 멀티 계정 관점에서 다시 보기

초급 단계에서는 IAM을 “사용자/그룹/역할/정책” 정도로 배움.

하지만 멀티 계정 환경에서는 IAM을 더 넓게 봐야 함.

핵심 관점은 다음과 같음.

  • 누가 어떤 계정에 접근하는가
  • 어느 계정에서 어떤 역할을 Assume 하는가
  • 공통 권한과 계정별 권한을 어떻게 나누는가
  • 사람 중심 접근과 서비스 중심 접근을 어떻게 분리하는가

즉, 멀티 계정 환경에서 IAM은 단순 권한 설정이 아니라

계정 간 신뢰와 접근 구조를 설계하는 도구가 됨.

2.10 IAM 사용자 중심 구조의 한계

멀티 계정 환경에서 계정마다 IAM User를 일일이 만드는 방식은 점점 관리가 어려워짐.

문제점

  • 계정마다 사용자 생성/삭제 반복
  • 권한 일관성 유지 어려움
  • 비밀번호와 MFA 관리 복잡
  • 퇴사/이동 시 정리 부담 큼
  • 계정 수가 늘수록 운영 비용 증가

즉, 계정 수가 적을 때는 가능할 수 있어도

조직 규모가 커지면 사람 계정을 계정마다 직접 관리하는 방식은 비효율적임.

2.11 Role 중심 접근의 중요성

멀티 계정 구조에서는 보통 Role 중심 접근이 더 중요해짐.

기본 사고방식은 다음과 같음.

사람은 중앙 인증 체계를 통해 로그인하고,
필요한 계정에서 필요한 역할을 Assume 해서 작업한다.

이 방식의 장점

  • 권한 경계를 역할 단위로 명확히 나눌 수 있음
  • 계정별 사용자 계정을 많이 만들지 않아도 됨
  • 최소 권한 원칙 적용이 쉬움
  • 감사 로그 추적이 쉬워짐

즉, 멀티 계정 환경에서는 “유저를 많이 만드는 구조”보다

역할을 설계하는 구조가 더 중요함.

2.12 최소 권한 원칙을 멀티 계정에서 적용하는 방법

최소 권한 원칙은 단일 계정에서도 중요하지만, 멀티 계정 환경에서 더 중요해짐.

멀티 계정에서는 다음 두 수준에서 최소 권한을 봐야 함.

계정 수준

누가 어느 계정까지 접근 가능한가

리소스 수준

그 계정 안에서 어떤 리소스에 어떤 작업을 할 수 있는가

즉, 최소 권한은 단순히 “S3 읽기만 허용” 같은 수준을 넘어서

접근 가능한 계정 범위 자체를 제한하는 것도 포함함.

2.13 AWS Organizations 개요

AWS Organizations는 여러 AWS 계정을 중앙에서 관리할 수 있게 해주는 서비스임.

멀티 계정 구조의 핵심 기반이라고 봐도 됨.

Organizations를 사용하면 다음이 가능해짐.

  • 계정들을 한 조직으로 묶음
  • 조직 단위 결제 관리
  • 계정 그룹화
  • 정책 중앙 적용
  • 계정 생성/관리 표준화 기반 제공

즉, Organizations는 멀티 계정의 “모음 기능”이 아니라

중앙 통제와 표준화의 기반임.

2.14 Organizations의 핵심 개념

Organizations를 이해할 때 중요한 개념은 다음과 같음.

  • Management Account
  • Member Account
  • Organizational Unit
  • Service Control Policy

2.14.1 Management Account

조직 전체를 관리하는 중심 계정임.

예전에는 Master Account라고 부르던 개념과 연결되지만, 현재는 보통 Management Account라고 표현함.

이 계정은 조직 수준 설정, 정책 배포, 계정 관리를 담당함.

즉, Management Account는 강력하지만

실제 워크로드를 많이 두는 계정으로 사용하는 것은 일반적으로 권장되지 않음.

2.14.2 Member Account

조직에 속한 개별 계정임.

운영, 개발, 보안, 로그 보관, 공유 서비스 등의 역할을 가진 계정들이 여기에 해당함.

즉, 실제 워크로드는 대개 Member Account에 위치하게 됨.

2.14.3 Organizational Unit (OU)

OU는 여러 계정을 논리적으로 묶는 단위임.

예

Root
 ├ Security OU
 ├ Infrastructure OU
 ├ Workloads OU
 │   ├ Prod Account
 │   ├ Dev Account
 │   └ Test Account
 └ Sandbox OU

OU를 사용하는 이유

  • 비슷한 성격의 계정을 묶음
  • 정책 적용 범위를 그룹 단위로 나눔
  • 운영 구조를 더 체계적으로 정리 가능

즉, OU는 계정 분류 체계이자 정책 적용 경계임.

2.15 SCP(Service Control Policy) 개요

SCP는 Organizations에서 사용하는 중앙 정책 통제 방식임.

IAM 정책과 비슷해 보일 수 있지만 역할이 다름.

핵심은 다음과 같음.

IAM이 "허용할 수 있는 권한"을 주는 도구라면,
SCP는 "그 계정에서 절대 할 수 없는 범위"를 제한하는 상위 경계다.

즉, SCP는 권한을 직접 부여하는 도구라기보다

계정 또는 OU가 가질 수 있는 최대 권한 범위를 제한하는 도구임.

2.16 IAM Policy와 SCP 차이

이 둘은 매우 자주 혼동됨.

반드시 구분해서 설명해야 함.

항목IAM PolicySCP
적용 범위사용자, 그룹, 역할계정, OU, 조직
목적권한 부여 또는 제한최대 권한 범위 제한
사용 위치계정 내부Organizations 중앙 통제
의미개별 권한 정책상위 가드레일

즉,

  • IAM Policy는 “무엇을 할 수 있는가”
  • SCP는 “아무리 IAM이 있어도 이건 못 한다”

를 정의하는 것에 가까움.

2.17 SCP가 필요한 이유

멀티 계정 환경에서는 개별 계정 관리자에게 많은 권한이 있을 수 있음.

이때 조직 차원에서 반드시 막고 싶은 작업이 있을 수 있음.

예

  • 특정 리전 사용 금지
  • 특정 서비스 사용 금지
  • 보안 관련 설정 삭제 금지
  • CloudTrail 중지 금지

이런 요구를 계정마다 개별 IAM으로만 통제하면 관리가 매우 어려움.

그래서 SCP로 상위 경계를 거는 것임.

즉, SCP는 멀티 계정 환경의 중앙 가드레일 역할을 함.

2.18 태그, 표준화, 계정 구조의 관계

멀티 계정 구조를 만들었다고 해서 거버넌스가 자동 완성되는 것은 아님.

실제로는 계정 구조 위에 다음이 같이 필요함.

  • 태그 표준
  • 네이밍 표준
  • 권한 모델 표준
  • 로깅 표준
  • 비용 분류 기준
  • 배포 표준

즉, 거버넌스는 계정을 나누는 것만이 아니라

계정을 일관되게 운영하는 규칙 체계까지 포함함.

2.19 AWS Control Tower 개요

Control Tower는 멀티 계정 환경을 좀 더 쉽게 시작하고 표준화된 형태로 관리할 수 있도록 도와주는 서비스임.

쉽게 말하면 다음과 같음.

멀티 계정 환경의 초기 구조와 기본 가드레일을 더 쉽게 마련하도록 돕는 서비스

2.20 Control Tower를 어느 정도까지 이해하면 되는가

  • Organizations 기반으로 동작함
  • 랜딩존 개념과 연결됨
  • 기본 계정 구조와 일부 가드레일 구성을 돕는 서비스임
  • 엔터프라이즈 멀티 계정 시작을 빠르게 할 수 있음

멀티 계정 표준화 도구 정도로 이해하면 충분함.

2.21 랜딩존 관점에서 계정 구조 보기

고급 환경에서는 랜딩존이라는 표현을 자주 씀.

이는 AWS 멀티 계정 환경을 본격적으로 운영하기 위한 초기 기반 구조를 의미함.

보통 여기에 포함되는 것

  • Organizations 구조
  • 핵심 계정 분리
  • 기본 보안 통제
  • 중앙 로그 보관
  • 기본 네트워크 방향성
  • 계정 생성 표준화

즉, 랜딩존은 계정 몇 개 만든 상태가 아니라

조직이 AWS를 안전하게 사용할 수 있도록 깔아 둔 기반 환경이라고 보면 됨.

2.22 비용 관점에서 멀티 계정이 가지는 의미

멀티 계정은 보안만을 위한 것이 아님.

비용 분석과 책임 분리에도 매우 중요함.

예를 들어 계정을 나누면 다음이 쉬워짐.

  • 프로젝트별 비용 분리
  • 운영/개발 환경 비용 비교
  • 조직별 예산 추적
  • 사용량 책임 명확화

즉, 계정은 보안 경계이면서 동시에 비용 회계 단위로도 의미가 큼.

2.23 감사와 로그 보존 관점

멀티 계정 구조에서 특히 중요한 것이 감사 가능성임.

누가 무엇을 했는지, 어떤 변경이 있었는지, 어떤 설정이 바뀌었는지를 추적할 수 있어야 함.

그래서 일반적으로 중요해지는 것

  • 중앙 CloudTrail 로그 보관
  • Config 기록 보존
  • 로그 아카이브 계정 분리
  • 보안 계정에서 통합 조회

즉, 멀티 계정 구조는 단순 분산이 아니라

중앙 감사 체계를 가능하게 하는 기반이기도 함.

2.24 멀티 계정 환경에서 자주 하는 실수

1. 계정만 많이 만들고 기준이 없음

왜 나눴는지 기준이 없으면 오히려 복잡성만 증가함.

2. 운영 계정과 개발 계정을 충분히 분리하지 않음

실수나 테스트가 운영에 영향을 줄 수 있음.

3. 로그를 원본 계정 안에만 둠

감사 증적의 안전성이 떨어질 수 있음.

4. IAM User를 계정마다 반복 생성함

운영 부담이 커지고 일관성이 떨어짐.

5. SCP와 IAM 역할을 혼동함

상위 제한과 개별 권한 부여를 구분하지 못하면 설계가 꼬이기 쉬움.

즉, 멀티 계정은 “많이 만드는 것”보다 왜, 어떻게 나누는가가 더 중요함.

2.25 솔루션아키텍트 관점에서 꼭 기억할 것

  • 왜 운영/개발 계정을 나누는가
  • 왜 로그 아카이브 계정을 따로 두는가
  • Organizations가 왜 필요한가
  • OU가 어떤 의미인가
  • SCP가 IAM과 어떻게 다른가
  • Control Tower가 무엇을 쉽게 해주는가

즉, 세부 운영 명령보다

구조적 이유를 설명할 수 있는 것이 더 중요함.

2.27 한 줄 정리

멀티 계정 구조는 AWS 계정을 많이 만드는 것이 아니라,
보안, 운영, 비용, 감사의 경계를 분리해서
조직이 AWS를 더 안전하고 일관되게 사용할 수 있도록 만드는 거버넌스 구조다.
