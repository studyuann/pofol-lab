3장 고급 네트워크 연결 아키텍처

3.1 고급 네트워크 연결 아키텍처의 의미

AWS에서 네트워크를 설계할 때 초반에는 보통 하나의 VPC 안에서 서브넷을 나누고, 인터넷 게이트웨이와 NAT 게이트웨이를 배치하는 수준으로 시작함.

하지만 실제 운영 환경으로 가면 네트워크 설계 범위가 단일 VPC를 넘어서기 시작함.

예를 들어 다음과 같은 요구사항이 생김.

  • 여러 VPC를 서로 연결해야 함
  • 여러 계정의 VPC를 중앙에서 통합 관리해야 함
  • 특정 AWS 서비스에는 인터넷을 거치지 않고 사설 경로로 접근해야 함
  • 네트워크 구조를 허브-앤-스포크 형태로 설계해야 함
  • 공통 서비스망과 워크로드망을 분리하면서도 연결해야 함

즉, 고급 네트워크 연결 아키텍처는 단순히 “연결된다” 수준이 아니라

보안, 확장성, 운영성, 중앙 통제, 트래픽 흐름까지 함께 고려하는 설계 영역임.

3.2 왜 고급 네트워크 연결 구조가 필요한가

단일 VPC 구조는 단순하고 이해하기 쉬움.

하지만 서비스 수, 계정 수, 조직 수가 늘어나면 다음 문제가 발생함.

  • VPC 간 연결 관계가 많아짐
  • 공통 서비스와 개별 워크로드를 분리할 필요가 생김
  • 네트워크 라우팅이 복잡해짐
  • 중앙 보안 통제가 필요해짐
  • 여러 환경이 서로 독립적이면서도 필요한 범위만 연결되어야 함

이런 상황에서 단순 피어링 수준의 연결만으로는 구조가 빠르게 복잡해질 수 있음.

즉, 고급 네트워크 연결 아키텍처의 목적은 다음과 같음.

  • 연결 구조 단순화
  • 라우팅 중앙화
  • 보안 경계 명확화
  • 공통 서비스 접근 통제
  • 멀티 계정 환경의 네트워크 표준화

3.3 네트워크 연결을 바라보는 세 가지 관점

고급 AWS 네트워크 연결은 보통 다음 세 관점에서 정리할 수 있음.

1. AWS 서비스로의 사설 접근

VPC 내부 리소스가 S3 같은 AWS 서비스에 인터넷 없이 접근하는 구조임.

2. VPC 간 연결

서로 다른 VPC 또는 서로 다른 계정의 VPC를 연결하는 구조임.

3. 중앙 허브 기반 연결

여러 네트워크를 허브형 구조로 묶어 중앙에서 제어하는 구조임.

이 장에서는 이 중 특히 다음에 집중함.

  • Amazon S3 VPC 엔드포인트 통신 보안
  • Transit Gateway
  • 멀티 계정 / 멀티 VPC 연결 구조
  • 중앙 허브형 네트워크 설계

3.4 Amazon S3 VPC 엔드포인트 개요

VPC 내부의 리소스가 Amazon S3에 접근할 때, 단순히 인터넷을 통해 접근하게 둘 수도 있음.

하지만 보안과 운영 관점에서는 인터넷 경로를 통하지 않고 AWS 내부 네트워크를 통해 접근하는 것이 더 적절한 경우가 많음.

이때 사용하는 것이 VPC 엔드포인트임.

S3에 대해서는 일반적으로 Gateway Endpoint를 사용함.

이 방식은 VPC 내부 라우팅 수준에서 S3로 향하는 경로를 AWS 내부 경로로 우회하게 만드는 구조임.

즉, S3 VPC 엔드포인트는 다음 의미를 가짐.

VPC 내부 자원이 S3에 접근할 때
인터넷 게이트웨이나 NAT 게이트웨이를 거치지 않고
사설 경로처럼 접근하게 만드는 방식

3.5 S3 VPC 엔드포인트가 필요한 이유

S3는 AWS의 대표적인 객체 스토리지 서비스이며, 로그 저장, 백업, 정적 파일 저장, 데이터 적재 등 다양한 목적으로 사용됨.

이때 Private Subnet의 인스턴스가 S3에 접근해야 하는 경우가 많음.

만약 VPC 엔드포인트가 없다면 보통 다음과 같은 구조가 됨.

  • Private Subnet 인스턴스
  • NAT Gateway
  • 인터넷 경로
  • S3

이 구조는 동작은 가능하지만 다음 관점에서 한계가 있음.

1. 인터넷 경로 의존

실제로는 AWS 서비스에 접근하는데도 인터넷/NAT 구조를 거치게 됨.

2. 보안 단순성 저하

사설 네트워크 기반 설계 관점에서 덜 깔끔함.

3. NAT 비용 증가 가능성

S3로 향하는 트래픽까지 NAT 처리 비용에 영향을 줄 수 있음.

4. 네트워크 통제력 약화

어떤 S3 버킷에 어떤 방식으로 접근할 것인지 더 엄격하게 통제하고 싶을 수 있음.

즉, S3 VPC 엔드포인트는 보안성, 비용, 구조 단순성 측면에서 의미가 큼.

3.6 Gateway Endpoint의 동작 방식

S3용 VPC 엔드포인트는 일반적으로 Gateway Endpoint 방식으로 제공됨.

이 방식은 서브넷 내부에 새로운 ENI를 생성하는 구조가 아니라, 라우팅 테이블에 S3로 가는 특별한 경로를 추가하는 방식임.

즉, 핵심은 다음과 같음.

  • 라우팅 테이블에 S3 대상 경로가 생김
  • 해당 경로는 AWS 내부 네트워크로 연결됨
  • 인스턴스는 인터넷을 거치지 않고 S3에 접근함

이 구조는 VPC 내부에서 매우 자연스럽게 동작함.

따라서 S3 통신 보안을 설명할 때 단순히 “접근된다”가 아니라, 어떤 경로로 접근되는가를 같이 이해하는 것이 중요함.

3.7 S3 VPC 엔드포인트 통신 보안의 핵심

S3 VPC 엔드포인트를 사용한다고 해서 자동으로 보안이 완성되는 것은 아님.

실제로는 다음 요소를 함께 고려해야 함.

1. 어떤 서브넷/라우트 테이블이 엔드포인트를 사용하는가

필요한 네트워크 범위만 연결하는 것이 중요함.

2. 어떤 버킷에 접근 가능한가

모든 S3 버킷을 열어두기보다 특정 버킷만 허용할 수 있어야 함.

3. 누가 접근하는가

IAM Role, 버킷 정책, 엔드포인트 정책이 함께 작동함.

4. 인터넷 경로를 막았는가

진짜 사설 경로만 허용하려면 다른 우회 경로도 함께 검토해야 함.

즉, S3 VPC 엔드포인트 통신 보안은

경로 보안 + 정책 보안 + 접근 주체 보안을 함께 봐야 함.

3.8 엔드포인트 정책과 버킷 정책의 관계

S3 보안을 설명할 때 자주 혼동되는 것이 IAM 정책, 버킷 정책, 엔드포인트 정책의 관계임.

이 장에서는 구조적으로 다음처럼 이해하면 됨.

IAM 정책

누가 무엇을 할 수 있는가를 정의함.

버킷 정책

이 버킷이 누구에게 어떤 접근을 허용할 것인가를 정의함.

엔드포인트 정책

이 엔드포인트를 통해 어떤 S3 작업과 어떤 리소스를 허용할 것인가를 제한함.

즉, 엔드포인트 정책은 “이 경로를 통해서는 여기까지만 허용”이라는 추가 보안 경계 역할을 함.

이 점이 중요함.

단순히 S3에 접근하게 만드는 기능이 아니라, 접근 경로 자체에 정책을 거는 구조이기 때문임.

3.9 S3 VPC 엔드포인트 보안 설계 원칙

고급 설계에서는 다음 원칙이 중요함.

1. 필요한 서브넷만 연결

모든 경로를 무조건 열지 않음.

2. 특정 버킷 중심 허용

모든 버킷 접근보다 필요한 버킷만 허용하는 것이 바람직함.

3. IAM Role과 함께 설계

인스턴스 또는 워크로드 역할과 결합해서 최소 권한 원칙을 유지해야 함.

4. 인터넷 경로를 대체하는 구조로 사용

Private 네트워크 설계를 명확하게 가져가는 것이 중요함.

즉, S3 VPC 엔드포인트는 단순한 성능 기능이 아니라

사설 접근 구조를 구현하는 네트워크 보안 요소로 봐야 함.

3.10 멀티 VPC 환경의 등장

네트워크가 단일 VPC에 머무르지 않는 순간부터 설계 난이도가 크게 올라감.

여러 VPC를 사용하는 대표적인 이유는 다음과 같음.

  • 운영/개발 환경 분리
  • 애플리케이션별 네트워크 분리
  • 계정별 VPC 독립성 확보
  • 공통 서비스망 분리
  • 보안 요구사항 차등 적용

이렇게 VPC가 늘어나면 자연스럽게 질문이 생김.

  • 이 VPC들은 서로 연결해야 하는가
  • 모두 연결해야 하는가
  • 중앙 허브가 필요한가
  • 라우팅은 어디서 통제할 것인가

즉, 멀티 VPC 설계는 단순 연결보다 연결 정책 설계가 더 중요함.

3.11 단순 연결 방식의 한계

VPC 수가 적을 때는 단순 직접 연결이 가능할 수 있음.

하지만 VPC 수가 늘어나면 다음과 같은 한계가 나타남.

1. 연결 수 증가

연결 조합 수가 많아짐.

2. 라우팅 복잡도 증가

각 연결마다 라우팅을 맞춰야 함.

3. 운영 표준화 어려움

팀별로 연결 방식이 달라질 수 있음.

4. 중앙 통제 한계

네트워크를 한 곳에서 보기 어려워짐.

즉, 멀티 계정 / 멀티 VPC 환경에서는

연결을 개별적으로 만드는 방식보다 중앙 구조가 더 중요해짐.

3.12 Transit Gateway 개요

Transit Gateway는 여러 VPC와 네트워크 연결을 중앙 허브 방식으로 연결하는 서비스임.

이 서비스의 핵심은 다음과 같음.

여러 네트워크를 하나의 허브에 연결하고
중앙에서 라우팅과 연결 구조를 단순화한다.

즉, Transit Gateway는 VPC를 단순히 하나 더 연결하는 서비스가 아니라

네트워크 허브 역할을 하는 중앙 라우팅 계층임.

3.13 Transit Gateway가 필요한 이유

멀티 VPC 구조에서는 연결을 많이 만드는 것보다

연결 구조를 단순화하는 것이 더 중요함.

Transit Gateway가 필요한 이유는 다음과 같음.

1. 허브-앤-스포크 구조 가능

각 VPC는 서로 직접 연결하는 대신 허브에 연결함.

2. 중앙 라우팅 관리

네트워크 경로를 중앙에서 더 일관되게 관리할 수 있음.

3. 멀티 계정 환경에 적합

각 계정의 VPC를 공통 네트워크 허브에 연결하는 구조가 가능함.

4. 확장성 향상

VPC 수가 많아져도 구조가 비교적 단순하게 유지됨.

즉, Transit Gateway는 네트워크 확장성 문제를 해결하는 구조적 도구임.

3.14 Transit Gateway의 기본 구조

Transit Gateway를 사용하면 보통 다음과 같은 허브 구조가 형성됨.

          VPC-A
            │
          TGW
       /    |    \
   VPC-B  VPC-C  Shared Services VPC

이 구조의 의미는 다음과 같음.

  • 각 VPC는 서로 전부 직접 연결하지 않음
  • 각 VPC는 중앙 TGW에만 연결함
  • TGW가 라우팅 허브 역할을 수행함

즉, Transit Gateway는 직접 연결의 복잡성을 중앙 허브 구조로 바꾸는 방식임.

3.15 Transit Gateway의 핵심 개념

Transit Gateway를 이해할 때 중요한 개념은 다음과 같음.

  • Attachment
  • Route Table
  • Association
  • Propagation

이 장에서는 개념 중심으로 이해하면 됨.

3.15.1 Attachment

Attachment는 Transit Gateway에 연결되는 개별 연결 단위임.

예를 들어 특정 VPC가 TGW에 연결되면 그것이 하나의 Attachment가 됨.

즉, Attachment는 “어떤 네트워크가 이 허브에 연결되었는가”를 나타내는 단위임.

3.15.2 TGW Route Table

Transit Gateway도 자체 라우팅 테이블을 가짐.

이 라우팅 테이블을 통해 어떤 Attachment로 어떤 트래픽을 보낼지 결정함.

즉, VPC 라우팅 테이블과 별도로

허브 내부 라우팅 논리가 하나 더 존재한다고 이해하면 됨.

3.15.3 Association

어떤 Attachment가 어떤 TGW Route Table을 사용할지 연결하는 개념임.

즉, 연결만 만든다고 끝나는 것이 아니라

그 연결이 어떤 라우팅 정책을 따를 것인지도 정해야 함.

3.15.4 Propagation

특정 Attachment의 경로 정보를 TGW Route Table에 전파하는 개념임.

즉, 연결된 네트워크의 경로를 라우팅 테이블에 자동 반영하게 만드는 구조라고 볼 수 있음.

이 개념을 통해 단순 연결이 아니라

정책 기반 중앙 라우팅 제어가 가능해짐.

3.16 허브-앤-스포크 구조의 의미

Transit Gateway를 설명할 때 가장 중요한 것은 허브-앤-스포크 구조임.

허브

중앙 네트워크 제어 지점

스포크

허브에 연결된 개별 VPC 또는 네트워크

이 구조의 장점

  • 중앙 통제 가능
  • 연결 수 감소
  • 표준화 쉬움
  • 공통 서비스망 구성 쉬움
  • 계정별 분리와 연결의 균형을 맞추기 쉬움

즉, 허브-앤-스포크 구조는 단순 연결이 아니라

네트워크 운영 모델 자체를 정리하는 구조임.

3.17 Shared Services VPC와 중앙 네트워크 설계

멀티 계정 환경에서는 공통 서비스망을 따로 두는 경우가 많음.

예를 들어 다음과 같은 리소스를 공통으로 둘 수 있음.

  • 중앙 로깅 도구
  • 공통 보안 도구
  • 공통 저장소 접근 경로
  • 공통 네트워크 서비스

이 경우 Transit Gateway는 각 워크로드 VPC와 Shared Services VPC를 연결하는 허브 역할을 함.

즉, 고급 네트워크 설계에서는 단순 연결보다

공통 서비스 접근 구조를 어떻게 만들 것인가가 중요함.

3.18 멀티 계정 / 멀티 VPC 연결 구조

고급 환경에서는 다음과 같은 구조를 자주 보게 됨.

관리 구조
 ├ 운영 계정 VPC
 ├ 개발 계정 VPC
 ├ 보안 계정 VPC
 └ 공유 서비스 계정 VPC
          │
        Transit Gateway

이 구조의 의미는 다음과 같음.

  • 계정은 분리되어 있음
  • 네트워크도 계정 단위로 나뉨
  • 하지만 필요한 범위 안에서 중앙 허브를 통해 연결됨

즉, 멀티 계정 구조와 Transit Gateway는 서로 강하게 연결됨.

계정을 분리했더라도 네트워크가 완전히 단절되어야 하는 것은 아니며,

통제된 연결 구조를 설계해야 하기 때문임.

3.19 고급 네트워크에서 중요한 설계 질문

Transit Gateway나 VPC Endpoint 같은 기술을 사용하기 전에 다음 질문이 중요함.

1. 무엇을 왜 연결하는가

모든 VPC를 무조건 연결할 필요는 없음.

2. 공통 서비스는 어디에 둘 것인가

각 계정에 중복 배치할지, 공통 계정으로 중앙화할지 결정해야 함.

3. 라우팅 통제는 어디서 할 것인가

각 VPC가 알아서 연결되게 둘 것인지, 중앙에서 통제할 것인지 결정해야 함.

4. 인터넷 없이 접근해야 하는 AWS 서비스는 무엇인가

S3, Systems Manager, Secrets Manager 등은 Private 접근 요구가 있을 수 있음.

5. 보안 경계는 어떻게 유지할 것인가

연결을 많이 만들수록 보안 경계가 흐려질 수 있음.

즉, 고급 네트워크 설계는 연결 기술을 외우는 것이 아니라

연결 정책을 먼저 정하는 것이 핵심임.

3.20 중앙 허브형 네트워크의 장점

중앙 허브형 구조는 다음과 같은 장점이 있음.

1. 구조 단순화

복잡한 직접 연결 관계를 줄일 수 있음.

2. 운영 표준화

모든 네트워크 연결이 비슷한 패턴을 따르게 됨.

3. 보안 통제 용이

중앙에서 흐름을 제어하기 쉬움.

4. 공통 서비스 재사용

공유 서비스망을 만들기 쉬움.

5. 계정 확장 대응

새 계정, 새 VPC가 추가되어도 연결 구조가 크게 흔들리지 않음.

즉, 중앙 허브형 설계는 네트워크 규모가 커질수록 장점이 더 커짐.

3.21 중앙 허브형 네트워크의 주의점

장점만 있는 것은 아님.

Transit Gateway 같은 중앙 허브 구조도 설계가 잘못되면 복잡성이 생길 수 있음.

주의할 점

1. 모든 것을 연결하지 않음

중앙 허브가 있다고 해서 모든 VPC가 모두 통신해야 하는 것은 아님.

2. 라우팅 분리가 중요함

환경별, 계정별, 용도별 라우팅 분리가 필요할 수 있음.

3. 공통 서비스 접근 범위를 제한해야 함

공유 서비스가 있다고 해서 모든 계정이 무제한 접근하면 안 됨.

4. 네트워크 구조 문서화가 필요함

허브 구조는 시각적으로는 단순해 보여도 실제 라우팅은 복잡할 수 있음.

즉, 허브 구조는 강력하지만

중앙 집중이 곧 무조건 단순함을 의미하지는 않음을 이해해야 함.

3.22 S3 Endpoint와 중앙 네트워크의 연결 관점

S3 VPC 엔드포인트와 Transit Gateway는 성격이 다르지만 함께 이해할 필요가 있음.

  • S3 Endpoint는 AWS 서비스로의 사설 접근
  • Transit Gateway는 네트워크 간 중앙 연결

즉, 하나는 서비스 접근 구조, 다른 하나는 네트워크 연결 구조임.

고급 설계에서는 이 둘을 함께 조합할 수 있음.

예를 들어

  • 워크로드 VPC는 TGW로 중앙망에 연결
  • 각 워크로드 VPC는 S3 Endpoint를 통해 인터넷 없이 S3 접근

이 구조는 네트워크 연결과 AWS 서비스 접근을 모두 통제된 방식으로 설계하는 예가 됨.

3.23 운영 관점의 핵심

고급 네트워크 아키텍처는 결국 운영성과 연결됨.

1. 단순한 구조가 중요함

연결 기술을 많이 쓰는 것이 아니라, 운영 가능한 구조를 만드는 것이 중요함.

2. 중앙 통제와 독립성을 균형 있게 가져가야 함

계정과 VPC는 분리하되 필요한 범위만 연결해야 함.

3. 보안 정책과 네트워크 구조를 같이 설계해야 함

연결이 곧 허용을 의미해서는 안 됨.

4. 문서화와 표준화가 필요함

허브 구조, 라우팅 정책, 엔드포인트 정책은 표준 형태로 가져가는 것이 좋음.

즉, 고급 네트워크 연결 설계는 기술 조합이 아니라

운영 가능한 구조를 만드는 일임.
