4장 컨테이너 및 현대적 애플리케이션 플랫폼

4.1 현대적 애플리케이션 플랫폼의 의미

애플리케이션 실행 환경은 오랜 기간 동안 물리 서버, 가상머신, 가상 서버 중심으로 발전해 왔음.

초기에는 애플리케이션을 특정 서버에 직접 설치하고, 운영체제와 미들웨어를 함께 관리하는 방식이 일반적이었음.

하지만 서비스 규모가 커지고 배포 주기가 짧아지면서, 서버 중심 운영만으로는 다음과 같은 한계가 뚜렷해짐.

  • 환경 차이로 인한 배포 실패
  • 애플리케이션별 의존성 충돌
  • 확장 속도 한계
  • 배포 단위가 너무 큼
  • 운영 환경 일관성 확보 어려움

이런 문제를 해결하기 위해 등장한 대표적인 방식이 컨테이너 기반 애플리케이션 플랫폼임.

즉, 현대적 애플리케이션 플랫폼은 단순히 코드를 실행하는 장소가 아니라

일관된 실행 환경, 빠른 배포, 탄력적 확장, 운영 자동화를 가능하게 하는 구조임.

4.2 왜 컨테이너 기반 플랫폼이 필요한가

애플리케이션을 직접 서버에 설치하는 방식은 처음에는 단순해 보일 수 있음.

하지만 서비스 수가 늘어나고 배포 빈도가 높아질수록 다음 문제가 발생함.

1. 환경 차이 문제

개발 환경에서는 정상 동작하지만 운영 환경에서는 실패할 수 있음.

2. 종속성 관리 문제

서로 다른 애플리케이션이 서로 다른 라이브러리 버전을 요구할 수 있음.

3. 서버 의존성 증가

특정 서버에 강하게 묶인 애플리케이션은 확장과 교체가 어려워짐.

4. 배포 단위 비대화

애플리케이션 일부만 바꾸고 싶어도 전체 환경에 영향이 갈 수 있음.

즉, 현대적 플랫폼이 필요한 이유는

애플리케이션과 서버 환경을 느슨하게 분리하고, 실행 단위를 더 가볍고 반복 가능하게 만들기 위해서임.

4.3 컨테이너의 기본 개념

컨테이너는 애플리케이션과 그 실행에 필요한 종속 요소를 하나의 패키지처럼 묶어 실행하는 방식임.

여기서 중요한 점은 단순히 파일을 압축해 두는 것이 아니라,

어디에서 실행하더라도 동일한 방식으로 애플리케이션을 실행할 수 있게 만드는 실행 단위라는 점임.

즉, 컨테이너는 다음 의미를 가짐.

애플리케이션과 실행 환경을 함께 패키징해서
일관되게 배포하고 실행하는 방식

이 구조를 통해 운영체제나 패키지 차이에서 오는 문제를 줄이고, 배포를 더 빠르고 안정적으로 수행할 수 있음.

4.4 가상머신과 컨테이너의 차이

컨테이너를 이해하려면 가상머신과 비교하는 것이 가장 직관적임.

항목가상머신컨테이너
격리 단위운영체제 전체애플리케이션 프로세스
포함 범위Guest OS 포함앱과 종속성 중심
자원 효율성상대적으로 낮을 수 있음상대적으로 높음
시작 속도느린 편빠른 편
배포 단위VM 이미지컨테이너 이미지

가상머신은 하나의 운영체제를 통째로 띄우는 구조에 가까움.

반면 컨테이너는 호스트 커널을 공유하면서 애플리케이션 실행 단위를 분리하는 구조임.

즉, 컨테이너는 더 가볍고 빠르게 복제할 수 있으므로

현대적인 배포와 확장 구조에 더 잘 맞음.

4.5 컨테이너의 장점

컨테이너 기반 구조가 널리 사용되는 이유는 다음과 같음.

1. 실행 환경 일관성

같은 이미지라면 어느 환경에서도 동일하게 실행될 가능성이 높음.

2. 빠른 배포

이미지를 기반으로 실행하므로 준비 시간이 짧음.

3. 높은 자원 효율성

가상머신처럼 운영체제를 매번 따로 띄우지 않아도 됨.

4. 독립적인 서비스 운영

서비스를 작은 단위로 분리하고 각자 독립 배포하기 쉬움.

5. 확장 자동화 적합

같은 이미지 기반으로 인스턴스를 여러 개 손쉽게 늘릴 수 있음.

즉, 컨테이너는 애플리케이션 배포와 운영을

더 작고, 더 빠르고, 더 반복 가능하게 만드는 기술임.

4.6 컨테이너만으로는 충분하지 않은 이유

컨테이너 기술 자체는 강력하지만, 컨테이너를 하나 띄우는 것과 운영 환경에서 수십 개, 수백 개를 안정적으로 운영하는 것은 전혀 다른 문제임.

운영 환경에서는 다음 요구가 생김.

  • 컨테이너를 어디에서 실행할 것인가
  • 장애가 나면 누가 다시 띄울 것인가
  • 트래픽이 늘어나면 어떻게 수를 늘릴 것인가
  • 배포 중 서비스 중단 없이 교체할 수 있는가
  • 로드 밸런서와 어떻게 연결할 것인가
  • 로그와 모니터링은 어디서 할 것인가

즉, 컨테이너를 사용한다고 끝나는 것이 아니라

컨테이너를 관리하는 플랫폼이 필요함.

이 역할을 하는 것이 컨테이너 오케스트레이션 서비스이며, AWS에서는 대표적으로 ECS와 EKS가 있음.

4.7 Docker 개요

컨테이너를 설명할 때 가장 많이 함께 언급되는 것이 Docker임.

Docker는 컨테이너 이미지를 만들고, 실행하고, 배포하는 데 널리 사용되는 도구임.

Docker를 이해할 때 핵심이 되는 개념은 다음과 같음.

  • Image
  • Container
  • Dockerfile
  • Registry

이 네 가지가 정리되면 이후 ECR, ECS, EKS 구조를 훨씬 쉽게 이해할 수 있음.

4.8 Image와 Container의 관계

컨테이너 환경에서 가장 먼저 구분해야 하는 것이 이미지와 컨테이너임.

Image

애플리케이션 실행에 필요한 내용이 담긴 불변 패키지임.

Container

이미지를 실제로 실행한 결과물임.

관계는 다음처럼 이해하면 됨.

Image → 실행 → Container

즉, 이미지는 설계도 또는 실행 원본이고,

컨테이너는 그 원본을 실행한 인스턴스임.

이 구조 덕분에 동일 이미지를 여러 개 실행해 손쉽게 확장할 수 있음.

4.9 Dockerfile의 의미

Dockerfile은 컨테이너 이미지를 만들기 위한 정의 파일임.

즉, 어떤 베이스 환경을 사용할지, 어떤 파일을 포함할지, 어떤 명령으로 실행할지를 코드처럼 적어두는 파일임.

여기서 중요한 의미는 다음과 같음.

애플리케이션 실행 환경을 문서가 아니라 코드로 정의한다.

즉, Dockerfile은 단순 빌드 스크립트가 아니라

애플리케이션 실행 환경의 선언서라고 볼 수 있음.

4.10 Registry의 의미

이미지를 만들었다면 어딘가에 저장하고 필요할 때 가져와야 함.

그 저장소 역할을 하는 것이 Registry임.

대표 예

  • Docker Hub
  • Amazon ECR

즉, Registry는 컨테이너 이미지의 배포 저장소임.

애플리케이션 코드를 바로 실행하는 것이 아니라,

이미지라는 패키지 형태로 보관하고 전달하는 구조가 중요함.

4.11 마이크로서비스와 컨테이너의 관계

현대적 애플리케이션 플랫폼을 설명할 때 자주 등장하는 개념이 마이크로서비스임.

마이크로서비스는 애플리케이션을 하나의 거대한 단일 시스템이 아니라, 기능별로 더 작은 서비스들로 나누는 구조를 의미함.

예를 들어 다음처럼 나눌 수 있음.

  • 사용자 서비스
  • 주문 서비스
  • 결제 서비스
  • 알림 서비스
  • 상품 서비스

여기서 중요한 점은 컨테이너와 마이크로서비스가 같은 개념은 아니라는 점임.

  • 마이크로서비스는 아키텍처 방식
  • 컨테이너는 실행 및 배포 단위

즉, 마이크로서비스를 운영할 때 컨테이너가 매우 잘 맞기 때문에 자주 함께 사용되는 것임.

4.12 모놀리식과 마이크로서비스의 차이

모놀리식 구조

애플리케이션 전체가 하나의 큰 배포 단위로 묶여 있음.

장점

  • 초기 구조가 단순함
  • 개발 시작이 비교적 쉬움

한계

  • 일부 기능 수정도 전체 배포가 필요할 수 있음
  • 서비스가 커질수록 복잡도가 높아짐
  • 특정 기능만 독립 확장하기 어려움

마이크로서비스 구조

기능을 작은 서비스 단위로 분리함.

장점

  • 서비스별 독립 배포 가능
  • 독립 확장 가능
  • 장애 영향 범위를 줄일 수 있음
  • 팀별 책임 분리 쉬움

한계

  • 서비스 간 통신 복잡도 증가
  • 운영 복잡도 증가
  • 관찰 가능성과 보안 체계가 더 중요해짐

즉, 현대적 플랫폼은 단순히 작은 서비스로 나누는 것이 아니라

그 작은 서비스들을 안정적으로 운영할 플랫폼이 함께 필요함을 의미함.

4.13 Amazon ECR 개요

Amazon ECR은 Elastic Container Registry의 약자이며, AWS에서 제공하는 관리형 컨테이너 이미지 저장소임.

ECR의 역할은 매우 명확함.

컨테이너 이미지를 저장하고,
배포 플랫폼이 그 이미지를 가져가게 한다.

즉, ECR은 컨테이너를 실행하는 서비스가 아니라

이미지를 저장하고 배포 파이프라인의 시작점을 제공하는 서비스임.

4.14 ECR의 역할과 의미

ECR은 다음과 같은 역할을 수행함.

  • 컨테이너 이미지 저장
  • 버전 태그 관리
  • 접근 제어
  • ECS/EKS와의 연계
  • 이미지 배포 표준화

즉, 컨테이너 기반 애플리케이션에서는 소스코드 저장소 외에도

실행 가능한 애플리케이션 패키지 저장소가 필요하며, 그 역할을 ECR이 담당함.

4.15 ECS 개요

Amazon ECS는 Elastic Container Service의 약자이며, AWS의 관리형 컨테이너 오케스트레이션 서비스임.

즉, ECS는 다음 문제를 해결함.

  • 컨테이너를 어디서 실행할지
  • 몇 개를 유지할지
  • 장애 시 어떻게 다시 띄울지
  • 로드 밸런서와 어떻게 연결할지
  • 확장을 어떻게 자동화할지

즉, ECS는 이미지를 저장하는 곳이 아니라

컨테이너를 실행하고 유지하는 플랫폼임.

4.16 ECS의 핵심 개념

ECS를 이해할 때 중요한 개념은 다음과 같음.

  • Cluster
  • Task Definition
  • Task
  • Service
  • Launch Type

이 개념들을 구분하면 ECS 구조가 훨씬 명확해짐.

4.16.1 Cluster

Cluster는 ECS 리소스를 논리적으로 묶는 실행 영역임.

컨테이너가 동작하는 관리 범위라고 이해하면 됨.

즉, Cluster는 실제 애플리케이션을 담는 상위 운영 공간 역할을 함.

4.16.2 Task Definition

Task Definition은 컨테이너를 어떻게 실행할지 정의한 설계서임.

포함되는 정보 예

  • 어떤 이미지 사용할지
  • CPU/메모리 얼마나 사용할지
  • 어떤 포트를 열지
  • 어떤 환경변수를 줄지
  • 어떤 로그 설정을 사용할지

즉, Task Definition은 ECS에서 컨테이너 실행 방식을 정의하는 핵심 문서임.

4.16.3 Task

Task는 Task Definition을 실제로 실행한 단위임.

즉, 컨테이너 실행 결과물에 해당함.

같은 Task Definition을 여러 번 실행하면 여러 Task가 만들어질 수 있음.

이 특성 덕분에 동일한 애플리케이션을 손쉽게 복제해 확장할 수 있음.

4.16.4 Service

Service는 원하는 수의 Task가 항상 유지되도록 관리하는 기능임.

예를 들어 2개의 Task를 유지하도록 설정하면,

  • 하나가 장애 나면 다시 생성
  • 업데이트 시 교체
  • 필요하면 수를 늘리거나 줄임

즉, Service는 운영 환경에서 애플리케이션을 안정적으로 계속 유지하게 해주는 핵심 구성요소임.

4.17 ECS Launch Type

ECS는 컨테이너를 어디에서 실행할지에 따라 대표적으로 두 가지 방식을 가짐.

  • EC2 Launch Type
  • Fargate Launch Type

이 둘의 차이는 매우 중요함.

4.17.1 EC2 Launch Type

EC2 Launch Type은 ECS용 EC2 인스턴스를 직접 준비하고, 그 위에서 컨테이너를 실행하는 방식임.

의미

  • 컨테이너 플랫폼은 ECS가 관리
  • 하지만 하부 서버는 직접 관리해야 함

장점

  • 세밀한 제어 가능
  • 특수한 환경 구성 가능

한계

  • EC2 운영 부담 존재
  • 패치, 용량 계획, 서버 관리가 필요함

즉, EC2 Launch Type은 컨테이너를 쓰지만

서버 운영 책임이 완전히 사라지는 것은 아님.

4.17.2 Fargate Launch Type

Fargate는 서버를 직접 관리하지 않고 컨테이너를 실행할 수 있는 방식임.

즉, 컨테이너 실행 자체를 더 관리형 서비스로 끌어올린 형태라고 볼 수 있음.

의미

컨테이너는 실행하지만,
그 아래 EC2 서버를 직접 운영하지는 않는다.

장점

  • 서버 관리 부담 감소
  • 빠른 시작 가능
  • 표준적인 애플리케이션 운영에 적합
  • 탄력적 실행 구조와 잘 맞음

즉, Fargate는 현대적 애플리케이션 플랫폼에서

운영 부담을 크게 줄이는 선택지임.

4.18 왜 Fargate가 중요한가

Fargate의 가치는 단순 편의 기능이 아님.

고급 설계 관점에서는 다음 의미가 큼.

1. 서버 운영 관심사 축소

운영자는 인스턴스 패치와 클러스터 용량보다 애플리케이션 실행 단위에 집중할 수 있음.

2. 배포 단위 명확화

애플리케이션 단위로 더 명확하게 실행 구조를 설계할 수 있음.

3. 확장 단위 축소

EC2 수가 아니라 Task 수 중심으로 확장 설계 가능

4. 관리형 서비스 활용

Well-Architected 관점에서 운영 우수성과 단순성을 높이기 좋음.

즉, Fargate는 ECS를 더 현대적인 플랫폼 형태로 활용하게 해주는 중요한 요소임.

4.19 EKS는 어떻게 바라봐야 하는가

Amazon EKS는 관리형 Kubernetes 서비스임.

즉, Kubernetes 기반으로 컨테이너를 운영하고 싶은 경우 사용하는 서비스임.

이 장에서는 EKS를 깊게 다루기보다 비교 관점에서 이해하는 것이 적절함.

핵심은 다음과 같음.

  • ECS는 AWS 고유의 컨테이너 오케스트레이션 서비스
  • EKS는 Kubernetes 기반의 오케스트레이션 서비스

즉, 두 서비스는 모두 컨테이너를 운영하지만

기반 철학과 생태계가 다름.

4.20 ECS와 EKS 비교 관점

항목ECSEKS
기반AWS 고유 서비스Kubernetes
학습 난이도비교적 낮음상대적으로 높음
운영 복잡도비교적 낮음상대적으로 높음
표준성AWS 중심Kubernetes 중심
활용 맥락AWS 최적화 운영쿠버네티스 표준 필요 시

즉, 컨테이너 플랫폼을 설계할 때는

기술 선호가 아니라 운영 복잡도, 조직 역량, 표준 요구사항을 보고 선택해야 함.

이 장에서는 현대적 애플리케이션 플랫폼의 중심을 ECS/Fargate에 두고,

EKS는 비교 선택지로 이해하면 충분함.

4.21 컨테이너 기반 App Tier의 의미

멀티 티어 구조에서 App Tier는 전통적으로 EC2 기반 애플리케이션 서버로 구현되곤 했음.

하지만 현대적 구조에서는 이 계층을 컨테이너 플랫폼으로 바꾸는 경우가 많음.

즉, App Tier가 다음처럼 바뀔 수 있음.

ALB
 │
ECS Service / Fargate
 │
RDS / Redis / S3

이 구조의 의미는 다음과 같음.

  • 애플리케이션 서버를 고정 EC2로 두지 않음
  • 컨테이너 단위로 배포와 확장이 가능함
  • 무중단 배포와 빠른 교체에 유리함
  • 상태 비저장 구조와 잘 맞음

즉, 컨테이너 플랫폼은 멀티 티어 구조에서

App Tier를 더 유연하고 자동화 친화적으로 만드는 방식임.

4.22 상태 비저장 설계와 컨테이너

컨테이너 플랫폼에서는 특히 Stateless 설계가 중요함.

왜냐하면 컨테이너는 언제든 교체되거나 재생성될 수 있기 때문임.

따라서 다음 원칙이 중요함.

  • 컨테이너 안에 중요한 상태를 오래 저장하지 않음
  • 세션은 외부 저장소에 둠
  • 업로드 파일은 외부 저장소에 둠
  • 핵심 데이터는 DB 계층에 둠

예

  • 로그인 세션 → Redis
  • 사용자 업로드 → S3 / EFS
  • 업무 데이터 → RDS / DynamoDB

즉, 컨테이너는 처리 계층에 집중하고, 상태는 외부 계층으로 분리하는 것이 바람직함.

4.23 컨테이너와 로드 밸런서

컨테이너 기반 애플리케이션도 외부 요청을 받아야 하므로 로드 밸런서와의 연결이 중요함.

AWS에서는 보통 ALB와 ECS Service를 연동하는 구조가 자주 사용됨.

구조 예

사용자
 │
ALB
 │
ECS Service
 │
여러 Task

이 구조의 의미

  • ALB가 외부 요청을 수신함
  • ECS Service가 Task를 유지함
  • ALB가 Task들로 요청을 분산함

즉, 컨테이너 환경에서도

트래픽 진입 계층과 애플리케이션 실행 계층은 분리되어 있음.

4.24 컨테이너와 Auto Scaling

컨테이너 환경에서도 확장성은 매우 중요함.

다만 EC2 중심 구조와는 확장 단위가 다름.

전통적 구조에서는 주로 인스턴스 수를 늘렸다면,

컨테이너 환경에서는 Task 수를 늘리는 방식이 중심이 됨.

즉, 확장 관점이 다음처럼 달라짐.

  • EC2 중심: 서버 수 확대
  • 컨테이너 중심: 실행 단위 수 확대

이 차이는 매우 중요함.

현대적 플랫폼에서는 더 작은 단위로 더 유연하게 확장을 설계할 수 있기 때문임.

4.25 현대적 애플리케이션 플랫폼에서 중요한 질문

컨테이너와 플랫폼을 설계할 때는 다음 질문이 중요함.

1. 애플리케이션을 서버 중심으로 볼 것인가, 실행 단위 중심으로 볼 것인가

현대적 플랫폼은 후자에 가깝게 생각해야 함.

2. 상태를 어디에 둘 것인가

컨테이너 내부가 아니라 외부 계층으로 분리해야 함.

3. 어떤 플랫폼을 선택할 것인가

ECS/Fargate가 적합한지, Kubernetes 기반이 필요한지 판단해야 함.

4. 운영 복잡도를 감당할 수 있는가

모든 조직이 가장 복잡한 플랫폼을 선택할 필요는 없음.

5. 배포와 확장은 어떤 단위로 일어나는가

서버 단위인지, Task 단위인지, 함수 단위인지 구분해야 함.

즉, 현대적 애플리케이션 플랫폼은 단순히 새로운 서비스를 배우는 것이 아니라

애플리케이션 실행 단위를 어떻게 재정의할 것인가의 문제임.

4.26 ECS/Fargate가 적합한 경우

다음과 같은 경우 ECS/Fargate가 매우 적합할 수 있음.

  • AWS 환경에 최적화된 컨테이너 플랫폼이 필요함
  • 서버 운영 부담을 줄이고 싶음
  • 표준적인 웹/API 애플리케이션을 배포하고 싶음
  • App Tier를 컨테이너 기반으로 현대화하고 싶음
  • 운영 복잡도는 가능한 낮게 가져가고 싶음

즉, ECS/Fargate는

현대적이면서도 비교적 단순한 컨테이너 운영 구조를 제공하는 선택지임.

4.27 EKS를 선택할 수 있는 경우

다음과 같은 상황에서는 EKS가 선택지가 될 수 있음.

  • Kubernetes 표준이 필요함
  • 기존 Kubernetes 운영 경험이 있음
  • 멀티 클라우드나 Kubernetes 생태계 활용이 중요함
  • 플랫폼 표준을 Kubernetes 중심으로 가져가려 함

즉, EKS는 충분히 강력한 선택지이지만

항상 기본 선택지인 것은 아니며, 복잡도와 조직 역량까지 고려해야 함.

4.28 운영 관점의 핵심

현대적 애플리케이션 플랫폼을 설계할 때는 기술보다 운영 관점이 중요함.

1. 플랫폼이 복잡할수록 운영 체계도 함께 필요함

배포, 모니터링, 로그, 보안, 권한 관리까지 같이 설계해야 함.

2. 상태 비저장 설계가 중요함

플랫폼이 자동 복구/자동 확장될수록 더 중요해짐.

3. 관리형 서비스를 우선 고려해야 함

운영 부담을 줄일 수 있기 때문임.

4. 애플리케이션과 인프라의 책임을 분리해야 함

컨테이너 플랫폼은 실행 기반을 제공하고, 애플리케이션은 그 위에서 동작함.

즉, 현대적 플랫폼은 단순 배포 도구가 아니라

운영 모델 전체를 바꾸는 기반임.

현대적 애플리케이션 플랫폼은 컨테이너를 사용하는 것 자체가 목적이 아니라,
애플리케이션 실행 단위를 더 작고 일관되게 만들고,
배포와 확장, 운영을 더 유연하게 만드는 구조를 설계하는 것이다.
