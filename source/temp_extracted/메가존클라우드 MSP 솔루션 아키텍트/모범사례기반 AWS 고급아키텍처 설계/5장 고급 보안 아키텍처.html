5장 고급 보안 아키텍처

5.1 고급 보안 아키텍처의 의미

AWS에서 보안을 설계할 때 가장 자주 발생하는 오해 중 하나는 보안을 특정 서비스 하나로 해결할 수 있다고 보는 것임.

예를 들어 IAM만 잘 설정하면 된다거나, 보안 그룹만 잘 닫아두면 충분하다고 생각하기 쉬움.

하지만 실제 보안은 특정 서비스 하나가 아니라 계정, 네트워크, 애플리케이션, 데이터, 엣지, 운영 절차가 함께 맞물려야 성립함.

즉, 고급 보안 아키텍처는 다음과 같은 질문에 답해야 함.

  • 어떤 계층을 외부에 노출할 것인가
  • 어떤 요청을 엣지에서 차단할 것인가
  • 어떤 데이터는 반드시 암호화해야 하는가
  • 애플리케이션 비밀정보를 어디에 저장할 것인가
  • 장애 상황과 공격 상황을 어떻게 분리해서 대응할 것인가
  • 보안 통제를 운영 가능한 구조로 만들었는가

즉, 고급 보안은 단순히 “막는다”가 아니라

구조적으로 위험을 줄이고, 통제를 표준화하고, 운영 가능하게 만드는 설계임.

5.2 보안을 계층으로 나누어 봐야 하는 이유

보안은 하나의 지점에서 완성되지 않음.

같은 시스템이라도 보호해야 하는 대상은 계층마다 다름.

예를 들면 다음과 같음.

  • 계정 계층에서는 누가 로그인하고 어떤 권한을 가지는지가 중요함
  • 네트워크 계층에서는 누가 어디와 통신할 수 있는지가 중요함
  • 애플리케이션 계층에서는 어떤 HTTP 요청을 허용할지가 중요함
  • 데이터 계층에서는 어떤 데이터가 암호화되고 누가 복호화할 수 있는지가 중요함
  • 운영 계층에서는 로그, 감사, 키 관리, 비밀값 관리가 중요함

즉, 좋은 보안 설계는 다음처럼 봐야 함.

계정 보안
→ 네트워크 보안
→ 엣지 보안
→ 데이터 보안
→ 비밀정보 관리
→ 운영 통제

이 장에서는 특히 다음에 집중함.

  • DDoS와 웹 계층 보호
  • WAF와 Shield의 역할
  • 데이터 암호화 구조
  • KMS의 의미
  • Secrets Manager를 통한 비밀정보 관리
  • 계층화된 보안 설계 원칙

5.3 보안과 고가용성은 함께 봐야 함

보안 장에서 자주 놓치기 쉬운 부분은 보안과 가용성이 따로 움직이지 않는다는 점임.

예를 들어 대규모 공격으로 서비스가 느려지거나 중단된다면, 그것은 보안 문제이면서 동시에 가용성 문제이기도 함.

즉, 다음 상황은 모두 보안과 가용성이 만나는 지점임.

  • 대량 HTTP 요청으로 인한 서비스 지연
  • 비정상 트래픽 유입으로 인한 자원 고갈
  • 악성 요청으로 인한 애플리케이션 오류
  • 인증서나 키 관리 실패로 인한 서비스 중단
  • 잘못된 비밀값 노출로 인한 내부 시스템 침해

즉, 고급 보안 아키텍처는 공격을 막는 것만이 아니라

서비스를 지속 가능하게 만드는 구조까지 포함함.

5.4 엣지 보안의 중요성

보안 통제를 애플리케이션 내부에서만 처리하려고 하면 이미 너무 늦을 수 있음.

이유는 악성 요청이 원본 서버까지 도달한 뒤에야 차단이 되기 때문임.

그래서 엣지 보안이 중요함.

엣지 보안의 의미는 다음과 같음.

  • 사용자와 가장 가까운 접점에서 요청을 검사함
  • 비정상 트래픽을 가능한 앞단에서 차단함
  • 원본 서버로 도달하는 요청 자체를 줄임
  • 성능과 보안을 동시에 고려할 수 있음

즉, 엣지 계층은 단순 CDN 계층이 아니라

보안의 1차 방어선이 될 수 있음.

5.5 DDoS 개요

DDoS는 Distributed Denial of Service의 약자이며, 대량의 트래픽 또는 요청을 집중시켜 서비스 이용을 방해하는 공격 방식임.

대표적으로 다음과 같은 형태가 존재함.

  • 네트워크 대역폭을 소진시키는 공격
  • 연결 자원을 소모시키는 공격
  • HTTP 요청을 폭주시켜 애플리케이션을 느리게 만드는 공격
  • 특정 URL이나 기능에 과도한 요청을 몰아넣는 공격

즉, DDoS는 데이터를 훔치는 공격이라기보다

서비스를 못 쓰게 만드는 공격에 가깝지만, 실제 비즈니스 영향은 매우 클 수 있음.

5.6 왜 DDoS 대응이 중요한가

DDoS 공격은 단순히 트래픽이 많아지는 문제가 아님.

특히 인터넷에 노출된 서비스에서는 다음과 같은 영향을 줄 수 있음.

1. 서비스 응답 저하

정상 사용자도 느린 응답을 경험하게 됨.

2. 자원 고갈

로드 밸런서, 웹 서버, 애플리케이션 서버, 네트워크 자원이 고갈될 수 있음.

3. 원본 인프라 장애

백엔드까지 부하가 전파되면 시스템 전체 장애로 이어질 수 있음.

4. 비용 증가

비정상 요청이 많아질수록 사용량 기반 비용이 증가할 가능성도 있음.

즉, DDoS 대응은 보안만의 문제가 아니라

가용성, 비용, 운영 리스크까지 포함한 문제임.

5.7 AWS Shield 개요

AWS Shield는 AWS에서 제공하는 관리형 DDoS 보호 서비스임.

대규모 네트워크 계층 공격이나 전송 계층 공격에 대해 AWS 인프라 차원에서 보호를 제공함.

Shield는 크게 두 수준으로 이해할 수 있음.

  • Shield Standard
  • Shield Advanced

이 장에서는 구조적 의미를 이해하는 것이 중요함.

즉, Shield의 핵심은 다음과 같음.

대규모 비정상 트래픽이 서비스까지 도달하기 전에
AWS 네트워크 계층에서 완충하고 방어한다.

5.8 Shield Standard의 의미

Shield Standard는 기본적으로 제공되는 수준의 DDoS 보호라고 이해하면 됨.

특히 CloudFront, Route 53, ALB 같은 인터넷 접점 서비스와 결합될 때 의미가 큼.

여기서 중요한 것은 “설정 여부”보다 AWS 엣지 서비스와 함께 설계할 때 보호 효과가 커진다는 점임.

즉, 서비스가 인터넷에 직접 노출되는 구조보다

CloudFront, Route 53, ALB 같은 관리형 진입 계층을 거치는 구조가 보안적으로 유리함.

5.9 Shield를 어떻게 바라봐야 하는가

Shield는 세밀한 웹 요청 제어 도구가 아님.

예를 들어 특정 URI를 막거나, 특정 패턴의 요청 본문을 차단하는 기능은 WAF의 영역에 더 가까움.

Shield는 주로 다음 관점에서 봐야 함.

  • 대량 트래픽 완충
  • 인프라 계층 보호
  • 엣지 계층 방어
  • 가용성 유지

즉, Shield는 규모가 큰 공격을 막는 바깥쪽 보호막이라고 이해하면 됨.

5.10 AWS WAF 개요

AWS WAF는 Web Application Firewall임.

이 서비스는 HTTP/HTTPS 요청을 검사하고, 정의된 규칙에 따라 허용 또는 차단하는 역할을 함.

즉, WAF의 핵심은 다음과 같음.

웹 요청 내용을 보고
애플리케이션에 도달하기 전에 필터링한다.

이 점에서 WAF는 Shield와 역할이 다름.

Shield가 대규모 트래픽 방어 중심이라면, WAF는 요청 내용과 패턴을 기준으로 제어하는 서비스임.

5.11 WAF가 필요한 이유

애플리케이션은 단순히 트래픽 양만으로 공격당하는 것이 아님.

정상적인 HTTP 요청처럼 보이지만 실제로는 악의적인 패턴을 가진 요청이 많이 존재함.

예를 들어 다음과 같은 요청은 문제가 될 수 있음.

  • 비정상적으로 긴 쿼리 문자열
  • 반복적인 로그인 시도
  • SQL Injection 시도
  • XSS 시도
  • 특정 국가나 IP 대역에서의 비정상 요청
  • 봇 기반 반복 호출

이런 문제는 네트워크 계층 보호만으로는 어렵고,

웹 요청 자체를 해석해서 차단할 필요가 있음.

그 역할을 WAF가 담당함.

5.12 WAF의 보호 대상

WAF는 보통 다음과 같은 AWS 서비스와 앞단에서 결합되어 사용됨.

  • CloudFront
  • ALB
  • API Gateway

즉, WAF는 원본 애플리케이션 서버에 직접 붙는 개념이 아니라

사용자 요청이 들어오는 진입 계층 앞단에서 동작하는 경우가 많음.

이 구조가 중요한 이유는, 악성 요청이 원본 애플리케이션에 도달하기 전에 차단할 수 있기 때문임.

5.13 WAF가 처리하는 대표 보안 시나리오

WAF는 다양한 보안 시나리오에 활용될 수 있음.

1. SQL Injection 대응

입력값 안에 SQL 구문 삽입을 시도하는 요청을 차단함.

2. XSS 대응

스크립트 삽입을 시도하는 요청을 차단함.

3. Rate-based 제어

짧은 시간에 너무 많은 요청을 보내는 소스를 제한함.

4. 특정 패턴 차단

특정 헤더, URI, Query String 패턴을 가진 요청 차단 가능

5. 국가/IP 기반 제한

운영 정책상 필요 없는 지역 또는 대역 차단 가능

즉, WAF는 웹 계층에서 매우 세밀한 통제를 가능하게 하는 도구임.

5.14 WAF와 Shield의 차이

이 둘은 자주 함께 쓰이지만 역할이 다름.

항목AWS ShieldAWS WAF
핵심 목적대규모 DDoS 방어웹 요청 필터링
주 관점네트워크/전송 계층 중심애플리케이션 계층 중심
대표 대응트래픽 폭주SQLi, XSS, 비정상 요청
보호 방식대규모 공격 완충요청 규칙 기반 제어

즉,

  • 대량 트래픽 공격 대응은 Shield
  • 웹 요청 품질 통제는 WAF

라고 이해하면 됨.

5.15 CloudFront, Shield, WAF를 함께 보는 이유

보안 아키텍처에서는 이 세 가지를 함께 봐야 함.

사용자
   │
CloudFront
 ├ Shield
 └ WAF
   │
ALB / API / Origin

이 구조의 의미는 다음과 같음.

  • CloudFront : 글로벌 진입점
  • Shield : 대규모 공격 보호
  • WAF : 웹 요청 필터링
  • Origin : 실제 애플리케이션

즉, 원본 서버에 모든 보안 처리를 몰아넣지 않고

앞단에서 성능과 보안을 함께 처리하는 구조를 만드는 것이 중요함.

5.16 데이터 보안의 중요성

네트워크와 엣지 계층을 보호하더라도, 데이터 자체가 안전하지 않다면 전체 시스템은 여전히 위험함.

특히 다음과 같은 데이터는 반드시 보호해야 함.

  • 고객 개인정보
  • 인증 관련 정보
  • 결제 관련 정보
  • 비즈니스 핵심 데이터
  • 내부 설정과 비밀값
  • 로그 안의 민감 정보

즉, 데이터 보안은 단순 저장 문제가 아니라

기밀성, 무결성, 접근 통제와 연결된 핵심 설계 영역임.

5.17 데이터 보안에서 가장 중요한 질문

데이터 보안을 설계할 때는 다음 질문이 중요함.

1. 어떤 데이터가 민감한가

모든 데이터가 같은 수준의 보호를 필요로 하지는 않음.

2. 저장 시 암호화가 필요한가

대부분의 민감 데이터는 저장 시 암호화를 검토해야 함.

3. 전송 중 암호화가 필요한가

내부 통신이라도 민감 데이터는 TLS를 검토해야 함.

4. 누가 복호화할 수 있는가

암호화보다 더 중요한 것이 키 접근 통제일 수 있음.

5. 비밀값은 어디에 저장할 것인가

애플리케이션 설정 파일이나 코드에 넣는 것은 위험함.

즉, 데이터 보안은 저장소만의 문제가 아니라

키, 접근권한, 운영 방식 전체의 문제임.

5.18 KMS 개요

AWS KMS는 Key Management Service의 약자이며, 암호화 키를 안전하게 생성, 저장, 관리할 수 있도록 도와주는 관리형 서비스임.

여기서 중요한 것은 KMS가 단순 암호화 기능이 아니라

키 관리 체계를 제공한다는 점임.

즉, KMS의 핵심은 다음과 같음.

데이터를 보호하려면 암호화만이 아니라
그 암호화에 사용되는 키를 안전하게 관리해야 한다.

5.19 왜 키 관리가 중요한가

암호화는 키가 안전하게 관리될 때만 의미가 있음.

예를 들어 데이터를 암호화해 두더라도 키가 무분별하게 노출되면 보호 효과가 크게 줄어듦.

키 관리에서 중요한 요소

  • 누가 키를 사용할 수 있는가
  • 누가 키를 생성/삭제할 수 있는가
  • 키 사용 기록을 남길 수 있는가
  • 키를 서비스와 안전하게 연동할 수 있는가
  • 키를 주기적으로 교체하거나 통제할 수 있는가

즉, KMS는 “암호화 알고리즘”보다

운영 가능한 키 통제 체계의 의미가 더 큼.

5.20 KMS가 연결되는 대표 서비스

AWS에서는 많은 관리형 서비스가 KMS와 자연스럽게 연계됨.

예

  • S3
  • EBS
  • RDS
  • EFS
  • Lambda 환경변수
  • Secrets Manager

이 구조의 의미는 매우 중요함.

운영자가 직접 암호화 라이브러리를 구현하지 않아도,

관리형 서비스 수준에서 암호화와 키 관리가 통합될 수 있기 때문임.

5.21 KMS를 어떻게 바라봐야 하는가

KMS는 다음 세 관점에서 이해하는 것이 좋음.

1. 데이터 암호화 기반

저장 데이터 보호

2. 키 접근 통제 기반

누가 어떤 키를 사용할 수 있는지 제어

3. 감사 가능성 기반

키 사용 이력과 변경 이력 추적 가능

즉, KMS는 단순 기능 서비스가 아니라

데이터 보안의 운영 중심축이라고 볼 수 있음.

5.22 비밀정보 관리가 필요한 이유

애플리케이션은 실행 과정에서 다양한 민감 정보를 사용함.

예

  • DB 비밀번호
  • API 키
  • 토큰
  • 인증서 관련 값
  • 외부 서비스 인증 정보

이런 값을 다음 위치에 직접 저장하는 것은 보안상 매우 위험함.

  • 소스코드
  • Git 저장소
  • 환경파일 평문
  • 사용자 데이터 스크립트
  • 컨테이너 이미지 내부

즉, 비밀정보는 데이터와는 별도로

전용 관리 구조를 가져가야 함.

5.23 Secrets Manager 개요

AWS Secrets Manager는 애플리케이션 비밀정보를 안전하게 저장하고 사용할 수 있게 도와주는 관리형 서비스임.

이 서비스의 핵심은 다음과 같음.

비밀정보를 코드나 파일에 직접 넣지 않고,
중앙에서 저장하고 통제된 방식으로 사용한다.

즉, Secrets Manager는 단순 저장소가 아니라

비밀값 운영 체계를 제공하는 서비스임.

5.24 Secrets Manager가 필요한 이유

비밀정보를 잘못 관리하면 다음 문제가 발생함.

1. 코드 노출 시 함께 유출될 수 있음

소스 저장소나 배포 아티팩트에 비밀이 섞이면 매우 위험함.

2. 회전(Rotation)이 어려움

비밀번호를 바꾸려면 코드와 환경파일까지 바꿔야 할 수 있음.

3. 권한 통제가 어려움

누가 어떤 비밀값을 읽을 수 있는지 명확히 제어하기 어려움.

4. 감사가 어려움

누가 언제 어떤 비밀에 접근했는지 추적이 어려울 수 있음.

즉, Secrets Manager는 비밀값 자체보다

비밀값의 생명주기와 접근통제를 관리하는 데 의미가 있음.

5.25 Secrets Manager와 일반 설정값의 차이

모든 설정값이 Secrets Manager 대상은 아님.

민감하지 않은 일반 설정값과 구분해서 봐야 함.

예

  • 일반 설정값: 리전 이름, 기능 토글, URL 경로
  • 비밀정보: 비밀번호, 토큰, 인증키, 자격증명

즉, Secrets Manager는 모든 환경설정을 저장하는 곳이 아니라

민감한 자격정보를 위한 저장소로 이해하는 것이 적절함.

5.26 KMS와 Secrets Manager의 관계

KMS와 Secrets Manager는 자주 함께 언급되지만 같은 역할은 아님.

항목KMSSecrets Manager
중심 역할암호화 키 관리비밀정보 저장 및 관리
보호 대상키와 암호화 연산비밀번호, 토큰, 자격정보
의미암호화 기반 제공비밀값 운영 체계 제공

즉,

  • KMS는 키를 다룸
  • Secrets Manager는 비밀값을 다룸

이라고 이해하면 됨.

그리고 Secrets Manager도 내부적으로 KMS와 결합해 사용할 수 있음.

5.27 보안 계층화의 의미

고급 보안 아키텍처에서는 한 계층만 강하게 해서는 부족함.

다음처럼 여러 계층이 함께 보호되어야 함.

엣지 계층

CloudFront, Shield, WAF

네트워크 계층

VPC, Security Group, Subnet 분리

애플리케이션 계층

인증, 입력 검증, 권한 로직

데이터 계층

KMS 기반 암호화, 저장소 정책

운영 계층

Secrets Manager, 로그, 감사 추적

즉, 보안은 하나의 거대한 기능이 아니라

여러 층을 겹겹이 쌓는 구조로 봐야 함.

5.28 보안 그룹과 WAF를 혼동하지 않아야 하는 이유

보안 그룹은 네트워크 레벨에서 포트와 소스/대상을 제어하는 도구임.

반면 WAF는 HTTP/HTTPS 요청 내용까지 보는 도구임.

즉, 다음처럼 역할이 다름.

  • 보안 그룹: TCP 443을 열지 말지
  • WAF: 443으로 들어온 요청 중 악성 패턴을 막을지

이 둘은 대체 관계가 아니라 서로 다른 계층의 보안 도구임.

5.29 좋은 보안 설계의 특징

고급 보안 아키텍처는 다음 특징을 가짐.

1. 외부 노출 최소화

꼭 필요한 진입점만 인터넷에 노출함.

2. 앞단에서 차단

비정상 요청은 최대한 엣지에서 차단함.

3. 데이터는 기본적으로 보호

암호화와 키 통제를 설계에 포함함.

4. 비밀값은 코드 밖으로 분리

애플리케이션과 비밀값의 생명주기를 분리함.

5. 운영 가능한 보안

보안 정책이 지나치게 수작업 의존적이면 유지가 어려움.

즉, 좋은 보안은 강한 통제만이 아니라

실제로 운영 가능한 구조여야 함.

5.30 설계 시 핵심 질문

고급 보안 설계에서는 다음 질문이 중요함.

1. 공격이 가장 먼저 들어오는 지점은 어디인가

보통 사용자 접점, 즉 엣지와 API 진입점이 됨.

2. 어떤 요청은 앞단에서 차단해야 하는가

애플리케이션까지 보내지 말아야 할 요청을 구분해야 함.

3. 어떤 데이터가 반드시 암호화되어야 하는가

민감한 데이터와 일반 데이터를 구분해야 함.

4. 비밀값을 어떻게 애플리케이션에 전달할 것인가

코드, 이미지, 설정파일에 직접 넣지 않는 구조가 중요함.

5. 권한과 감사는 어떻게 추적할 것인가

키 사용, 비밀 사용, 요청 차단 로그를 볼 수 있어야 함.

즉, 보안 설계는 설정값 암기가 아니라

위험 지점을 찾고 각 계층에 적절한 통제를 배치하는 일임.

5.31 다른 장과의 연결

이 장은 다른 장들과 매우 강하게 연결됨.

2장 멀티 계정 관리와 거버넌스 기초

보안 계정, 로그 아카이브, 중앙 통제 구조와 연결됨.

3장 고급 네트워크 연결 아키텍처

S3 엔드포인트 보안, 네트워크 경계, 중앙 허브 구조와 연결됨.

4장 컨테이너 및 현대적 애플리케이션 플랫폼

컨테이너 워크로드의 비밀값 관리, 권한 구조, 엣지 보호와 연결됨.

6장 비용 최적화와 엣지 아키텍처

CloudFront와 엣지 구조는 보안과 성능을 함께 설계해야 하기 때문임.

즉, 고급 보안 아키텍처는 독립 장이 아니라

전체 아키텍처의 모든 계층과 연결되는 주제임.

엣지, 네트워크, 애플리케이션, 데이터, 운영 계층에 맞는 통제를 배치하여
