3. 템플릿 기반 설정 자동화와 웹서버 종합 실습

3.1 설정 자동화가 필요한 이유

제2장에서는 패키지 설치, 사용자 생성, 디렉터리 생성, 파일 복사 같은 기본적인 서버 자동화 작업을 다루었음.

이 작업들만으로도 Ansible의 핵심 사용 방식은 이해할 수 있음. 하지만 실제 운영 환경에서는 단순 설치보다 설정파일 관리가 더 중요한 경우가 많음.

예를 들어 웹서버를 운영한다고 가정하면 다음과 같은 작업이 필요할 수 있음.

  • 서버별로 다른 호스트명 표시
  • 서버별 IP 주소를 페이지에 출력
  • 환경별 설정파일 배포
  • 설정파일 변경 시 서비스 재시작
  • 동일한 구조의 파일을 여러 서버에 조금씩 다르게 배포

이런 작업은 단순 copy 모듈만으로 처리하기에는 한계가 있음.

정적인 파일 하나를 모든 서버에 똑같이 복사하는 것은 가능하지만, 서버마다 다른 값을 반영해야 하는 순간부터는 더 유연한 방식이 필요함.

이 문제를 해결하는 기능이 template와 handler임.

즉, 이번 장의 핵심은 다음과 같음.

  • 서버마다 다른 값을 반영한 파일 자동 생성
  • 변경이 발생한 경우에만 서비스 재시작
  • 지금까지 배운 내용을 종합하여 웹서버 자동 구성 완성

3.2 copy와 template의 차이

Ansible에서 파일을 배포할 때 자주 사용하는 모듈은 copy와 template임.

두 모듈은 비슷해 보이지만 역할이 분명히 다름.

3.2.1 copy 모듈

copy 모듈은 제어 노드에 있는 파일을 대상 서버로 그대로 복사함.

즉, 파일 내용이 고정되어 있을 때 사용하기 좋음.

예를 들어 다음과 같은 정적인 HTML 파일은 copy로 충분히 배포 가능함.

<html>
  <body>
    <h1>Welcome</h1>
    <p>This page was deployed by Ansible.</p>
  </body>
</html>

이 파일은 어느 서버에 배포하든 내용이 동일함.

3.2.2 template 모듈

template 모듈은 파일 안에 변수를 포함할 수 있고, 실행 시 서버별 값으로 치환하여 배포함.

즉, 파일 구조는 같지만 일부 값이 서버마다 달라야 할 때 적합함.

예를 들어 다음과 같은 정보를 웹페이지에 표시하고 싶다고 가정함.

  • 호스트명
  • 운영체제 이름
  • IP 주소

이 값들은 서버마다 다를 수 있음.

이럴 때 template를 사용하면 한 개의 템플릿 파일로 여러 서버에 서로 다른 결과물을 만들어 배포할 수 있음.

즉, 차이는 아래처럼 정리할 수 있음.

  • copy : 파일을 그대로 복사함
  • template : 파일 안의 변수 값을 치환해서 배포함

3.3 템플릿 개념 이해

Ansible의 template 모듈은 Jinja2 문법을 사용함.

Jinja2는 Python 계열에서 널리 사용하는 템플릿 엔진으로, 변수 치환과 간단한 제어 구문을 지원함.

가장 기본적인 변수 치환 문법은 다음과 같음.

{{ 변수명 }}

예를 들어 Ansible에서 수집한 facts 중 호스트명을 출력하고 싶으면 다음처럼 작성할 수 있음.

{{ inventory_hostname }}

운영체제 이름은 다음처럼 출력 가능함.

{{ ansible_distribution }}

기본 IP 주소는 다음과 같이 출력 가능함.

{{ ansible_default_ipv4.address }}

즉, 템플릿은 정적인 파일 안에 동적인 값 삽입 지점을 만들어두는 방식이라고 이해하면 됨.

3.4 첫 번째 템플릿 파일 작성

이번 실습에서는 웹서버의 기본 페이지를 템플릿 방식으로 배포해봄.

각 서버에 접속했을 때 호스트명, 운영체제, IP 주소가 다르게 표시되도록 구성함.

파일명

index.html.j2

여기서 .j2 확장자는 Jinja2 템플릿 파일이라는 의미로 자주 사용함.

반드시 .j2여야 하는 것은 아니지만, 템플릿 파일임을 구분하기 위해 보통 붙임.

내용

<html>
  <head>
    <title>Ansible Web Server</title>
  </head>
  <body>
    <h1>{{ inventory_hostname }} 서버</h1>
    <p>배포판: {{ ansible_distribution }}</p>
    <p>IP 주소: {{ ansible_default_ipv4.address }}</p>
  </body>
</html>

내용 해설

<h1>{{ inventory_hostname }} 서버</h1>

inventory에서 인식한 호스트명을 출력함.

같은 템플릿을 여러 서버에 배포해도 서버별 이름이 달라질 수 있음.

{{ ansible_distribution }}

Ansible facts 중 운영체제 배포판 정보를 출력함.

Ubuntu, Debian 등 대상 서버 정보에 따라 달라질 수 있음.

{{ ansible_default_ipv4.address }}

대상 서버의 기본 IPv4 주소를 출력함.

즉, 이 템플릿은 서버마다 같은 구조를 갖지만 값은 다르게 생성됨.

3.5 템플릿 배포 Playbook 작성

이제 위 템플릿을 실제로 웹서버에 배포하는 playbook을 작성함.

파일명

deploy-template.yml

내용

---
- name: Deploy templated web page
  hosts: web
  become: true

  tasks:
    - name: Deploy index page from template
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        mode: '0644'

구성 해설

hosts: web

web 그룹 서버를 대상으로 실행함.

즉, 웹서버 역할을 맡는 서버들만 대상임.

ansible.builtin.template

템플릿 파일을 읽어 변수 치환 후 원격 서버에 배포하는 모듈임.

src: index.html.j2

제어 노드에 있는 템플릿 파일 경로임.

dest: /var/www/html/index.html

원격 서버에서 최종 배치될 경로임.

nginx 기본 웹 루트 경로를 사용함.

mode: '0644'

원격 서버에 배포되는 파일의 권한을 지정함.

3.6 템플릿 배포 실행 및 확인

실행

ansible-playbook -i inventory.ini deploy-template.yml

정상 실행되면 각 서버에 index.html이 생성되거나 갱신됨.

확인 방법 1: 원격에서 파일 확인

ansible -i inventory.ini web -m command -a "cat /var/www/html/index.html"

이 명령을 통해 각 서버에 실제 어떤 HTML 내용이 생성되었는지 확인할 수 있음.

확인 방법 2: 브라우저로 접속

웹서버 IP 주소로 접속하면 다음과 같은 내용이 나타나야 함.

  • 서버별 호스트명
  • 운영체제 정보
  • IP 주소

즉, 같은 템플릿 파일을 사용했지만 각 서버에서 서로 다른 결과물이 생성되었음을 확인할 수 있음.

3.7 Handler 개념 이해

Ansible에서 파일을 배포하거나 설정을 변경한 후, 그 내용을 반영하기 위해 서비스를 재시작해야 하는 경우가 많음.

예를 들어 nginx 설정파일이 바뀌었는데 서비스를 재시작하지 않으면 새로운 설정이 적용되지 않을 수 있음.

하지만 여기서 중요한 문제가 있음.

설정파일이 바뀌지 않았는데도 매번 재시작하면 비효율적일 수 있음.

서비스 재시작은 불필요한 순간에도 순간적인 서비스 영향이나 로그 노이즈를 만들 수 있음.

이 문제를 해결하는 기능이 handler임.

handler는 일반 task와 비슷해 보이지만, 다음과 같은 특징이 있음.

  • 평소에는 실행되지 않음
  • 특정 task가 notify를 보냈을 때만 실행됨
  • 해당 task에서 실제 변경이 발생했을 때만 동작함
  • 보통 서비스 재시작, reload 같은 후속 작업에 사용함

즉, handler는 조건부 후속 처리기라고 이해하면 됨.

3.8 notify와 handler의 관계

handler는 단독으로 실행되는 것이 아니라, 어떤 task가 notify를 통해 호출해야 실행됨.

동작 구조는 다음과 같음.

Task 실행
 ├─ 변경 없음
 │   └─ handler 실행 안 함
 └─ 변경 발생
     └─ notify 발생
         └─ handler 실행

이 구조의 장점은 다음과 같음.

  • 변경이 있을 때만 서비스 재시작
  • 불필요한 재시작 방지
  • 설정파일 변경과 후속 조치를 자연스럽게 연결 가능

3.9 Handler 예제 작성

이번에는 설정파일이 바뀌면 nginx를 재시작하는 playbook을 작성해봄.

파일명

deploy-template-with-handler.yml

내용

---
- name: Deploy page with handler
  hosts: web
  become: true

  tasks:
    - name: Deploy index page
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        mode: '0644'
      notify: Restart nginx

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

구조 해설

notify: Restart nginx

현재 task에서 실제 변경이 발생하면 Restart nginx라는 handler를 호출함.

handlers:

handler 목록을 정의하는 영역임.

name: Restart nginx

호출될 handler 이름임.

이 이름은 위 notify 값과 정확히 일치해야 함.

ansible.builtin.service

nginx 서비스를 재시작함.

3.10 Handler 동작 확인

첫 번째 실행

ansible-playbook -i inventory.ini deploy-template-with-handler.yml

첫 실행에서는 보통 템플릿 파일이 새로 배포되므로 changed가 발생하고, 그 결과 handler가 실행됨.

예상 흐름:

  • 템플릿 배포 task → changed
  • notify 발생
  • Restart nginx handler 실행

두 번째 실행

동일한 템플릿 파일 내용으로 다시 실행하면, 이미 원하는 상태라면 changed가 발생하지 않을 수 있음.

이 경우 handler도 실행되지 않음.

즉, 재실행 결과를 보면 다음 차이를 확인할 수 있음.

  • 변경 있음 → handler 실행
  • 변경 없음 → handler 미실행

이 특성이 Ansible의 매우 중요한 실무 장점 중 하나임.

3.11 템플릿과 handler를 함께 사용하는 이유

실무에서는 설정파일 자동화와 서비스 재시작이 거의 항상 같이 등장함.

예를 들어 다음과 같은 상황을 생각해볼 수 있음.

  • nginx 설정파일 변경 후 재시작
  • Apache 가상호스트 변경 후 reload
  • 애플리케이션 설정파일 변경 후 서비스 재시작
  • systemd unit 파일 변경 후 daemon reload 및 재시작

이런 작업은 사람이 직접 수행하면 다음 순서를 기억해야 함.

  1. 파일 수정
  1. 문법 확인
  1. 서비스 재시작 또는 reload
  1. 정상 동작 확인

Ansible에서는 이 흐름을 playbook과 handler로 묶어서 자동화할 수 있음.

즉, 템플릿과 handler를 조합하면 “파일 변경 → 필요한 경우에만 후속 처리” 구조를 매우 자연스럽게 구현할 수 있음.

3.12 종합 실습 목표

이제 제1장과 제2장에서 배운 내용을 모두 활용해 웹서버 자동 구성 playbook을 완성함.

이번 종합 실습의 목표는 web 그룹 서버를 다음 상태로 만드는 것임.

  • 공통 패키지가 설치되어 있어야 함
  • 관리자 계정이 생성되어 있어야 함
  • 필요한 디렉터리가 존재해야 함
  • nginx가 설치되어 있어야 함
  • nginx 서비스가 실행 중이어야 함
  • 서버별 정보가 포함된 웹페이지가 배포되어 있어야 함
  • 템플릿 변경 시 nginx가 재시작되어야 함

즉, 단순 설치가 아니라 웹서비스 가능한 서버 상태를 자동으로 완성하는 것이 목적임.

3.13 종합 실습용 템플릿 파일 작성

파일명

index.html.j2

내용

<html>
  <head>
    <title>Web Server Information</title>
  </head>
  <body>
    <h1>{{ inventory_hostname }} 서버</h1>
    <p>이 페이지는 Ansible 템플릿으로 배포되었음.</p>
    <p>운영체제: {{ ansible_distribution }}</p>
    <p>호스트명: {{ ansible_hostname }}</p>
    <p>IP 주소: {{ ansible_default_ipv4.address }}</p>
  </body>
</html>

이 템플릿은 브라우저에서 접속했을 때 서버별 식별 정보를 바로 보여주도록 구성했음.

3.14 종합 실습 Playbook 작성

파일명

web-config.yml

내용

---
- name: Configure web servers
  hosts: web
  become: true

  vars:
    common_packages:
      - vim
      - curl
      - git

  tasks:
    - name: Install common packages
      ansible.builtin.apt:
        name: "{{ item }}"
        state: present
        update_cache: true
      loop: "{{ common_packages }}"

    - name: Create webadmin user
      ansible.builtin.user:
        name: webadmin
        shell: /bin/bash
        create_home: true

    - name: Create /opt/webinfo directory
      ansible.builtin.file:
        path: /opt/webinfo
        state: directory
        mode: '0755'

    - name: Install nginx package
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Start nginx service
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    - name: Deploy templated index page
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        mode: '0644'
      notify: Restart nginx

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

3.15 종합 실습 Playbook 해설

위 playbook은 지금까지 배운 핵심 내용을 모두 포함하고 있음.

각 task의 역할을 자세히 보면 다음과 같음.

Install common packages

공통적으로 필요한 패키지들을 반복문으로 설치함.

여기서는 vim, curl, git을 예시로 사용했음.

Create webadmin user

웹서버 운영용 계정을 생성함.

실습에서는 단순 예시이지만, 실제 환경에서는 운영용 별도 계정 생성이 자주 필요함.

Create /opt/webinfo directory

운영용 디렉터리를 생성함.

디렉터리 생성 실습을 실제 서비스 구성 흐름 안에 포함한 것임.

Install nginx package

웹서비스를 위한 nginx 패키지를 설치함.

Start nginx service

nginx 서비스가 실행 중이어야 함을 선언함.

또한 부팅 시 자동 시작되도록 설정함.

Deploy templated index page

서버별 정보를 포함하는 HTML 페이지를 템플릿 방식으로 배포함.

notify: Restart nginx

HTML 페이지 변경이 발생하면 nginx 재시작 handler를 호출함.

정적 페이지 배포에는 꼭 재시작이 필요하지 않을 수도 있지만, handler 동작 원리를 학습하기 위해 포함한 구조임.

3.16 종합 실습 실행

실행 명령

ansible-playbook -i inventory.ini web-config.yml

정상적으로 실행되면 다음 흐름이 순서대로 처리됨.

  1. 공통 패키지 설치
  1. 계정 생성
  1. 디렉터리 생성
  1. nginx 설치
  1. nginx 시작
  1. 템플릿 페이지 배포
  1. 변경 발생 시 handler 실행

3.17 종합 실습 결과 확인

실습 후에는 반드시 결과를 검증해야 함.

자동화는 실행만 하는 것이 아니라, 원하는 상태가 실제로 만들어졌는지 확인하는 과정까지 포함해야 완성됨.

확인 1. 사용자 계정 생성 여부

ansible -i inventory.ini web -m command -a "id webadmin"

확인 2. 디렉터리 생성 여부

ansible -i inventory.ini web -m command -a "ls -ld /opt/webinfo"

확인 3. nginx 서비스 상태

ansible -i inventory.ini web -m command -a "systemctl status nginx"

확인 4. 배포된 HTML 파일 내용

ansible -i inventory.ini web -m command -a "cat /var/www/html/index.html"

확인 5. 브라우저 접속

웹서버 IP 주소로 접속해서 다음이 보이는지 확인함.

  • 서버명
  • 운영체제 정보
  • IP 주소

즉, 서버별로 서로 다른 정보가 페이지에 반영되어 있어야 함.

3.18 재실행과 멱등성 확인

종합 실습 playbook도 같은 원리로 다시 실행해봄.

ansible-playbook -i inventory.ini web-config.yml

이미 원하는 상태라면 대부분의 task는 ok로 처리될 수 있음.

템플릿 파일이 바뀌지 않았다면 handler도 실행되지 않을 가능성이 큼.

이 과정을 통해 교육생은 다음을 직접 확인할 수 있음.

  • Ansible은 같은 작업을 여러 번 실행해도 안정적으로 동작함
  • 이미 원하는 상태라면 불필요한 변경을 최소화함
  • handler는 변경이 있을 때만 동작함

이 확인 과정이 매우 중요함.

Ansible의 핵심 장점은 “한 번 실행하는 자동화”가 아니라 “반복 실행 가능한 자동화”에 있기 때문임.

3.19 자주 발생하는 오류와 점검 방법

제3장 실습에서는 주로 템플릿, facts, 서비스 재시작과 관련된 문제가 발생할 수 있음.

3.19.1 템플릿 변수 오류

증상:

  • 템플릿 렌더링 실패
  • 변수 이름을 찾을 수 없다는 오류 발생

원인:

  • 변수명 오타
  • 존재하지 않는 facts 사용
  • gather_facts 비활성 상태

확인 방법:

ansible -i inventory.ini web -m setup

3.19.2 파일 경로 오류

증상:

  • src 파일을 찾을 수 없음
  • 원격 서버 경로가 잘못됨

원인:

  • 템플릿 파일 위치 오류
  • playbook 실행 위치와 파일 경로 혼동

3.19.3 nginx 서비스 오류

증상:

  • nginx 시작 실패
  • handler 실행 후 서비스 상태 비정상

원인:

  • 잘못된 설정파일
  • 패키지 설치 미완료
  • 시스템 포트 충돌

확인 방법:

ansible -i inventory.ini web -m command -a "systemctl status nginx" -b

3.19.4 웹페이지 접속 불가

원인:

  • nginx 미기동
  • 방화벽 문제
  • 보안그룹 또는 네트워크 접근 문제
  • 웹 루트 파일 배포 실패

즉, Ansible playbook이 성공해도 실제 서비스 접근은 별도 검증이 필요함.

3.20 정리

  • copy는 정적인 파일 복사에 적합함
  • template는 변수 치환이 필요한 파일 배포에 적합함
  • Jinja2 문법을 이용해 서버별 정보를 파일에 반영할 수 있음
  • notify와 handler를 사용하면 변경이 있을 때만 후속 작업을 수행할 수 있음
  • 템플릿과 handler를 조합하면 설정 변경과 서비스 재시작을 효율적으로 자동화할 수 있음
  • 종합 playbook을 통해 웹서버 자동 구성 흐름을 완성할 수 있음
  • playbook 재실행을 통해 멱등성과 handler 동작 원리를 확인할 수 있음

Ansible만으로 여러 대의 서버에 웹서비스 구성을 자동 적용하고, 서버별 차이를 반영한 설정파일 배포까지 수행할 수 있음.
